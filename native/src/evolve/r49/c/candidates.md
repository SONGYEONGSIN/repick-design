# r49 / c — Seller Onboarding Checklist

One-line concept: a whole-screen, four-step sequential checklist ("Verify your identity" → "Link a payout account" → "Set up your storefront profile" → "List your first item") with a done/current/locked state per row, a progress ring + "N of M complete" text, and one real interaction (a "Mark as done" button on the current step that promotes the next step and fires a single polite live-region announcement).

Values/rules the brief left open that I had to decide myself:

1. **How many steps, and which four.** The brief named example steps but not an exact count. ①Picked exactly 4: identity verification, payout linking, storefront profile, first listing. ②As literal strings in `data.ts`. ③This is the smallest set that still tells a coherent "you can't sell until these are done" story and matches the brief's own four examples almost verbatim, while staying clearly distinct from the existing standalone "seller verification (submission)" screen (just step 1's sub-flow) and "pro seller plan" screen (a subscription tier picker, unrelated).

2. **Initial demo state (how many steps start "done").** Nothing in the brief fixed this. ①Chose: step 1 done, step 2 current, steps 3–4 locked (i.e. "1 of 4 complete" at load). ②Fixed array `INITIAL_COMPLETED_STEP_IDS = ["verify-identity"]` in `data.ts`, no randomness. ③Starting with exactly one step already done demonstrates all three row states (done/current/locked) simultaneously and lets the one real interaction ("Mark as done") visibly advance the current pointer and unlock the next row, which a 0-done or already-all-done start state couldn't show.

3. **What the "current step" row's no-op tap does vs. the real interaction.** The brief says tapping the current step would navigate onward but should be a no-op since there's nowhere to go, and separately requires at least one real interaction. ①Split these into two sibling controls per row: the row body itself is the no-op/disabled Pressable (current: no-op press feedback only, no hint; locked: disabled with a spoken+visible "Complete \"X\" first" reason), and a separate "Mark as done" button (visible only on the current row) is the one real state-mutating interaction. ②Implemented as two sibling `Pressable`s inside one row `View` — deliberately never nested Pressable-in-Pressable. ③Keeps the "fake navigation" affordance honest (no accessibilityHint promising a screen that doesn't exist) while still giving the screen a genuine, testable interaction as required by the a11y rules.

4. **Progress indicator shape.** Brief said "progress ring/bar" as an example, not mandating either. ①Built an actual SVG ring (via `react-native-svg`, already a repo dependency) with a numeral in the center, paired with adjacent "N of M complete" text and a "X steps left" / "shop is ready" subline. ②New `OnboardingProgressRing.tsx` component, driven purely by a `ratio` prop derived from state — no own state, no random/time source. ③A true ring reads as a more deliberate "progress" metaphor than a bar for a short, sequential checklist, and the repo already ships `react-native-svg` so this didn't require a new dependency.

5. **Locked-reason copy format.** DNA requires locked rows to explain *why* via visible copy or hint (e.g. "Complete step 2 first") but didn't fix exact wording. ①Used `Complete "<previous step's title>" first.` referencing the step's own title rather than its ordinal number. ②Computed in the row from `previousStepTitle`, shown both as visible caption text and as the disabled Pressable's `accessibilityHint`. ③Naming the actual blocking step by title is more useful/concrete than a bare ordinal ("step 2"), especially for a screen reader user who may not have the full list order memorized.
