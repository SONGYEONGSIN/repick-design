# r49 / b — Item Comparison

**Concept:** A two-pane spec-comparison table (frozen attribute-label column + horizontally scrolling item columns) that lets a buyer stack 2–3 watched items side-by-side across price, condition, match %, seller rating, and shipping time, with non-destructive per-item removal, a catalog-driven "add another item" picker, and an optional best-value highlight that never relies on color alone.

**Values/rules I had to decide myself (not in the brief):**

1. **What counts as "better" per attribute, and the tie rule** → decided price and shipping time are lower-is-better, condition grade/match %/seller rating are higher-is-better (condition ranked via a fixed Like New > Very Good > Good > Fair order); if two or more items share the single best value for a row, no cell is marked "Best" (tie = no winner) → chosen because the brief names the dimensions but not their comparison direction, and silently crowning one side of an exact tie would be a real correctness bug, not just a style choice.
2. **Minimum comparison size and what happens at zero items** → decided removal is allowed all the way down to 0 items (no artificial floor of 2), at which point the table is replaced by the required empty state ("Add an item to start comparing" + action) → chosen because the brief's own UX checklist mandates an empty-state-with-action pattern, and enforcing a hard floor of 2 would make that state unreachable through the one interaction (remove) that's supposed to produce it.
3. **Add-item picker as inline expanding panel vs. modal** → decided to render it as an inline panel appended below the table/empty-state rather than a `Modal` overlay → chosen for structural novelty (the DNA rule bars reusing ref/callback/union-state shapes across screens) and because a full-screen modal felt heavier than the action warrants for picking from a short catalog list.
4. **Highlight-better default state and its control type** → decided the toggle defaults to "on" (highlighting visible from first paint) and is built as a custom Pressable track+knob rather than the RN `Switch` primitive → chosen so the comparison's main value (seeing the winner per row) is demonstrated immediately rather than requiring a first interaction to discover, and a custom control kept full styling control under `tokens` instead of platform-themed `Switch` colors.
5. **Watched-item catalog size and starting selection** → decided on a fixed 5-item catalog with items `wi-1` and `wi-2` preselected into the comparison → chosen to leave exactly 3 items addable through the picker (enough to demonstrate hitting the 3-item cap) while keeping the dummy dataset small and fully deterministic.
