# r49 / a — Nearby Sellers Map Browse

One-line concept: a buyer-facing discovery screen that toggles between a stylized abstract "map" of nearby meetup-eligible sellers (fixed-position pins over a distance-ring backdrop) and a virtualized list, with a shared filter sheet (distance radius + category) and two-way selection sync between a tapped pin and its matching list row.

Values/rules not specified in the brief that I had to decide myself:

1. **How to represent "geographic position" without a map SDK** → fixed `pinXPct`/`pinYPct` (0–100) literals per seller in `data.ts`, rendered as `left/top` percentage strings on an absolutely-positioned 44×44 hit area inside a square `aspectRatio: 1` canvas, centered via negative margins (not transforms, since RN transform doesn't accept percentage units) → chosen because it's the simplest fully-deterministic way to get a map-like layout with zero runtime randomness and no third-party map dependency, while still giving each pin a real 44×44 touch target regardless of its visual dot size.

2. **Distance-ring backdrop as decorative-only vs. functional** → rendered three concentric rings + labels (1/3/5 mi) as a purely visual scale reference, wrapped in a container marked `accessibilityElementsHidden` + `importantForAccessibility="no-hide-descendants"` so screen readers skip straight to the real pins → chosen because the rings don't carry filter logic themselves (the filter sheet's radius chips do), so exposing them to AT would just be redundant noise competing with the actually-interactive pins.

3. **Pin↔list sync mechanism** → tapping a pin sets `selectedSellerId` and opens an inline callout card (not a modal/navigation) with a "View in list" button; pressing it switches `viewMode` to "list" and, via a `pendingScrollSellerId` ref consumed in a `useEffect` keyed on `viewMode`, calls `FlatList.scrollToIndex` once the list has (re)mounted. Tapping a list row's "View on map" button does the reverse (sets selection + switches to map) → chosen because the brief offered two acceptable accessibility strategies ("pin press scrolls list to the item" OR "pin itself is a fully accessible Pressable") and this does both: every pin already carries a full `accessibilityLabel` (name + category + distance + selected state), and the explicit "View in list"/"View on map" buttons give a deterministic, discoverable path between the two views for all users, not just an implicit side-effect of pressing the pin.

4. **Filter sheet draft vs. applied state** → the sheet edits a separate `draftFilters` copy (seeded from `appliedFilters` on open) and only commits on "Apply filters"; "Cancel" or the scrim discards the draft → chosen so the map/list don't visibly jump around while the user is still deciding between radius/category chips inside the sheet, and so there's a clean moment ("Apply") to fire the one live-region announcement.

5. **FlatList row height / `getItemLayout`** → gave every list row a fixed height (`SELLER_ROW_HEIGHT = 136`) that never changes with selection (selection only changes border/background color, never adds/removes a line of content), specifically so `getItemLayout` can be supplied and `scrollToIndex` (used by the pin→list sync) is reliable instead of best-effort → chosen over a variable-height "expand on select" row because the brief's pin-tap-scrolls-to-list accessibility pattern needs a dependable scroll target.

6. **Live region scope** → a single live region above the view toggle announces only post-filter-apply / reset result counts ("Showing N sellers within X mi."), with `accessibilityRole="alert"` applied only for `LIVE_MESSAGE_VISIBLE_MS` (2600 ms) after a change and then reverted to an empty string → chosen to satisfy the brief's "at most one live region, and only flag `alert` right after the transition" rule, and I picked filter-apply/reset as the one state change in this screen that actually changes "how many results are reachable," per the brief's description of what qualifies.
