# page-commission — 주문 제작

## 0. 이 스킬의 자리

| 스킬 | 무엇을 정하나 | 입력 |
|---|---|---|
| `dash-evolve` | **시스템이** 정한다 (미채움 큐) | 라운드 수 |
| `design-evolve` | **designer가** 발산한다 | 타깃 이름 |
| `design-polish` | 이미 있는 것을 다듬는다 | 완성된 `page.tsx` |
| **`page-commission`** | **사용자가** 정한다 | **요구사항 (대화로 캐낸다)** |

이 스킬의 값어치는 생성이 아니라 **인터뷰**에 있다. 생성 자체는 자율 루프와 같은 정본·같은 게이트를 쓴다. 다른 것은 "무엇을 만들지"가 탐색이 아니라 **사용자의 실제 필요**에서 온다는 점뿐이다.

**불변식**
- 산출물은 `app/src/app/commissioned/<slug>/` 에만 만든다. 자율 루프 산출물(`*-evolve/`)·승격 작품과 섞지 않는다
- **정본을 바꾸지 않는다** — `vault/00-principles/*` 는 읽기 전용. 이 스킬의 결과물은 3렌즈 판정을 거치지 않았으므로 delta·프로파일의 근거가 될 수 없다
- `works.ts` 등재는 **사용자가 명시적으로 요청할 때만**. 등재하면 갤러리·큐·다양성 집계에 들어가므로 기본은 미등재다

## 1. 인터뷰 — 이 스킬의 본체

**한 번에 다 묻지 않는다.** 답이 다음 질문을 정한다. 답이 이미 정본이나 레포에 있으면 **묻지 말고 읽는다**(게이트 규칙·결정론 계약·활자 화이트리스트·토큰).

### 1-1. 타입 판별 (먼저, 반드시)

사용자가 부르는 이름과 실제 타입이 자주 다르다. "랜딩페이지"라고 해도 하나의 상품을 파는 화면이면 `product-detail`이고, 한도 도달 후 업그레이드를 권하는 화면이면 `paywall`이다.

> **이 페이지에 도착한 사람이 다음에 무엇을 하길 바라나?** 하나만 고른다면.

그 답으로 타입을 제안하고 사용자에게 확인받는다. 그다음 세 갈래로 갈린다.

| 갈래 | 조건 | 브리프 |
|---|---|---|
| **A** | 프로파일 있음 (10종: dashboard·settings·landing·login·404·catalog·scene·product-detail·paywall·profile) | `page-brief-core` + 해당 프로파일 |
| **B** | `PAGE_TYPES`에 있으나 프로파일 없음 (blog·about·careers·contact·developers·integration·media-kit·mobile) | `page-brief-core` + **§1-3 계약 인터뷰** |
| **C** | `PAGE_TYPES` 밖 (가격표·체인지로그·이벤트 신청 …) | `page-brief-core` + **§1-3 계약 인터뷰** (더 길게) |

목록은 `app/src/lib/works.ts`의 `PAGE_TYPES`와 `page-brief-core` §"타입 프로파일 목록"에서 **매번 읽는다** — 여기 복사해 두면 갈라진다.

### 1-2. 공통 질문 — **사용자 말로 묻는다**

**정본 용어를 그대로 묻지 마라.** "핵심 증명"·"도메인 실체"·"아키타입"은 이 레포의 어휘다. 처음 듣는 사람은 답할 수 없고, 물으면 "알아서 해줘"가 나온다. **묻는 말과 기록하는 말을 분리한다** — 평이하게 묻고, 정본 용어로의 변환은 스킬이 한다.

| 기록할 것 | 묻는 말 |
|---|---|
| 회사·브랜드명 | "회사(또는 서비스) 이름이 뭐예요?" |
| 핵심 증명 | "이 페이지를 본 사람이 **딱 하나만** 기억한다면 뭐였으면 좋겠어요?" |
| 도메인 실체 | "뭘 파는(보여주는) 곳이에요? 가격대나 규모가 어느 정도인지도 알려주세요" |
| 읽는 사람 | "누가 볼 페이지예요? 우리를 이미 아는 사람인가요, 처음 보는 사람인가요?" |
| 분량 | "한 화면에서 끝났으면 좋겠어요, 아니면 쭉 내려보는 형태?" |
| **페이지 언어** | "페이지를 **한국어**로 쓸까요, **영어**로 쓸까요? 아니면 둘 다 넣고 토글로 전환할까요?" |

- **회사명을 다른 질문에 묶지 마라.** 복합 질문에 넣으면 실행 단계에서 항목이 떨어져 나간다 — 2026-08-08 첫 시험에서 실제로 그랬다(도메인 선택지에 이름 칸이 없어 designer가 `Tillmark`를 지었다). 사용자가 답을 이미 갖고 있을 확률이 가장 높은 항목이고, 페이지에 그대로 실린다
- **플랜·제품·모델 이름**은 "직접 정할래요 / 지어드릴까요" 선택지로 준다. 위임은 괜찮고, **안 물어서 designer가 정하는 것은 사고다** — 결과가 같아도 성격이 다르다
- **헤드라인 카피**도 한 번 묻는다 — "생각해 둔 문구 있어요, 아니면 지어드릴까요"
- **페이지 언어는 반드시 묻는다.** [[page-brief-core]] §1은 "영문 전용"을 강제하지만 그 근거가 **"글로벌 벤치마크 정합"** — 즉 카탈로그 작품이 Linear·Stripe급과 나란히 비교되기 위한 규칙이다. **주문 제작은 기본이 카탈로그 미등재라 그 근거가 적용되지 않는다.** 한국 회사 소개 페이지를 영문으로 쓸 이유가 없다.
  - 영문 전용은 **기계로 강제되지 않는다** — `static-check`에 한글 검사가 없다(2026-08-08 실측: 한글 소스 위반 0). 자율 라운드에서는 judge 렌즈1이 대조하는데 **주문은 judge를 안 거친다.** 지금까지 영문이었던 것은 오케스트레이터가 designer 프롬프트에 적어 넣었기 때문이다
  - **한 페이지 내 혼용은 언어와 무관하게 금지.** §1의 이 부분은 그대로 살아 있다 — 결함이 맞다
  - **i18n(둘 다)을 고르면 designer에게 세 가지를 명시하라**: ① 카피가 두 배이므로 분량 예산을 다시 잡을 것 ② 한글 본문은 Pretendard 고정이라 **디스플레이 활자 선택이 라틴에만 걸린다**(`--font-display-*`는 한글 글리프가 없다) ③ 토글 자체가 인터랙션 1종으로 계산된다
- **사업 규칙은 묻지 않는다** — 할부 조건·수수료율·과금 단위 같은 것. 페이지 요청을 사업 설계 상담으로 바꾸면 안 되고, 디자인 산출물의 숫자는 **예시**여서 그럴듯하고 내부적으로 일관되면 된다. 사용자가 아는 사업 사실은 위 "도메인 실체"에서 자연히 나오고(첫 시험에서 가격 대역이 그렇게 나왔다), 나머지는 designer가 메운 뒤 §5에서 분류돼 보고된다

### 1-3. 타입 계약 (갈래 B·C) — **묻지 말고 제안해 확인받는다**

프로파일이 없으면 그 자리에서 계약을 세운다. 다만 **계약 항목을 사용자에게 직접 묻지 마라** — "핵심 판정 기준을 정해 주세요"에 답할 수 있는 사용자는 없다. §1-2 답변에서 **도출해 제안하고 확인만 받는다.**

| 항목 | 어떻게 얻나 |
|---|---|
| **필수 요소** 3~6개 | **묻는다** — "이게 없으면 말이 안 된다 싶은 게 뭐예요?" 후보를 함께 제시 |
| **핵심 판정 기준** | **도출해 제안** — 핵심 증명 + 필수 요소에서 구조 기준 한 줄을 뽑아 "이게 맞나요?" |
| **인터랙션 최소 개수** | **도출** — 필수 요소 중 조작이 필요한 것을 세면 나온다 |
| **스크롤 연출** | **도출** — 분량 답이 정한다 |
| **인접 타입과의 차이** | **도출해 제안** — "○○ 페이지와 비슷한데 이 점이 다른 것 같아요, 맞나요?" |
| **기존 작품과의 관계** | **묻지 않는다** — 사용자는 카탈로그를 모른다. 스킬이 읽고 판단한다 |

사용자가 "모르겠다"고 하면 **후보를 제시해 고르게 한다** — 빈칸으로 두고 designer가 지어내게 하지 않는다. 후보를 골랐다는 사실도 기록한다.

### 1-4. 제약

- **테마·액센트·활자** — 지정이 있나. 없으면 `node scripts/catalog-variety.mjs`로 카탈로그 분포를 보여주고 **덜 쓰인 축을 제안**한다(강제는 아니다)
- **하드게이트는 협상 대상이 아니다** — 결정론·이모지·원시 img·외부 무작위 이미지·폰트 화이트리스트·a11y 95는 사용자가 원해도 못 푼다. 요구가 이와 충돌하면 그 자리에서 말하고 대안을 낸다

## 2. 확인받고 진행 — **세 가지를 보인다**

인터뷰 결과를 다음과 합쳐 **1회용 생성 브리프**를 만든다:

- `vault/00-principles/page-brief-core.md` (전 타입 강제)
- 갈래 A면 해당 타입 프로파일 / B·C면 §1-3에서 세운 계약
- 해당 타입의 미종결 delta (`vault/00-principles/<type>-deltas-provisional.jsonl`, 있으면)
- `vault/20-catalog/` 중 관련분 — 차트가 있으면 `charts.catalog.md`, 색은 `colors.catalog.md`, 전 타입 `ux-guidelines.catalog.md`(Plat=web/both), 연출이 있으면 `motion.catalog.md`

그다음 **사용자에게 세 가지를 보이고 승인받는다.** 계약만 읽어 주는 것으로는 부족하다 — 페이지의 **모양**을 사용자가 못 본 채 생성으로 넘어가면 골격이 designer 독단이 된다(2026-08-08 첫 시험: "위는 판독행·아래는 조작행"이라는 전체 골격을 사용자가 **스크린샷에서 처음** 봤다).

**① 타입 계약** — §1-3에서 세운 것. 특히 **핵심 증명**과 **핵심 판정 기준**은 그대로 읽어 준다. 여기서 어긋나면 뒤가 전부 어긋난다.

**② 구성안** — 이 페이지가 **무엇으로 이루어지는가.** 섹션 목록과 배치 순서, 무엇이 어디에 놓이는가. 한 화면이면 화면 분할, 스크롤이면 섹션 순서. **3~6줄이면 족하다** — 도면이 아니라 합의점이다.

**③ 제작에서 중요하게 볼 것** — 이 페이지에서 특히 조심할 것과 우선할 것. 적용할 **함정 회피**를 여기서 밝힌다(예: "한 화면 + 다열 비교라 390px에서 표가 깨질 위험이 가장 큽니다 — 모바일은 카드로 갑니다"). 사용자가 *"그건 상관없어요"* 또는 *"그게 제일 중요해요"*라고 말할 유일한 기회다.

## 3. 생성

- **designer 1명.** 자율 루프의 3병렬은 발산이 목적이라 그렇고, 여기는 요구가 정해져 있으므로 후보 경쟁이 필요 없다. 사용자가 "몇 개 보고 고르고 싶다"고 하면 그때만 늘린다
- 경로: `app/src/app/commissioned/<slug>/page.tsx` (+ 클라이언트 컴포넌트·`data.ts` 분리 허용, 자기 폴더만)
- designer에게 **조립한 브리프 전문**을 넘긴다. 정본 경로만 주고 알아서 읽으라고 하지 않는다 — 인터뷰로 얻은 맥락이 정본에는 없다
- **완료 확인 — 파일 존재는 완료가 아니다.** designer가 비동기로 돌면 산출물을 여러 번에 걸쳐 쓰고, **보고 직전에 멈추는 일이 잦다**(2026-08-08 첫 시험에서 3회 연속 발생 — 1회차는 `page.tsx`가 통째로 없었고, 2·3회차는 파일은 완성됐으나 보고가 없었다). 완료 알림이 와도 다음 셋을 직접 확인한 뒤에만 §4로 넘어간다:
  1. **라우트가 성립하는가** — `page.tsx` 존재. 없으면 라우트 자체가 없다
  2. **파일이 멈췄는가** — 소스 해시를 20초 간격으로 두 번 떠서 같은지 본다. 다르면 아직 쓰는 중이다
     ```bash
     cat app/src/app/commissioned/<slug>/* | shasum | cut -d" " -f1
     ```
  3. **폴더 밖을 건드렸는가** — `git status --short | grep -v commissioned/` 가 비어야 한다
  미완성이면 **처음부터 다시 시키지 말고** 같은 에이전트를 이어서 돌린다(컨텍스트를 갖고 있다). 무엇이 없는지 구체적으로 적어 준다.
- **브리프 구멍 보고** — designer에게 "요구·브리프에 없어 스스로 정한 값"을 함께 내게 하되, **§5의 5분류(이름 / 숫자·조건 / 카피 / 구조·미학 / 접근성·기술)로 묶어서** 내게 한다. 평평한 목록으로 받으면 오케스트레이터가 다시 분류해야 하고, 그 과정에서 항목이 샌다. **사용자가 말하지 않아 designer가 정한 것**이 무엇인지 아는 것이 인수의 핵심이다

## 4. 게이트

**게이트 전에 타입 검사가 먼저다.** `gate.mjs`는 정적 규칙·린트·폭·Lighthouse를 보지만 **컴파일 여부는 보지 않는다** — 타입 에러가 있어도 dev 서버가 라우트를 200으로 응답하므로 게이트가 통과할 수 있다. 첫 시험에서 실제로 그랬다(`Quote`에 없는 필드를 반환하는데 라우트는 200이었다).

```bash
cd app && npx tsc --noEmit
```

> ESLint는 **더 이상 여기서 돌리지 않는다** — 2026-08-09부터 게이트의 `lint` 관문이 같은 flat config로 스코프 파일을 검사한다(error·warning 모두 하드페일).

그다음 게이트:

```bash
node scripts/gate.mjs --target web --routes /commissioned/<slug>
```

자율 루프와 **같은 게이트**를 쓴다(정적·sweep·a11y·perf). 실패하면 `verdict.violations`를 designer에게 넘겨 **1회 수정** 후 재실행.

- dev 서버 3100이 필요하다 — 없으면 `cd app && npm run dev` 백그라운드 기동
- a11y < 95는 하드페일. 사용자 요구와 무관하게 통과해야 한다
- perf는 기록만

## 5. 인수

- 스크린샷: `node scripts/capture-shots.mjs --route /commissioned/<slug> --name <slug> --out vault/40-commissions/<slug>/shots` — 4폭 × 4 스크롤 지점. **빈 프레임 판정이 붙어 있으므로 blank가 나오면 인수 전에 고친다**. `/tmp`로 찍지 마라 — 재부팅하면 사라져 인수 근거가 휘발한다
- 게이트 결과를 그대로 보인다
- **designer가 정한 것을 5분류로 보인다.** 평평한 목록으로 내면 사용자가 전부 읽어야 하고, 고칠 확률이 높은 항목이 묻힌다 — 2026-08-08 첫 시험에서 **34항목이 평평하게** 왔고 회사명이 그 안에 섞여 있었다. **고칠 확률 순으로** 묶는다:

  | | 분류 | 사용자에게 |
  |---|---|---|
  | ① | **이름** — 회사·플랜·제품·모델 | **고칠 것 있나 묻는다** |
  | ② | **숫자·조건** — 가격·기간·수수료·기본값·범위 | **고칠 것 있나 묻는다** |
  | ③ | **카피** — 헤드라인·소개문·법적 문구 | **고칠 것 있나 묻는다** |
  | ④ | 구조·미학 — 레이아웃·테마·액센트·활자 | 읽어보라고만 한다 |
  | ⑤ | 접근성·기술 — 라이브 리전·마크업 판단·파일 분할 | 읽어보라고만 한다 |

  ④⑤는 designer 영역이라 **승인을 구하지 않는다.** 다만 **감추지도 않는다** — 사용자가 짚으면 고친다.
- **계약과 다르게 만든 것이 있으면 별도로 짚는다.** 첫 시험에서 "한 화면 완결"이 390px에서 세로 스크롤로 완화됐고, 그 이탈을 명시해 사용자가 인수 여부를 판단했다. 묻히면 계약이 있으나 마나가 된다
- 수정 요구를 받으면 §3~§5를 반복한다. **반복 횟수 제한 없음** — 자율 루프의 1-fix 제한은 판정 공정성 때문이고 여기는 판정이 없다

## 6. 마무리

- **인수 기록을 남긴다** — `vault/40-commissions/<slug>/RECORD.md` + `shots/`. 산출물만 커밋하면 **왜 그렇게 만들었는지가 대화에만 남고 사라진다.** 담을 것: 인터뷰 결과 · 타입 계약 · 게이트 결과 · **designer가 정한 것(§5의 5분류 그대로)** · 계약 이탈과 인수 판단.
  자율 루프는 `vault/20-generations/<run>/`에 DECISION·SCORES·shots를 남겨 주간 반증이 링크로 건다. 주문 제작은 판정을 안 거쳐 걸 PR이 없지만, **나중에 "그때 그 페이지 어땠지"를 볼 사람은 사용자 본인**이라 오히려 더 필요하다.
  `wiki-lint`는 `40-commissions/`를 20-generations와 같은 **경로 기반 키**로 다룬다(주문마다 `RECORD.md`가 겹치므로). index 등재는 요구하지 않는다.
- 기본은 **미등재**. `works.ts`를 건드리지 않는다
- **한국어·i18n으로 만든 페이지를 갤러리에 등재하려 하면 그때 [[page-brief-core]] §1이 발동한다.** 카탈로그에 들어가는 순간 "글로벌 벤치마크 정합"이 적용되기 때문이다. 등재 시점에 **충돌을 알리고** 사용자가 정하게 한다 — 영문화하거나, 등재를 포기하거나. 조용히 등재하지 마라
- 사용자가 갤러리 등재를 원하면: `works.ts`에 entry 추가 + `category` 부여 + `desc:{en,ko}` + `LAST_UPDATED` 갱신 + `cd app && npx eslint src --max-warnings=0` 확인. **이때부터 그 작품은 다양성 집계와 미채움 큐에 영향을 준다**는 것을 사용자에게 알린다
- 커밋은 사용자 지시가 있을 때만. `main` 직접 커밋 금지(레포 규약)

## 금지

- **정본(`vault/00-principles/*`) 수정 금지.** 이 스킬의 산출물은 판정을 거치지 않았다 — delta도, 프로파일도, 질문 큐도 만들지 않는다. 인터뷰에서 정본의 구멍을 발견했다면 **사용자에게 말하고 별건으로 남긴다**
- **하드게이트 우회 금지.** 사용자가 요구해도 결정론·a11y·이모지·이미지 규칙은 그대로다
- **인터뷰 생략 금지.** "적당히 알아서" 요청이라도 §1-1(타입) · §1-2의 **회사명 · 핵심 증명 · 도메인 실체 · 페이지 언어** 다섯은 반드시 확정한다. 앞 넷이 비면 결과물은 카탈로그에 이미 있는 것과 구분되지 않는다. **언어는 성격이 다르다** — 묻지 않으면 정본 §1의 영문 전용이 **조용히 적용**되고, 사용자는 다 만들어진 뒤에야 자기 페이지가 영어라는 걸 안다
- **정본 용어로 묻지 않는다.** "핵심 증명"·"아키타입"·"핵심 판정 기준"은 이 레포의 어휘다. 사용자에게는 §1-2 표의 평이한 말로 묻고, 변환은 스킬이 한다. 사용자가 언어화할 수 없는 항목(구조 기준·인접 타입 차이)은 **묻지 말고 도출해 제안**한다
- **사업 규칙을 캐묻지 않는다.** 할부 조건·수수료율·과금 단위 같은 것. 페이지 요청을 사업 설계 상담으로 바꾸면 사용자는 "알아서 해줘"로 도망가고, 그게 인터뷰를 안 한 것보다 나쁘다
- **빈칸을 designer에게 넘기지 않는다.** 모르는 항목은 후보를 제시해 사용자가 고르게 한다
