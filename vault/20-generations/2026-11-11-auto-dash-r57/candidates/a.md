Ridgehaul — an IT/customer-support ops console whose centerpiece is a per-team ticket resolution-time box plot (median/Q1/Q3/min/max, always-visible) paired with a live ticket activity feed below it.

## 브리프에 없던 것

1. ① 팀 이름과 개수, 실제 티켓 데이터 값
   ② 5개 팀(Network Ops / App Platform / Billing / Security / Field Ops), 7일 기준 팀당 8건, 30일 기준 팀당 12건의 해결 시간(시간 단위) 배열을 직접 작성
   ③ 임의 선택. 팀 이름은 일반적인 IT 운영/고객지원 조직 구조(네트워크, 앱, 결제, 보안, 현장)를 참고했고, 글자 수를 11자 이하로 제한한 것은 테이블 "Team" 컬럼(15% 폭)에서 줄임표 없이 안전하게 들어가게 하려는 레이아웃 제약에서 역산한 결정.

2. ① SLA 목표 시간(몇 시간 이내 해결이 "준수"인지)
   ② 8시간으로 고정
   ③ 임의 선택이지만 업무시간 기준 "하루 안에 해결" 이라는 일반적인 B2B 지원 SLA 관행을 참고.

3. ① 색상 팔레트의 정확한 Tailwind 토큰 매핑 (브리프는 "~#0F172A/#22C55E 근처"라고만 지정)
   ② bg는 slate-950/slate-900, accent는 green-400/500, 상태뱃지는 sky(Open)/amber(In progress 및 High)/red(Escalated 및 Critical)/slate(Low) 4색 체계로 고정
   ③ Tailwind 기본 슬레이트 팔레트가 브리프가 준 헥스값과 거의 1:1로 대응되는 것을 확인하고 임의로 매핑(일반 관행: dark fintech/dev-tool 대시보드가 slate+accent 하나를 쓰는 패턴).

4. ① 아바타용 Unsplash 고정 사진 ID 5개 (사이드바 유저 1 + 담당자 4)
   ② 특정 photo-<id> 5개를 고정 지정 (파일 참조)
   ③ 임의 선택이지만 "전문적인 인물 사진"이라는 피사체 일관성 기준으로 고름. 랜덤/시드 피커 금지 규칙을 지키기 위해 완전히 하드코딩.

5. ① 커맨드 팔레트가 실제로 무엇을 하는지(브리프는 "필터/내비게이션 같은 real한 동작"만 요구)
   ② 팀 핀 고정 / 기간(7d·30d) 전환 / 티켓 테이블·피드로 스크롤 이동, 3가지 그룹의 액션으로 구성
   ③ 임의 선택. 이미 페이지에 존재하는 다른 상호작용(피자 고정, 기간 토글, 스크롤 대상)을 팔레트에서도 접근 가능하게 만들어 "진짜 동작"이라는 요건을 자연스럽게 만족시키는 방향으로 설계.

6. ① 선택 팬아웃의 정확한 분리 방식(브리프는 "두 개의 독립적으로 스코프된 선택"만 요구, 구현 디테일은 안 줌)
   ② 박스플롯 행의 onClick(핀, 영구 상태) 과 onMouseEnter/onFocus(툴팁, 휘발성 상태)를 같은 DOM 엘리먼트에 두되 서로 다른 state 변수(pinnedTeam vs hoveredTeam)로 완전히 분리
   ③ 브리프 수정 사항의 "별도 엘리먼트일 필요는 없다"는 암묵적 허용 범위 안에서, 추가 포커스 가능 엘리먼트를 만들지 않아 접근성 복잡도를 줄이는 쪽을 택한 임의 선택.

7. ① 피드 이벤트 필터 옵션의 구체적 분류(5가지 타입 중 몇 개를 세그먼트 버튼으로 노출할지)
   ② All / Created / Escalated / Resolved 4개만 버튼으로 노출(assigned, reopened는 "All"에서만 보임)
   ③ 임의 선택. 세그먼트 컨트롤이 5~6개 옵션으로 늘어나면 좁은 카드 폭에서 줄바꿈이 잦아질 것을 우려해 운영상 가장 자주 찾아볼 법한 4종으로 제한.

8. ① 정렬 가능한 컬럼을 Age/Priority 둘로 제한한 이유(브리프는 "aria-sort 가진 정렬 가능 테이블"만 요구, 몇 개 컬럼인지는 안 정함)
   ② Age(기본, 내림차순)와 Priority만 정렬 가능, Team/Status/Assignee/Ticket은 정렬 불가
   ③ 임의 선택. 운영자가 실제로 "가장 오래된 것부터" "가장 심각한 것부터" 보는 두 가지 축만 현실적으로 유의미하다고 판단.

9. ① 다크 테마에서 보조/캡션 텍스트의 정확한 하한선 토큰(브리프는 "zinc-400 아래로 가지 말 것"이라 했지만 전체 팔레트는 slate 기반)
   ② slate-400을 zinc-400과 동급의 최저 허용 밝기로 간주하고 그 아래(slate-500/600)는 텍스트에 전혀 쓰지 않음(아이콘·장식 요소에만 예외적으로 사용)
   ③ 두 색의 상대 휘도가 거의 동일하다는 계산 근거(slate-400 ≈ #94A3B8, zinc-400 ≈ #A1A1AA, 대비비 둘 다 배경 대비 ~7:1 이상)에 기반한 임의 결정.

10. ① "경쾌한 탑바 높이 44px" 규칙을 사이드바 워크스페이스 전환 버튼이나 내비게이션 행에도 적용할지
    ② 탑바의 모든 인터랙티브 컨트롤에만 h-[44px]를 명시적으로 고정하고, 사이드바 내비 행은 타겟사이즈 하한(24px)만 지키며 자연스러운 패딩(36px 안팎)으로 둠
    ③ 브리프 문구가 "Header control height 44px"로 헤더에 한정돼 있다고 읽고, 사이드바는 다른 리듬(4/8px spacing)을 따르도록 임의 해석.
