# Candidate b — Tax Export Tagging

## 1. Concept summary
A peer-to-peer marketplace screen where the user tags each completed sale or purchase with a direction-specific tax category (sales get "Taxable Income" / "Personal Sale"; purchases get "Business Expense" / "Personal Purchase") and locks a tagged batch into a numbered export (`EXP-###`) — rows already locked into a prior export can never be re-tagged.

## 2. Render-check string
`Tax Export Tagging` — literal heading text (`accessibilityRole="header"`) rendered unconditionally at the top of the screen in `src/evolve/r28/b/TaxExportTaggingScreen.tsx`.

## 3. Rules applied
- **Band form — selection-driven contextual bar** (GENERATION.md §3, third form): the bar is `{pickedCount > 0 ? <View style={styles.bar}>…</View> : null}`, derived directly from `pickedIds.size`, never a separate boolean. No undo toast exists anywhere on the screen, so the bar and a toast never compete.
- **Live region doctrine** (§3/§4): exactly one live region on the screen — a `View` with `accessibilityLiveRegion="polite"` wrapping a single `Text` with `accessibilityRole="alert"`. That one text node carries **both** the selection count and the computed net dollar total (and, during the lock-confirm step, the confirmation sentence), so the count and the running total never compete as two separate regions.
- **Real derived state, not just the bar mechanism:**
  1. *Business-rule gate*: rows with `locked: true` (already folded into a prior finalized export, e.g. `EXP-001`) have `disabled={true}` on their row `Pressable` and `accessibilityState={{ disabled: true }}` — they are structurally unselectable, not just dimmed.
  2. *Incompatible-category gate*: sale and purchase transactions use deliberately disjoint tag vocabularies (`commonTagOptions` in `data.ts` intersects the allowed tags across every direction in the current selection). Selecting a mix of sales and purchases collapses the quick-tag chip row into an explanatory message ("Selection mixes sales and purchases — tag each group separately") instead of showing chips.
  3. *Real computed running total*: `netPickedCents` is a signed sum (`signedAmountCents`: sales add, purchases subtract) over the currently selected rows, recomputed from state every render — not a static count.
  4. *Conditional primary-action gating with a distinct message*: the "Lock … for Export" button is disabled, with accessibility label and visible copy both switching to "Tag all selected to continue", until every selected row already carries a tag (independent of the direction-mix gate above — a selection can be mixed-direction and still lockable if each row was already individually tagged).
- **Destructive-confirm idiom** (§3/§4): locking a batch is irreversible (locked rows can never be re-tagged), so pressing the primary action does not open a native `Alert` — it flips the bar itself into a `Cancel` / `Confirm Lock` two-button row inside the same already-live-region-wrapped container, and the confirmation sentence is read by the same single live region.
- **Accessibility leaf-labeling**: no wrapper `View`/`Pressable` has `accessible={true}`; each row is a single `Pressable` (no nested interactive children) carrying one composed `accessibilityLabel` on itself (direction, counterparty, amount, tag state, lock state) — avoids the "opaque focus subtree" pitfall because there is nothing nested to swallow.
- **No false promises**: no `accessibilityHint` anywhere claims a side effect; the "Lock" action's label states exactly what pressing it does (opens the confirm step), and `confirmLock` actually performs the state change (`locked: true`, `exportBatchId` set, selection cleared) it describes.
- **Determinism**: no `Math.random`, `Date.now`, or bare `new Date()`. All transaction data in `data.ts` is fixed literals; `nextExportBatchId` deterministically parses the highest existing `EXP-###` and increments it.
- **Tokens / DNA**: all colors from `tokens.color.*`, spacing from `tokens.space(n)`, radius from `tokens.radius.*` — no hardcoded hex. `accentBg` used only for the selected-row background (its documented purpose), never as a flood. Tag badges reuse the existing semantic `success`/`warning` token pairs (expense ≈ success-toned, taxable income ≈ warning-toned) rather than inventing new hex. English-only copy, no emoji (a plain `✓` check-mark glyph is the only non-text glyph, used as a text character, not a pictograph). Currency is plain Latin `$1,234.56` formatting (sidesteps the ₩-glyph issue entirely per §1). `View`/`Text`/`Pressable`/`FlatList`/`SafeAreaView`/`StyleSheet` only, `FlatList` (not `.map()`) renders the transaction list, every `Pressable` has a visible pressed-state style and a ≥44×44pt target.

## Brief gaps
- **Tag taxonomy and labels**: the brief said to invent specific categories; I chose direction-scoped pairs (`Taxable Income`/`Personal Sale` for sales, `Business Expense`/`Personal Purchase` for purchases) rather than one flat shared tag set, specifically so the "incompatible categories" mechanic the brief asked for would be a real, non-cosmetic business rule (the sets are disjoint by construction) rather than a UI-only restriction layered on top of a shared vocabulary.
- **What "locks" a transaction**: the brief mentioned locked/finalized rows as an example gate but didn't specify the mechanism. I modeled it as a prior export batch id (`EXP-001`) already present on 2 of 12 seed rows, with `nextExportBatchId` deterministically computing the next batch number from existing data — this made the gate a genuine, inspectable piece of state rather than a random/flag-only disable.
- **Running-total semantics**: the brief asked for "a real computed sum of the selected transactions' amounts." I made it a *signed net* (sales positive, purchases negative) rather than a raw absolute total, since that is what's actually meaningful for a tax context (net taxable position), and it gives the live-region text a value that visibly changes sign/magnitude as selection changes — a stronger demonstration of real derived state than an unsigned sum would have been.
- **Relationship between bulk tag-chips and the lock gate**: not specified by the brief. I decided the lock button's eligibility ("every selected row already has a tag") is independent of the direction-mix chip gate — a user can select a mixed-direction batch where every row was already individually tagged earlier and still lock it; they just can't *bulk-apply* one tag across the mix via the chips. This kept the two business rules (bulk-tag compatibility vs. lock eligibility) distinct and both real, instead of collapsing them into one blanket "mixed selection = fully blocked" rule.
- **No separate "generate export file" screen/state**: the brief's flow was "tag → generate export." I treated "lock into export batch" as the terminal, irreversible action for this screen (consistent with the destructive-confirm idiom) rather than adding a further fake "export generated/downloaded" confirmation screen, to avoid claiming a system-level side effect (file generation, download, email) that no code on this screen actually represents.
