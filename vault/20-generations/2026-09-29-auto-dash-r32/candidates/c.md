# auto-dash-r32/c — Loopback

**한 줄 컨셉**: repick 반품/환불 운영팀을 위한 프로세스 맵 콘솔 — 9개 스테이지·10개 전이(루프백 1개 포함)를 노드-엣지 그래프로 그리고, 병목(에스컬레이션 리뷰)을 아이콘+라벨로 명시하며, 실제 상위 4개 변이 경로를 하단 필름스트립으로 보여준다.

- 아키타입: 도미넌트 그래프 캔버스 + 하단 필름스트립(카탈로그 최초의 노드-엣지 프로세스맵+병목표시 — Sankey `d37`/퍼널 `d36`과 달리 실제 분기·루프백 구조를 가짐, 열거된 마스터-디테일/3페인/캘린더-보드 아키타입 밖의 매크로 셸).
- 테마: light(zinc-50/white + hairline) · 액센트: amber · 디스플레이 활자: `--font-display-mono`(h1 한 곳에만) · 렌더 폰트 웨이트 3종(400 기본/500 medium/600 semibold, bold 계열 미사용, `<strong>`/`<b>` 미사용, th/dt/caption 전부 명시적 클래스)
- 셸: 좌측 사이드바(브랜드 록업+워크스페이스 스위처+섹션 내비+유저 메뉴) + 상단바(⌘K 검색 버튼·"New return case" primary·알림·아바타 메뉴, 전부 h-11=44px) — 모바일 드로어.
- 인터랙션 5종: ① 노드/엣지 hover 툴팁(마우스+키보드 Tab, 로컬 `hover` state) ② 스테이지 테이블 실제 정렬(aria-sort, 그래프의 스크린리더 대체 표이자 sortable table 겸용) ③ 30일/90일 기간 토글(그래프 볼륨·필름스트립·상단 통계 전부 재계산) ④ 핀→디테일 패널 동기화(노드 또는 필름스트립 경로 클릭 → `Selection` 유니온이 pin되어 인바운드/아웃바운드/체류시간/공유율 재계산) ⑤ ⌘K 커맨드팔레트(스테이지·경로 검색→핀).
- 셀렉션 분리: `selection: {kind:'stage',id}|{kind:'path',id}|null` 하나의 영속 pin — 노드 클릭과 필름스트립 클릭이 같은 유니온을 채우지만 3곳 이상에 동일 이름 `selectedId` prop으로 그대로 꿰인 게 아니라 각 소비자(그래프/디테일패널/테이블)가 다른 필드(`nodeIds`/`edgeIds` 하이라이트, dwell/pooled 통계, 행 강조)로 해석한다. hover는 그래프 컴포넌트 내부의 완전 로컬 state로 pin을 절대 쓰지 않으며, 하이라이트 계산 시 `isHoverOnly = hover?.id===x.id && !emphasized`로 이미 pinned인 대상엔 hover 전용 링을 겹쳐 그리지 않는다(코드 주석으로 명시). 독립 두 번째 축은 필름스트립의 결과-필터(전체/환불/반품/에스컬레이션 경유) — pin을 전혀 건드리지 않고 필름스트립에 보이는 행만 바꾼다.
- 액센트 대비(WCAG 상대휘도 공식 직접 계산, Node로 실행 검증, 미추정):
  - amber-600(#D97706) on white = **3.19:1** (아이콘·테두리·포커스링 전용 — UI 컴포넌트 3:1 기준만 충족, 본문 텍스트에는 안 씀)
  - amber-700(#B45309) on white = **5.02:1** (작은 액센트 텍스트는 전부 700 사용)
  - **흰 글자 vs amber-500(#F59E0B) 채움 = 2.15:1(탈락)**, **zinc-900(#18181B) vs amber-500 = 8.25:1(통과)** → 채움 배지·하이라이트에는 흰 글자가 아니라 진한 잉크(zinc-900)가 승리, 코드 전체에서 amber 채움 위엔 항상 `text-zinc-900` 사용
  - zinc-900 on amber-100(#FEF3C7, 병목 배지 배경) = **15.91:1**
  - zinc-500(#71717A) on white = **4.83:1**, on zinc-50(#FAFAFA) = **4.63:1** (본문 뮤트 텍스트 최소 기준), zinc-600 on zinc-100(#F4F4F5) = **7.03:1** (틴트 표면 위 라벨)

## 브리프에 없던 것

1. **뷰박스 크기를 두 번 다시 설계했다.** 처음엔 그래프를 1700×570 뷰박스로 넉넉하게 그렸는데, 사이드바(256px)+디테일 패널(고정 352px 사이드레일)까지 뺀 실제 콘텐츠 폭을 1280/1366/1440/1600/1920 각 너비에서 계산해보니(스케일=콘텐츠폭/1700) 1280에서 스케일이 0.435까지 떨어져 노드 라벨(12.5px)이 실사용 픽셀로 5.4px밖에 안 나온다는 걸 발견했다. 디테일 패널을 그래프 옆 고정폭 레일이 아니라 그래프 **아래** 전체폭 카드로 내리고(브리프가 "side panel or a panel below the graph" 둘 다 허용한다고 명시했으므로), 뷰박스도 1360×480으로 축소해 1280~1920 구간 스케일을 0.68~1.15로 좁혔다. 그래도 1280에서 12.5px 라벨은 8.5px밖에 안 나와서 노드 라벨(12.5→15px)·서브텍스트(11→13px)·엣지 볼륨 라벨(11→13px)·병목 배지(9.5→11px)를 전부 한 단계씩 키웠다 — 실사용 px가 아니라 뷰박스 좌표계 안에서의 크기라는 걸 계속 헷갈리기 쉬워서, 스케일 계산을 직접 손으로 다섯 breakpoint에 대해 해봤다.
2. **hover 툴팁이 그래프의 가로 스크롤 컨테이너 안에 있으면 잘릴 수 있다는 걸 뒤늦게 알아챘다.** 처음엔 `overflow-x-auto` div 안에 SVG와 툴팁을 같이 뒀는데, `overflow-x:auto`만 줘도 CSS 계산 규칙상 `overflow-y`도 `auto`로 승격되어(둘 중 하나가 visible이 아니면 나머지도 visible이 아니게 됨) 위로 뜨는 툴팁이 모바일 폭에서 세로로 잘릴 위험이 있었다. 툴팁을 스크롤 컨테이너의 형제로, 스크롤되지 않는 바깥 `relative` div의 직계 자식으로 옮기고 좌표 기준(`containerRef`)도 그 바깥 div로 바꿨다 — 이 저장소의 "가로 스크롤 컨테이너 안 sr-only" 함정과는 다른 케이스지만 같은 메커니즘(overflow 승격)이라 미리 피했다.
3. **엣지의 기본(비선택) 회색이 실제로는 대비 기준 미달이었다.** 그래프 엣지를 처음엔 `stroke-zinc-400`(흰 배경 대비 2.56:1)으로 그렸는데, 이건 장식이 아니라 "이 전이가 존재한다"는 걸 전달하는 그래픽 객체라서 1.4.11의 3:1 기준을 적용해야 한다고 판단했다. 화살표 마커·기본 엣지 색을 `zinc-500`(4.83:1)으로, hover 시 `zinc-600`으로 올렸다. 같은 논리로 hover-only 아이콘 전용 버튼(커맨드팔레트 닫기, 디테일 패널 핀 해제)도 `zinc-400→zinc-500`으로 일괄 상향했다 — 다만 텍스트 라벨과 나란히 있어 장식으로 판단한 체브론/화살표류(사이드바 워크스페이스 스위처, 정렬 미활성 아이콘 등)는 zinc-300/400을 그대로 뒀다.
4. **필터 세그먼트 라벨이 390px에서 넘칠 뻔했다.** 필름스트립 결과-필터에 "Via escalation"까지 4개 라벨을 한 줄에 넣었더니 대략 320px가 필요한데 390px 모바일에서 카드 패딩을 빼면 가용 폭이 326px밖에 안 돼 여유가 거의 없었다. 라벨을 "Escalated"로 줄이고, `SegmentedControl` 자체에 `flex-wrap`+`whitespace-nowrap`을 추가해 혹시 넘치면 버튼 단위로 줄바꿈되고 글자가 중간에 깨지진 않도록 방어적으로 고쳤다(기간 토글에도 동일 컴포넌트라 같이 적용됨).

## 불확실한 부분
- 그래프 SVG 안 `<g tabIndex={0} role="img">` 엣지에 대해 `outline`(FOCUS_RING) 포커스 링이 브라우저에서 정말 페인트되는지는 코드 리뷰로만 확인했다(gate/브라우저 실행은 지시받지 않아 안 함) — 혹시 렌더링이 약하면 `group-focus-visible:stroke-amber-700`로 실제 선 색이 바뀌는 폴백을 같이 넣어뒀지만, SVG `<g>` 자체의 아웃라인 렌더링은 브라우저마다 미묘하게 다를 수 있다.
- "pooled"(현재 해당 스테이지에 머물러 있는 케이스 수 = inbound − outbound)는 실제 시뮬레이션이 아니라 손으로 고른 엣지 볼륨의 산술 결과다 — 의도적으로 escalated(18건, 9.6%)와 approved(50건)에 잔류가 남도록 숫자를 짰지만, 90일 창에서 escalated 잔류 비율(60/530=11.3%)이 30일보다 약간 더 나쁘게 나오는 게 "추세 악화"로 읽힐 수 있어 이게 의도한 서사인지 재고할 여지가 있다.
