# c — Support Center (FAQ search + accordion + always-on escalate)

**한 줄**: 검색으로 필터링되는 카테고리별 FAQ 아코디언 + 언제나 눌러도 되는 상담원 연결 액션바 — 카탈로그에 없던 순수 정보/탐색형 고객지원 화면.

- 배정 화면유형: **Support Center** — FAQ 검색/브라우즈 + 카테고리 아코디언 + escalate. 기존 15개 화면 어디에도 없던 유형.
- 매크로 골격: 상단 검색 입력(고정 크롬 최소) + `SectionList` 카테고리 아코디언(전체 스크롤) + 리스트 끝 인라인 CTA 카드 + 하단 얇은 상시 액션바(상태기계 아님, 항상 같은 단일 액션).
- 이 화면은 **막힌 지점이 없는 read-only 탐색 화면**이다 — 그래서 하단 밴드를 진행 가능/불가를 판정하는 상태기계로 만들지 않았다. "Start a chat with an agent" 버튼은 언제 눌러도 유효하고, 조건부로 비활성화되는 경우는 오직 연결 중(`connecting`) 한 순간뿐이며 그마저도 즉시 가시적 결과(연결 중 → 연결됨)로 이어진다.
- escalate 경로는 두 곳에 반복 노출했다: (1) 리스트를 끝까지 본 사용자를 위한 인라인 CTA 카드(`ListFooterComponent`), (2) 스크롤 위치와 무관하게 항상 보이는 하단 얇은 액션바. 검색 결과가 0건일 때도 같은 액션을 빈 상태 카드 안에 다시 노출해, "막혔을 때 다음 행동"을 항상 제시한다.
- 터미널 액션(상담원 연결)은 무음 no-op이 아니다 — `idle → connecting → connected` 결정론적 로컬 상태 전이(고정 지연 900ms)로 가시적 결과를 낸다. 전이 문장에는 `accessibilityRole="alert"`, 그 문장을 담은 컨테이너에는 `accessibilityLiveRegion="polite"`를 걸어 스크린리더에서도 무음 DOM 교체가 되지 않게 했다. 검색 결과 카운터에도 별도로 `polite`를 걸었지만, 두 라이브 리전은 서로 다른 조작(검색 vs 에스컬레이트)에서만 발화하므로 한 조작에 두 곳이 동시에 낭독되는 일은 없다.
- 실제 상담 대화 스레드 UI는 만들지 않았다 — "Start a chat" 버튼이 상담원 연결을 확인해 주는 지점까지만 다루고, 메시지 스레드 자체는 이 화면의 범위 밖으로 남겨뒀다(offer-thread와 형태 충돌 회피).

## 브리프에 없던 것

1. **최상위 래퍼를 `SafeAreaView`로 할지 `View`로 할지**
   ① 무엇을 정해야 했나: GENERATION.md §1은 "최상위 래퍼 → SafeAreaView"라 하지만, 레포 관례 노트는 "App.tsx가 이미 SafeAreaView로 감싸므로 화면은 View 바로 아래 스크롤 컨테이너를 두면 된다"고 명시한다. 두 지시가 서로 다른 층위(일반 RN 관용구 vs 이 레포의 실제 합성 구조)에서 충돌했다.
   ② 무엇으로 정했나: `native/App.tsx`를 직접 읽어 실제로 `<SafeAreaView><Screen /></SafeAreaView>` 구조임을 확인하고, 화면 컴포넌트 루트는 `View`로 뒀다(SafeAreaView 이중 중첩 방지).
   ③ 왜 그렇게 정했나: 일반 규칙보다 이 레포에 대한 구체적이고 명시적인 관례 문장이 우선한다고 판단했다 — 실제 `App.tsx` 소스로 교차검증했으므로 임의가 아니라 확인된 사실에 근거한 선택이다.

2. **검색 결과 하이라이트/자동펼침 여부**
   ① 무엇을 정해야 했나: 검색어와 일치하는 FAQ 항목을 아코디언에서 자동으로 펼쳐 보여줄지, 아니면 계속 접힌 채로 두고 사용자가 직접 펼치게 할지 브리프에 지정이 없었다.
   ② 무엇으로 정했나: 접힌 채로 두고, 카드 자체를 필터링만 했다(펼침 상태는 별도 사용자 조작으로만 바뀜).
   ③ 왜 그렇게 정했나: 자동펼침을 검색 상태 변경과 동시에 발생시키면 접힘/펼침이라는 a11y 상태(`accessibilityState.expanded`)가 사용자 의도 없이 프로그램적으로 바뀌어, "한 조작에 한 라이브 리전만" 원칙과 충돌할 여지가 있다고 판단해 보수적으로 분리했다.

3. **에스컬레이트를 두 번 이상 반복 노출할지, 한 곳에만 둘지**
   ① 무엇을 정해야 했나: 매크로 골격 지시는 "인라인 반복 배치 OR 상시 액션바" 중 하나를 고르라고 했지 둘 다 하라고 하지 않았다.
   ② 무엇으로 정했나: 하단 상시 액션바를 기본으로 하되, 리스트 맨 아래와 빈 검색결과 상태에도 같은 액션을 인라인으로 추가 노출했다(총 3곳).
   ③ 왜 그렇게 정했나: "escalate 액션만큼은 스크롤 끝까지 가지 않아도 찾을 수 있어야 한다"는 지시는 상시 액션바만으로 이미 충족되지만, 빈 상태 규칙("빈 상태엔 안내+액션")을 별도로 만족시키려면 검색 결과 0건 카드 안에도 같은 동작의 버튼이 있어야 한다고 판단했다 — 두 요구사항이 겹치는 지점이라 배타적 선택이 아니라 합집합으로 처리했다.

4. **연결 완료 후 상태를 되돌릴지(재시도 가능하게) 계속 고정할지**
   ① 무엇을 정해야 했나: `connected` 상태 이후 시간이 지나면 `idle`로 리셋해 재시도 가능하게 할지, 그대로 고정할지 브리프에 지정이 없었다.
   ② 무엇으로 정했나: `connected`에서 되돌리지 않고 고정했다(버튼 자리를 확인 문구로 계속 대체).
   ③ 왜 그렇게 정했나: 임의 타임아웃으로 상태를 되돌리면 그 타이밍 자체가 결정론 원칙과 무관하게 사용자 경험상 예측 불가능해지고, "이미 상담이 연결됐다"는 사실이 스크롤/재방문 없이도 화면에 계속 남아있는 편이 실제 상담원 연결이라는 후속 화면(스코프 밖)으로 넘어가기 전 상태를 정직하게 보여준다고 판단했다.
