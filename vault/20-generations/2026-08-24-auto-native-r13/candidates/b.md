# auto-native-r13 · candidate b — Seller Onboarding Setup

한 줄 컨셉: 첫 리스팅 전에 완료해야 하는 판매자 스토어 설정 마법사 — 프로필→카테고리
선호→배송 설정→정산 계좌→검토의 5단계를 하나의 FlatList로 세로 나열하고, 진행 중인
단계만 폼으로 펼치고 완료 단계는 요약 카드로 접히며 미도달 단계는 잠긴 미리보기로
남는다. 하단 상태기계 밴드가 항상 "왜 못 넘어가는지"를 문장으로 말하고, 눌리면
막힌 경우 그 단계로 스크롤+포커스 이동, 준비된 경우 다음 단계로 진행 또는(검토
단계에서) 스토어를 실제로 활성화한다(로딩→성공 전환 포함).

## 브리프에 없던 것

① 스토어명·바이오 최소 길이 기준
② 스토어명 2자 이상, 바이오 20자 이상 (`data.ts`의 `STORE_NAME_MIN_LENGTH` / `BIO_MIN_LENGTH`)
③ 브리프에 수치 지정 없음 — "빈 문자열도 유효"로 두면 상태기계 밴드가 항상 ready 상태가
   되어 이 화면의 핵심 기믹(막힘→해소)을 시연할 수 없다. 임의로 낮은 문턱값을 정해 실제
   입력 없이는 통과 못 하되 사용자를 과도하게 막지 않는 선에서 정함.

① 카테고리 선호 몇 개까지 선택 가능한지
② 최대 3개 (`MAX_CATEGORY_SELECTION`), 최소 1개 필수
③ 브리프는 "카테고리 선호"만 언급하고 개수 제한 없음 — 무제한 선택은 "선호"의 의미를
   희석시킨다고 판단해 임의로 상한을 둠. 상한 도달 시 추가 탭은 조용히 무시(별도 에러
   문구 없이 토글 자체가 막힘 — 개수 표시로 이유는 항상 보임).

① 배송 설정 단계에 무엇을 물을지 (배송 방법만? 처리 기간도?)
② 배송 방법(밋업/택배/둘 다) + 평균 처리 기간(1-2일/3-5일/5-7일), 둘 다 필수
③ 브리프가 "배송 설정"이라고만 함 — 방법 하나만 고르면 실제 판매자 설정치고 지나치게
   빈약하다 판단, 다른 커머스 앱의 표준 판매자 설정 관행(처리 기간 SLA 명시)을 참고해
   두 번째 하위 필드를 임의로 추가. 상태기계 밴드 메시지도 두 하위 필드를 순서대로
   가리키도록 분기시킴.

① 정산 계좌 연결을 실제 은행 연동 폼으로 만들지, 목업 버튼으로 만들지
② 목업 "Connect payout account" 버튼 — 누르면 connecting(로딩, 고정 600ms)→connected로
   전환, 은행명/계좌 뒤 4자리 마스킹 표시. 실제 계좌번호 입력 폼은 없음.
③ 계좌번호·인증번호 등 실제 금융 입력 폼은 이 화면의 스코프(스토어 설정 마법사 UI)를
   벗어나 결제 연동 API 화면이 될 위험이 있고, 결정론 규칙상 임의의 은행 목록을 실제
   입력받는 것도 의미가 없다고 판단 — "연결됨/안 됨" 상태 전이 자체를 보여주는 것이
   이 화면 몫이라 임의로 범위를 좁힘.

① 완료된 단계를 "Edit"으로 되돌아갔을 때 그 뒤 단계들이 어떻게 되는지
② 되돌아간 지점 이후의 모든 단계가 다시 "잠김" 상태로 돌아간다(입력값 자체는 보존).
   즉 `currentStepIndex`를 그 단계로 되돌리는 것만으로 이후 단계는 인덱스 비교로 자동
   잠김 처리 — 재확인 없이 앞으로 건너뛸 수 없다.
③ 브리프의 "진짜 순차적 블로킹 워크플로" 강조를 문자 그대로 해석 — 뒤 단계를 그대로
   "완료"로 남겨두면 되돌아가기가 사실상 무의미한 장식이 되어 상태기계 원칙(다음
   미완료 지점으로 이동)이 깨진다고 판단해 임의로 엄격한 쪽을 택함.

① 최종 액션("Activate store")이 실패하는 경로를 만들지
② 만들지 않음 — 로딩(900ms 고정)→성공만 존재. 실패/에러 상태는 UI 코드 상 없음.
③ 결정론 규칙(Math.random/Date.now 금지)상 "가끔 실패"를 재현 가능한 방식으로 만들
   근거가 없고, 임의로 "항상 실패"를 고정하면 터미널 액션이 영구 no-op이 되어 §DNA
   규칙을 정면으로 어긴다. 따라서 로딩→성공 전환만으로 "가시적 결과" 요구를 충족시키는
   쪽을 택하고, 에러 분기는 다루지 않음(임의 결정, 향후 재현 실험 대상으로 남김).

① 라이브 리전을 밴드 문장 외에 필드 단위 블러 검증 에러에도 붙일지
② 붙이지 않음 — 밴드 컨테이너 하나에만 `accessibilityLiveRegion="polite"` + 밴드 문장에만
   `accessibilityRole="alert"`. 인풋 블러 시 나타나는 "Required — …" 텍스트는 일반 Text.
③ 정본이 "라이브 리전 두 개 이상 두지 마라"를 명시 — 필드 에러까지 알림 대상으로 삼으면
   한 조작(블러)에 두 영역이 동시에 낭독될 수 있어 규칙 위반. 밴드가 이미 "무엇이
   부족한지"를 문장으로 말하므로 필드 에러 텍스트는 보조 시각 정보로만 남김.

① 필수 표시(*)와 블러 에러 텍스트의 색
② 필수 표시는 `tokens.color.accent`, 에러 텍스트는 `tokens.color.ink`(굵게) + "Required — "
   접두 문구. 별도의 danger/red 톤 없음.
③ `tokens.ts`에 위험색 토큰이 없고 정본이 "토큰에 있는 것만 쓴다"고 명시 — 색을 새로
   추가하는 대신 문구 자체("Required")가 의미를 전달하도록 하고, 굵기로만 강조해
   "색만으로 전달 금지" 규칙과도 충돌하지 않게 함.
