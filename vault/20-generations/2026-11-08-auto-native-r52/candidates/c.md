# Candidate c — Split Delivery Addresses

**Split Delivery Addresses** lets a buyer who just checked out with several line items — several of them gifts — point each item at one of their saved delivery addresses before the order can be confirmed. State lives in exactly one map, `assignments: Record<itemId, addressId | null>`, which every derived value in the screen (which items are unassigned, which address backs a given row, the bottom band's sentence, and whether Confirm is enabled) is computed from in one `useMemo`. Tapping an unassigned (or already-assigned) row's "Choose address"/"Change address" button expands an inline, per-row picker listing the three saved addresses as individually focusable `radio`-role options — never a single opaque `Pressable` wrapping the whole row, so the expanded options stay reachable to a screen reader. The bottom band carries the screen's one live region: while any item lacks an address it states exactly how many ("3 of 5 items still need a delivery address…") and offers a "Next item (N left)" action that scrolls the list to, and opens the picker on, the first remaining unassigned item in catalog order; once every item has an address the band switches to an enabled "Confirm Order" button, and after confirming it collapses to a final confirmed sentence with no further actions.

## 브리프에 없던 것

1. **① 완료 조건을 "순서가 있는 체크리스트"가 아니라 "순서 없는 집합 조건"으로 어떻게 다르게 구현할지.** 브리프는 r49/c `SellerOnboardingChecklistScreen`을 참고하되 그 lock-step 메커니즘을 그대로 베끼지 말라고만 했다. **결정:** 상태를 `completedStepIds`류의 append-only 배열이 아니라, 각 아이템 id를 키로 갖는 `assignments` 맵(주소 id 또는 null)으로 모델링했다. 이 맵은 어느 방향으로든(배정→해제→재배정) 몇 번이든 뒤집을 수 있고, "현재 활성 행"이나 "잠긴 행" 개념이 전혀 없다 — 다섯 개 행 모두 항상 동시에 탭 가능하다. **근거:** 온보딩 체크리스트는 단계가 순서대로 잠금 해제되는 체인이라 "배열 + 고정 순서"가 자연스럽지만, 이 화면은 어느 아이템을 먼저 배정하든 상관없는 집합 문제라서 같은 구조(순서 기반 파생)를 그대로 쓰면 존재하지 않는 "잠김" 상태를 암시하게 된다.

2. **② "다음 미완료 지점으로 이동"을 비선형 메커닉에서 무엇으로 번역할지.** 브리프는 선형 체인이 아닌 경우에도 밴드가 "다음 미완료 지점으로 이동"하는 효과를 내야 한다고 요구했지만 구체적 동작은 정하지 않았다. **결정:** 고정된 아이템 배열 순서상 가장 먼저 나오는 미배정 아이템 하나를 골라 `FlatList.scrollToIndex`로 그 행까지 스크롤하고, 동시에 그 행의 인라인 피커를 자동으로 펼친다(선택까지 한 번에 이어지도록). **근거:** 순서 없는 집합에는 "다음 단계"가 논리적으로 존재하지 않지만, 사용자에게 보여줄 단 하나의 유용한 타겟은 필요했다 — 배열 순서는 게이트 로직이 의존하는 규칙이 아니라 순수한 프레젠테이션상의 타이브레이크일 뿐임을 주석과 구현 모두에서 분명히 했다(어떤 아이템을 먼저 배정해도 무방).

3. **③ 재배정·해제가 destructive 확인을 필요로 하는지.** 브리프는 "단순 재배정은 보통 destructive 확인이 필요 없다"는 판단을 맡겼다. **결정:** 이미 배정된 아이템의 주소를 바꾸는 것(다른 라디오 옵션 탭)과 "Clear assignment"로 완전히 해제하는 것 모두 네이티브 Alert나 Cancel/Confirm 플립 없이 즉시 반영한다. **근거:** 주문이 아직 확인(Confirm) 전이고 몇 번을 다시 바꿔도 비용이 없는 임시 배정 단계이므로, 유일하게 되돌릴 수 없는 지점은 "Confirm Order" 그 자체다 — 그래서 확인 흐름을 거기 하나로 집중시키고, confirm 이후에는 모든 행의 피커가 닫히고 더 이상 상호작용이 없는 종결 상태로 만들었다.

4. **④ 주문에 몇 개 아이템 / 몇 개 주소를 두고, 처음부터 몇 개를 미배정 상태로 둘지.** 브리프는 "선물로 여러 개 산 경우"라는 서사만 주고 구체적 개수나 초기 상태는 정하지 않았다. **결정:** 5개 라인아이템·3개 저장 주소로 고정했고, 처음부터 2개는 이미 배정(본인 주소), 3개는 미배정(선물)으로 시작하게 했다. **근거:** 전부 미배정으로 시작하면 "몇 개 남았는지" 문구가 항상 전체 개수와 같은 값만 보여주게 되어 부분 완료 상태의 문구("N of 5")를 화면을 전혀 조작하지 않고도 처음부터 검증할 수 있도록, 혼합 초기 상태를 의도적으로 선택했다.

5. **⑤ 저장 주소 데이터 모양을 기존 Saved Addresses 화면과 얼마나 맞출지.** 브리프는 "주소 데이터 모양은 맞추되 화면 아키텍처는 베끼지 말라"고 했다. **결정:** `label` / `recipientName` / `line1` / `line2?` / `cityStateZip` 필드는 r29·r34의 `SavedAddress`와 동일하게 유지했지만, 이 화면에 의미 없는 `isDefault`·`lockedByOrderId` 필드는 가져오지 않았다. **근거:** 이 화면은 주소 목록을 "관리"하지 않고 "참조"만 하므로, 그 두 화면이 가진 default-주소 승격이나 주문-잠금 같은 관리 전용 상태는 여기서 필요 없는 복잡도였다.
