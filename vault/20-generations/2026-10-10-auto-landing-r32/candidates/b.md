# Candidate b — round auto-landing-r32

## Concept
A near-monochrome, numbers-first repick landing where one circular category chooser drives a live chord/arc "companion purchase" diagram in the hero, and that same selection state cascades, unchanged in identity, through the value section's three recomputed stats and into the closing CTA's own button label.

## 브리프에 없던 것

**Brand voice / copy.** The brief fixes the device and the taboo phrases but not the actual sentences. I wrote repick as a resale marketplace that leads with proof (grade, verification, companion demand) before price, and kept every CTA/headline distinct from the convergence list (no "Watch", no "Right now,", no "Three ___ listing", no "List your first item", no disclosure literally framed as "why the AI picked this" — my disclosure is framed as "View condition report", a different mechanism/copy pair entirely).

**Accent color — rose-600 (#e11d48), calculated:**
- vs white (#ffffff): **4.70:1** — clears AA for small text (≥4.5) with a small margin. Used for solid fills (buttons, discount chip, focus outline) always paired with white text, and for borders/non-text strokes.
- vs ink zinc-900 (#18181b): **3.77:1** — clears only the 3:1 large-text/UI-component floor, not small text. I never place rose-600 as *text* directly against a zinc-900 surface anywhere in the route (the whole design stays light-surface, dark-ink-as-foreground-only, so this combination never actually occurs), so the shortfall is moot in practice but recorded as asked.
- Small-text-safe tint — rose-700 (#be123c): vs white **6.29:1**, vs zinc-50 **6.02:1**, vs zinc-100 **5.72:1**. Every place rose appears as *text* (eyebrows, AI-match tags, stat emphasis) uses rose-700, not rose-600, specifically so nothing sits at the borderline 4.70 number. All math via the standard WCAG relative-luminance formula, double-checked with a Python script, not eyeballed.
- Also verified the state-dependent neutral floor empirically: zinc-500 vs white 4.83, vs zinc-50 4.63, vs zinc-100 **4.40 (fails 4.5)** — so zinc-100+ tinted surfaces (the sort-toggle track, chip backgrounds) use zinc-600 (7.03–7.73 depending on exact surface), matching the brief's stated rule.
- Giant decorative quote-mark glyph in Social proof is aria-hidden but still a visible text node, so I sized it ≥24px (text-5xl) and colored it zinc-500 (≥3:1 and in fact ≥4.5:1) rather than a lighter "ghost" gray that would have failed.

**Body column width — calculated, not `ch`.** Using the given constant (chars/line = container-px ÷ (0.44 × font-px)):
- Hero sub: 18px font, `max-w-[34rem]` = 544px → 544 ÷ (0.44×18=7.92) = **68.7 chars/line**.
- Product-preview intro, Value intro/summary, Closing-CTA summary: 16px font, `max-w-[31rem]` = 496px → 496 ÷ (0.44×16=7.04) = **70.5 chars/line** (right at target, under the 75 ceiling).
- Social-proof blockquote: 18px font, `max-w-[32rem]` = 512px → 512 ÷ 7.92 = **64.6 chars/line** (intentionally under 70 — acceptable, quotes read like captions).
I initially wrapped the heading + body paragraph of two sections in one shared `max-w` div (36–40rem, which would have pushed body text to 80–91 chars/line, over the ceiling) and caught it on self-review — fixed by giving the `<p>` its own independent, narrower `max-w` instead of inheriting the heading container's width.

**Macro skeleton.** Left-aligned asymmetric hero (headline + single CTA + inline proof-listing card, all genuinely in Hero's own JSX, same grid) sitting above a full-width card holding the category chooser + chord diagram + live stat panel. Below: graded-listing grid with a sort toggle and a per-card condition-report disclosure, a 3-stat value row that recomputes from the same selection, a two-up testimonial/quote grid with a trust-stat strip, and a closing CTA panel whose headline, body sentence, and button label all re-derive from the live selection. Nothing resembling a pitch-deck snap sequence, map selector, swipe deck, wizard, or node-graph — confirmed against the whole banned-skeleton list.

**Category/weight dataset + arc geometry.** Six categories — Sneakers, Watches, Bags, Outerwear, Electronics, Vintage — with a symmetric 6×6 integer matrix (`COMPANION_MATRIX`, values 2–7, diagonal 0) meaning "out of 10 buyers of row-category, N also bought column-category within 30 days." No ties on any row's maximum, so `getTopCompanion()` (a plain row-scan, not a per-category switch of pre-written strings) deterministically picks one companion per category: Sneakers→Outerwear(7), Watches→Bags(6), Bags→Watches(6), Outerwear→Sneakers(7), Electronics→Vintage(3), Vintage→Outerwear(6). This single function result feeds the hero stat sentence, the Value section's first stat, and the closing CTA — verified live by curling the rendered route and grepping the HTML, which confirmed "Of every 10 Sneakers buyers, 7 also bought Outerwear…" and "List your sneakers — 7/10 buy outerwear too" both present and in sync on first load.
Geometry: nodes sit on a 440×440 viewBox, center (220,220), radius 150, at angles −90°+i·60°. I computed cos/sin once by hand and hardcoded the rounded (2dp) results as literals in `data.ts` (e.g. `{ x: 349.9, y: 145 }`) rather than running `Math.cos/sin` at module load, specifically to remove any possibility of server/client floating-point string drift. Arcs are quadratic Béziers `M ax ay Q 220 220 bx by` (control point = circle center) generated once from the 15 unordered category pairs; stroke-width = `1 + weight·0.85`, opacity = `0.35 + (weight/7)·0.55` when touching the selected category, else a flat `0.16`, color rose-500 active / zinc-300 dimmed.

**Static-data honesty.** All per-category numbers (companion matrix, days-to-sell, payout %) are explicitly described in copy as "repick's closed-sale history," never as live/real-time — matches the fact that `data.ts` is a fixed module, no fetch, no timer.

## SSR hydration-gating check
Confirmed by both code review and a live check: started the dev server, curled `/landing-evolve/r32/b`, and grepped the raw HTML for `opacity:0` — zero matches anywhere in the document, including inside the hero. The hero's entrance uses the pre-existing global CSS `rise` keyframe (pure CSS, `motion-reduce:animate-none`, resting state is the authored visible style — no JS/opacity risk at all). Every section below the hero wraps content in `Reveal.tsx`, which uses `useSyncExternalStore` (subscribing to nothing) to get a value that is `false` during SSR and the first hydration pass and only becomes `true` after React confirms hydration — rendering a plain, fully-visible `<div>` until then and only swapping to a real `motion.div` with `initial`/`whileInView` once genuinely mounted client-side. A no-JS or slow-hydration visitor therefore always sees fully opaque content. Verified the swap never ships `opacity:0` server-side via the curl+grep test above (0 occurrences of the literal string in the response body).

Exactly 3 rendered font weights used throughout (400 body default, 600 `font-semibold`, 800 `font-extrabold`/inline `fontWeight:800`) — grepped the whole route for every `font-*`/`fontWeight` occurrence to confirm no 500/700/300 sneaks in. Single display face `var(--font-display-mono)` used, written as the literal string at each of its ~6 call sites (Hero H1, three Value-section stat numbers, Social-proof trust-stat numbers, Closing-CTA H2) — never through a shared constant.
