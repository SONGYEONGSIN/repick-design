# Lens 2 (commercial polish) — auto-landing-r45

## Ranking
1. **c** — all four prescribed product-proof badges present (match%/grade/verified/discount), live recompute verified correct across the hero item *and* three secondary category items, closing CTA genuinely live.
2. **a** — cleanest, most polished execution and fully correct math with a genuinely live CTA, but the product card is missing the match% badge and only one item ever recomputes (no multi-item proof breadth).
3. **b** — correct math, honest non-faked CTA, and the richest animated interaction device, but the page has **zero product photo / match% / verified / discount badges anywhere** — it violates this repo's single most emphasized structural rule (product+proof in the hero fold) outright rather than just incompletely satisfying it.

## Per-candidate detail

### a — "Live Payout Receipt" (`app/src/app/landing-evolve/r45/a/`)

**Hand-verified math.** Core device: price slider (`PriceSlider.tsx`) + condition-grade radio group (`GradeSelector.tsx`), feeding `computeReceipt` in `data.ts:70-84`.
- Formula: `conditionDeduction = round2(price * rate)`; `afterCondition = round2(price - conditionDeduction)`; `platformFee = round2(afterCondition * 0.09)`; `netPayout = round2(afterCondition - platformFee + 4.50)`.
- Input 1 (the page's own default, `DEFAULT_PRICE=85`, `DEFAULT_GRADE_ID="excellent"` → rate 0.08, `data.ts:9,50`): deduction = round2(85×0.08) = **6.80**; afterCondition = **78.20**; fee = round2(78.20×0.09) = **7.04**; netPayout = round2(78.20−7.04+4.50) = **75.66**. The default-state screenshot (`a-1440.png`) shows the receipt lines `$85.00 / −$6.80 / −$7.04 / +$4.50`, and `a-1440-s100.png` shows the closing headline **"Sell it today and keep $75.66."** — exact match.
- Input 2 (price=200, grade="fair", rate 0.25): deduction = 50.00, afterCondition = 150.00, fee = 13.50, netPayout = 150.00−13.50+4.50 = **141.00**. Formula traced by hand, consistent with input 1's arithmetic pattern — no sign errors, no stale-variable bugs; `afterCondition` (not raw `listedPrice`) correctly feeds the fee calc per the stated "fee applied after condition deduction" rule (`data.ts:11`).

**Closing-CTA liveness.** `ClosingCTA.tsx:7` takes `netPayout: number` as a prop; `page.tsx:15` computes `receipt = useMemo(() => computeReceipt(price, gradeId), [price, gradeId])` and `page.tsx:58` passes `receipt.netPayout` straight through. No hardcoded literal — **genuinely live**, and the on-page copy (`ClosingCTA.tsx:16-17`) correctly tells the visitor to go move the slider to see it change.

**Strength.** The itemized "receipt" metaphor (scalloped ticket edge, barcode mark, dashed divider rows, expandable "why this deduction" accordion in `Receipt.tsx:142-166`) reads as a genuinely shipped fintech-style payout breakdown, not a mockup — the single cleanest, most restrained execution of the three, and the only one with a secondary expand/collapse interaction beyond the two core controls.

**Weakness.** `ITEM` in `data.ts:96-103` has `verified: true` and a grade but **no `matchPercent` field**, so the receipt's badge row (`Receipt.tsx:110-120`) only ever shows "Grade Excellent" + "Verified" — two of the four product-proof badges (매칭%·등급·인증·할인) the design principles call out explicitly (`design-principles.md:93`). There's also only one product on the page; unlike c, no secondary items are shown recomputing off the same inputs, so the "proof" breadth is thinner.

### b — "Match Reasoning Tree" (`app/src/app/landing-evolve/r45/b/`)

**Hand-verified math.** Core device: a 3-question single-choice tree (`ReasoningTree.tsx`) feeding `computeMatch` in `data.ts:98-112`.
- Formula: `sellers = max(6, round(48 × budgetFactor × categoryFactor × conditionFactor))`; `days = min(21, max(3, round(14 / (categoryFactor × conditionFactor))))`.
- Input 1 (budget="mid" 1.15, category="apparel" 1.5, condition="light" 1.0, `data.ts:75-77`): sellers = round(48×1.15×1.5×1.0) = round(82.8) = **83**; days = round(14/1.5) = round(9.33) = **9**.
- Input 2 (budget="high" 0.65, category="electronics" 0.7, condition="wellLoved" 1.35): sellers = round(48×0.65×0.7×1.35) = round(29.484) = **29** (above the `MIN_SELLERS=6` floor, so the floor never silently fires here); days = round(14/(0.7×1.35)) = round(14.81) = **15** (within the `[3,21]` clamp). Formula checks out — no sign errors, factors correctly multiplied not added, floor/ceiling clamps applied in the right direction.

**Closing-CTA liveness.** `ClosingCTA.tsx:7` takes `match: Match | null` directly; `page.tsx:20` computes `match = useMemo(() => computeMatch(answers), [answers])` and `page.tsx:57` passes it straight through, unmodified. When `match` is null (not all three questions answered) it shows an honest **"No path lit yet"** state (`ClosingCTA.tsx:36-43`) rather than faking a number — this is actually the most rigorous honesty behavior of the three candidates, explicitly designed against the exact "hardcoded literal that doesn't move" failure this repo's history warns about.

**Strength.** The animated tree itself (`LitLine.tsx`, `ReasoningTree.tsx`) is the richest interaction device of the three — locked/available/selected node tiers, framer-motion line-drawing gated by `useReducedMotion` (`LitLine.tsx:23,33`), a working "Restart" button (`ReasoningTree.tsx:38-44`), and a "Show the math" disclosure that reveals the three raw factors (`ReasoningTree.tsx:126-152`) so a skeptical visitor can audit the formula on-page. Genuinely more interactive and more transparent about its own arithmetic than a or c.

**Weakness — structural, not cosmetic.** A repo-wide `grep` across every file in `b/` for `Image|matchPercent|verified|ITEM|photo` returns **zero matches**. There is no product photo, no match-percentage badge, no seller-verification badge, and no before/after discount badge anywhere on this page — the entire "product preview" structural requirement (design-principles.md §Landing 구조 기본형 item 1 and item 2, `design-principles.md:91-93`, called out as **L2-promoted** and reproduced across two separate rounds) is simply absent. The tree substitutes an abstract archetype sentence ("furniture, $50–$200, light wear — 83 active sellers, avg 9-day sale") for an actual listing card. Compounding this, the captured default-state screenshot (`b-1440.png`, scroll 0) shows the tree fully unanswered, so the first-fold impression has **no visible proof number at all** until a visitor interacts three times — the one candidate whose hero screenshot doesn't demonstrate its own core value prop at rest.

### c — "Meet in the Middle" (`app/src/app/landing-evolve/r45/c/`)

**Hand-verified math.** Core device: a draggable/keyboard-operable split divider (`SavingsSplit.tsx`) setting a shared `discount` (15–70%) that feeds `repickPrice`/`savingsAmount` in `data.ts:44-50`.
- Formula: `repickPrice = round(newPrice × (1 − discount/100))`; `savingsAmount = newPrice − repickPrice`.
- Input 1 (the page's default, `DISCOUNT_DEFAULT=42`, hero item `newPrice=480`, `data.ts:8,62`): repick = round(480×0.58) = round(278.4) = **278**; saved = 480−278 = **202**. `c-1440.png` shows the "On repick" panel at **$278** with a "Save $202" handle, and `c-1440-s100.png`'s closing headline reads **"At 42% off, this overcoat is $278 on repick — a $202 gap from retail."** — exact match, verified against two independent surfaces of the same page.
- Input 2 — verified the "every price on the page recomputes" claim (`ValueSplit.tsx:11`, `Hero.tsx:22`) is literally true, not just asserted, by checking all three secondary category items at the same discount=42: Sneakers `round(180×0.58)=104.4→104`, Leather tote `round(410×0.58)=237.8→238`, Raw denim jacket `round(210×0.58)=121.8→122` — all three match the on-screen figures in `c-1440.png` exactly (`$104 / $238 / $122`). This is the only candidate where I could hand-verify live recompute across *four* independent dollar figures simultaneously, not just one.
- Also checked the `travelForDiscount` / `discountForTravel` round-trip (`data.ts:27-37`) for internal consistency: `travelForDiscount(42) = 30 + ((42-15)/55)×40 = 49.64`; `discountForTravel(49.64) = round(15 + ((49.64-30)/40)×55) = round(41.998) = 42` — inverse functions agree, no drift bug in the drag-handle math.

**Closing-CTA liveness.** `ClosingCTA.tsx:7` takes `discount: number` as a prop and **recomputes `repickPrice`/`savingsAmount` itself from that prop** (`ClosingCTA.tsx:8-9`) rather than receiving a pre-computed value — a slightly different wiring pattern than a/b (derived-in-component vs. derived-in-page) but equally live: `page.tsx:51` passes the live `discount` state straight through with no hardcoded literal anywhere in the chain.

**Strength.** The only candidate whose product card carries **all four** badges the design principles prescribe in one row — match% (`94% match`), condition grade (`A-`), verified-seller badge, and the live discount (`-42%`) — (`SavingsSplit.tsx:156-169`, confirmed in `c-1440.png`), plus a correctly-isolated "historical, doesn't move" closed-sale card in `SocialProof.tsx:8-10,62` whose own discount math (`Math.round((1 - soldPrice/newPrice) × 100)` = round((1−289/540)×100) = round(46.48) = **46%**) is deliberately computed from the closed sale's own two numbers rather than from the live `discount` state — correctly keeping "live" and "historical" math from ever being able to bleed into each other.

**Weakness.** In the fully-scrolled mobile screenshot (`c-390-s100.png`), the small closed-sale thumbnail (`SocialProof.tsx:46`, a 64px-wide `aspect-[4/3]` box with `overflow-hidden`) shows its alt text ("Brown shearling…") visibly bleeding outside the image container into the surrounding layout rather than being clipped — the exact image-load-failure overlap pattern design-principles.md explicitly flags as a graded failure mode (`design-principles.md:116`, the `auto-landing-r8`-sourced container-reservation rule). The hero-sized item images (96–112px boxes) render cleanly with no equivalent overflow, so this appears specific to the smaller 64px thumbnail; whether this is an artifact of the screenshot renderer failing to fetch the hotlinked Unsplash image or a genuine CSS containment gap at that size, it's visible in the delivered screenshot and is the one concrete rough edge on an otherwise fully-verified candidate.

## Unchecked scope
- Did not run the actual hard gates (`gate.mjs` static/sweep/a11y/perf) — relied on the tokens.ts files' self-documented WCAG contrast math and the design-principles.md historical contrast remedies, not independent recomputation of every color pair.
- Did not test real pointer-drag or keyboard interaction in a live browser — interaction correctness (onPointerDown/Move/Up wiring in c's `SavingsSplit.tsx`, radio-group wiring in a's `GradeSelector.tsx`, tree click wiring in b's `ReasoningTree.tsx`) was verified by source reading only, not by executing the app.
- Did not check `Reveal.tsx` / `useMounted.ts` scroll-reveal implementations for `motion-reduce` correctness in a and c as closely as I did for b's `LitLine.tsx` (which I did fully trace).
- Did not verify every testimonial/stat copy block for factual self-consistency beyond the ones directly tied to the live math (e.g., did not re-derive the `180K` / `3,100` / `18,400` headline stats, which are explicitly documented as fixed historical figures in all three candidates).
- Did not inspect page source for `multi-display-face` or font-weight-count violations beyond what each candidate's own `tokens.ts` comment block self-reports.
- Could not confirm with certainty whether the c mobile-thumbnail overflow is a renderer/network artifact (blocked Unsplash fetch in the screenshot tool) versus a reproducible CSS bug — flagged as the best available read of the evidence, not a certainty.
