# Lens 3 (differentiation) — auto-landing-r45

## Ranking
1. b — a sequentially-gated branching reasoning tree (lock states + animated path-lighting down a vertical spine) with no close mechanic-and-visualization twin anywhere in the catalog I could find.
2. a — a skeuomorphic itemized "payout receipt" (scallop edge, barcode, dashed rules) whose paper-ticket presentation is unique in the catalog, even though its input mechanic (price slider + single-select condition grade driving a fee formula) has several catalog cousins.
3. c — a draggable divider resizing two priced panels; the underlying interaction (pointer-capture drag handle along one axis, `setPointerCapture`, live recompute) is the most-repeated mechanic type in this catalog, with a fairly close precedent in production `v6/Slider.tsx`.

All three are genuinely different *devices* from each other (confirmed by reading each one's source, not just the screenshots) — no pair is a variation on the same idea. The difference between 1st/2nd/3rd here is about novelty relative to the existing catalog, not about any pair converging on each other.

## Per-candidate detail

### a — `app/src/app/landing-evolve/r45/a/`
**Device, confirmed from source:** `Hero.tsx` renders a `PriceSlider` (native `<input type=range>`, $15–$400) and a `GradeSelector` (4-option radio group styled as pills, deduction rates −3%/−8%/−15%/−25%). Both feed `computeReceipt()` in `data.ts` (pure function, no `Math.random`/`Date`), which produces a 5-line `ReceiptLines` object rendered by `Receipt.tsx` as a physical-ticket artifact: a `ScallopEdge` (radial-gradient punch-hole strip, `Receipt.tsx:15-30`), a decorative `BarcodeMark` (`Receipt.tsx:32-43`), dashed divider rules between line items, and an expandable "why this deduction" disclosure (`Receipt.tsx:142-166`).

**Neighbors checked:**
- `app/src/app/(marketing)/v14/PayoutCalculator.tsx` — select-dropdown category+condition → estimate range + fee + net, in a plain bordered card with a lead-capture form. Same genre (live fee math from user input) but no itemized multi-line receipt, no document skeuomorphism, no slider — a simpler calculator widget, not a close visual/structural twin.
- `app/src/app/(marketing)/v13/LedgerCard.tsx` — closest real neighbor: a range-slider-driven "ledger" with per-line amounts, share bars, a standing total and a fee multiple, plus waivable line items. Structurally closer (slider → multi-line money breakdown → footer total) than v14, but it reads as a clean paper-document "ledger" card, not a physical-ticket mimicry (no scallop edge, no barcode, no dashed receipt rules, uses toggle "waive" buttons rather than a condition-grade selector). Judged: same broad genre (live itemized-money device), different concrete device — acceptable differentiation, not a scaffold clone.
- `app/src/app/(marketing)/v22/Ledger.tsx` — misleading name-only match; this is actually a live-reranking order-book table driven by weight sliders, not a receipt/ledger of a single transaction. No real overlap.
- r44/c `PriceSlider.tsx` — same component name as a's slider but feeds a `DepletionChart`, a different downstream device entirely.

**Verdict:** Novel surface device (the physical-receipt object) on a familiar input mechanic (slider + grade radios) that recurs across the catalog in several forms. Clean, well-differentiated from its nearest neighbors in presentation even where the underlying "live fee math" genre is common.

### b — `app/src/app/landing-evolve/r45/b/`
**Device, confirmed from source:** `ReasoningTree.tsx` renders a strict sequential 3-question tree (Start → budget → category → condition → leaf) as a vertical spine (`QUESTIONS.map` loop, `ReasoningTree.tsx:54-117`). Every level is always rendered, but a level is `locked` (disabled buttons, `Lock` icon) until the level above has an answer (`ReasoningTree.tsx:86`). `LitLine.tsx` draws two stacked line layers per segment (a static dim layer + an animated accent layer that scales in via framer-motion when `lit` becomes true), so the path "lights up" as you answer. The leaf is a pure 3-factor multiplicative formula (`computeMatch` in `data.ts:98-112`), not a 27-entry lookup table, and has an optional "show the math" disclosure of the three factors.

**Neighbors checked:**
- `app/src/app/landing-evolve/r42/c/BracketTree.tsx` (+ `Connectors.tsx`, `Matchup.tsx`) — a visually tree-shaped device (SVG-connected columns, round labels) but it is a **static, pre-resolved single-elimination tournament bracket** (Round of 8 → Semis → Final → Champion) with a fixed dataset; the only control is a `showScore` toggle that doesn't change the tree's shape. No sequential answering, no locking, no path-lighting driven by user choices. Different data structure (fixed bracket vs. live decision tree) and different interaction model entirely.
- `app/src/app/(marketing)/v10/PreferenceGraph.tsx` — a bipartite weighted graph (5 preference nodes × 4 product nodes, 20 SVG bezier edges) where selecting one tab re-weights edge opacity/width. This is a single-select tablist over a network diagram, not a sequential multi-step tree with gating — different data shape (DAG/bipartite graph vs. strict branch) and different interaction (one active node at a time vs. three-step drill-down with lock states).
- `app/src/app/landing-evolve/r41/c/MatchQuiz.tsx` — superficially the closest "quiz" by name/purpose (category/budget/tolerance pill groups → matched listing), but it's a flat, unordered multi-select filter form with no branch visualization, no sequential locking, no tree/line rendering at all.

**Verdict:** No neighbor combines sequential gating + animated path-lighting + a vertical branching spine the way b does. The closest shape-match (BracketTree) is mechanically a different genre (static results display vs. live user-driven decision path). This is the most structurally distinctive of the three candidates.

### c — `app/src/app/landing-evolve/r45/c/`
**Device, confirmed from source:** `SavingsSplit.tsx` is a single draggable divider between two flex panels ("On repick" / "Buying new"), driven by one shared `discount` state (15–70%). Drag math: `updateFromClientX` computes a raw pointer percent against the container's bounding rect, maps it through `discountForTravel`/`travelForDiscount` (`data.ts:27-36`) into a 30–70% panel-width split, uses `setPointerCapture` for drag continuity (`SavingsSplit.tsx:54-58`) and full arrow-key/Home/End keyboard control. Every price in both panels (hero item + 3 category items) and the closing-section sentence re-derive from the same `discount` value via `repickPrice()`.

**Neighbors checked:**
- `app/src/app/(marketing)/v6/Slider.tsx` — the closest mechanical twin found: a pointer-drag handle on the x-axis using `setPointerCapture`, `onPointerDown/Move/Up`, full keyboard support, and a `role="slider"` handle — essentially the same drag-handle plumbing as c's `SavingsSplit`. The divergence is in payload and purpose: v6's slider reveals a before/after **image comparison** (clip-path over two photos, "Threshold AI Match" framing) for a single hero item, purely visual; c's divider resizes two **priced, itemized panels** with multiple line items that recompute live on both sides, plus a persistent shared-state sentence in the closing section. Judged: same core interaction primitive (x-axis pointer-drag handle), different purpose and different downstream content — this is the "device differs in what it manipulates, not identical surrounding scaffolding" case the brief says to treat generously, but it is the least novel of the three at the mechanic level since the interaction itself (not just the broad "slider" genre) has a direct, specific precedent in the production catalog.
- `app/src/app/(marketing)/v20/ValueSplit.tsx`, `v21/ValueSplit.tsx` — same component *name* ("ValueSplit") as c's own middle section, but these are static 3-stat-panel sections with zero drag/split-panel mechanic — name-only overlap from the shared scaffold, not a device match.

**Verdict:** Legitimate, well-executed device, and clearly a different concept from a and b. Relative to the wider catalog, though, it reuses the most common interaction primitive here (pointer-drag handle along an axis — also present in a's slider, v6, v13, v21 `WeightSlider`, v24 `slider-row`, r44/c `PriceSlider`), and has one genuinely close mechanical sibling in `v6/Slider.tsx`.

## Macro-shell convergence (noted, not scored against any one candidate)
All three r45 candidates use the identical file-splitting scaffold: `Hero.tsx` / `ValueSplit.tsx` / `SocialProof.tsx` / `ClosingCTA.tsx` / `Reveal.tsx` / `tokens.ts` / `useMounted.ts` / `data.ts`, with the same section order (nav → Hero+device → ValueSplit ghost-number/3-feature-card → SocialProof 2-testimonial+3-stat block → ClosingCTA centered-card-with-icon → footer disclaimer line). This matches the catalog's previously-flagged macro-shell-convergence pattern exactly, and the same file names (`ValueSplit.tsx`, `SocialProof.tsx`, `ClosingCTA.tsx`, `Hero.tsx`) recur verbatim in production `v20`, `v21`, `v22`. Since all three r45 candidates converge on it equally, it does not separate them from each other here, but it is worth naming as expected/systemic rather than a surprise.
