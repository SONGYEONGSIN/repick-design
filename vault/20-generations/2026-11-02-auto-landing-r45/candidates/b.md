# r45/b — Match Reasoning Tree

**One-line concept**: A three-question budget → category → condition quiz where every click lights the real branch and connecting edge of an always-visible decision-tree flowchart, terminating in a formula-derived listing-archetype leaf (active-seller count + avg days-to-sell) that the closing CTA quotes live.

Files: `app/src/app/landing-evolve/r45/b/{page.tsx, Hero.tsx, ReasoningTree.tsx, LitLine.tsx, Reveal.tsx, ValueSplit.tsx, SocialProof.tsx, ClosingCTA.tsx, data.ts, tokens.ts, useMounted.ts}`

## 브리프에 없던 것

① **Exact quiz questions/options** — invented all three, since the brief only gave the category names (budget/category/condition), not wording or option sets.
② Q1 "What's your budget range?" → Under $50 / $50–$200 / $200+. Q2 "What are you shopping for?" → Furniture / Apparel / Electronics. Q3 "How much wear can you live with?" → Like-new only / Light wear OK / Well-loved OK.
③ Kept each question to exactly 3 options so the tree is a true 3×3×3 = 27-leaf structure (small enough to render as a legible flowchart at 390px, large enough that the terminal numbers plausibly vary). Furniture/apparel/electronics and the three price bands map onto repick's actual resale catalog rather than a generic SaaS example.

① **Tree layout + node count** — invented the whole diagram geometry since the brief named the vocabulary ("flowchart/decision tree with nodes and connecting lines") but not a concrete structure.
② A single vertical spine: Start (1 node) → Q1 row (3 nodes) → Q2 row (3 nodes) → Q3 row (3 nodes) → one Leaf card. 11 nodes, max fan-out of 3 at any junction (no N×N mesh). Each row always renders in full; a row is "locked" (dashed border, Lock icon, disabled) until the question above it has an answer, then its 3 options go from locked → available-dim → selected-lit as the visitor clicks. Branch geometry: within each row, the vertical spine lands at the row's horizontal center (= the center option's own center, since 3 equal thirds put the middle third's midpoint exactly at 50%); two horizontal half-branches run from that 50% point to the left option's center (16.6667%) and the right option's center (83.3333%). These are expressed as literal Tailwind arbitrary percentages (`left-[16.6667%] w-[33.3333%]` etc.) rather than any JS/DOM measurement, so alignment is guaranteed by the grid's exact equal-thirds math (no gap on the 3-col grid; visual spacing between pills comes from inner `px-1.5`/`px-2` padding instead, which is symmetric and doesn't shift each column's true center) and holds at every breakpoint without runtime layout code.
③ Chose a re-centering spine (rather than a literal off-center branch from whichever node was actually picked) because: (a) it keeps every edge a simple 2-point line — no diagonal/offset routing code to get subtly wrong without a renderer to test against, and (b) it still satisfies the requirement literally — the selected node's own tick and its own half-branch are the ones that light, the other two stay dim, every click visibly moves the lit path — while staying legible as a *tree*, not a dense bipartite mesh that would read as a network/map (explicitly excluded).

① **Edge "draw" animation mechanism** — invented, since the brief asked for framer-motion-driven edge drawing but not an implementation.
② `LitLine.tsx`: every spine segment and branch is two stacked layers — a static dim line (the tree's permanent shape, `#3f3f46`) and an accent overlay (`#FB7185`) that framer-motion scales from 0→1 (scaleY for vertical segments with `transform-origin: top`, scaleX for horizontal half-branches with `transform-origin` pinned at the trunk-side edge so they visually grow *outward from the spine toward the chosen node*). Gated by `useReducedMotion()` + a `useMounted()` check — reduced-motion or pre-hydration renders the final scale value directly with no transition, never a lingering invisible state.
③ Avoided SVG + `getBoundingClientRect` path-drawing because without a running dev server to screenshot against, a coordinate-matching bug between an SVG viewBox and real DOM node positions would be undetectable until gated/reviewed; the layered-div approach can't drift out of alignment because both layers share the exact same box.

① **Formula constants for the leaf (seller count / avg days)** — invented; the brief's own example ("41 active sellers, avg 6-day sale") is a style target, not a model.
② `BASE_SELLERS=48, BASE_DAYS=14`; per-option factors — budget: under50=0.85, mid=1.15, high=0.65; category: furniture=1.0, apparel=1.5, electronics=0.7; condition: likeNew=0.6, light=1.0, wellLoved=1.35. `sellers = round(BASE_SELLERS × budgetFactor × categoryFactor × conditionFactor)` clamped to a 6 floor; `days = round(BASE_DAYS / (categoryFactor × conditionFactor))` clamped to [3,21]. E.g. apparel + $200+ + well-loved → 63 sellers / 7-day avg (same order of magnitude as the brief's example); electronics + under-$50 + like-new-only → 17 sellers / 21-day avg (narrow niche, slow sale — the formula's own extremes make sense).
③ Modeled on this catalog's existing `r44/c` `dailyRate(price)` pattern (a fixed closed-form function of the inputs) specifically so the leaf is demonstrably *computed*, not a 27-row lookup table someone wrote by hand — and exposed via an Q&A "Show the math" disclosure on the leaf (lists the three raw factors) as proof it's a real function, not a canned string.

① **Total-paths ghost number (27)** — invented as a secondary liveness-safe statistic.
② Computed in `data.ts` as `QUESTIONS.reduce((acc,q) => acc * q.options.length, 1)` rather than typed as a literal `27`, used as the ValueSplit ghost numeral and in one SocialProof stat, both explicitly labeled "a fixed count, not a live figure."
③ Needed one more section-level ghost number/stat per this catalog's structural doctrine, but any number on this page risks reading as a false liveness claim given the page's whole premise is "live." Deriving it from the question set (so it can't drift from the real branch count) and labeling it as fixed-not-live in the copy itself satisfies "don't let any other number make a blanket liveness claim that isn't true."

① **Accent hex + contrast numbers (rose/pink family, as assigned)** — invented and computed by hand (sRGB → linearized → relative luminance → WCAG ratio), written into `tokens.ts` alongside the classes:
② Fill/large-text hex: **`#E11D48`** (rose-600), relative luminance L≈0.1736 against bg `#0B0B0F` (L≈0.00345). White text on this fill → **4.70:1** (passes AA at all text sizes — used as the default on-fill text color). Dark ink (`#0B0B0F`) on this fill → **4.18:1** (clears the 3:1 large-text/non-text floor only, so it is never used for small text on the fill — not used anywhere in this candidate, documented for completeness). This hex as direct small text on bg → also 4.18:1, short of small-text AA, so it's used only as a *background fill*, never as running text.
   Small-text/icon/focus-ring tint: **`#FB7185`** (rose-400), L≈0.3401 → **7.30:1** against bg — used for all small accent text (Q-number labels, "Show the math" toggle, icons, focus ring).
③ Picked rose-600/rose-400 as the fill/tint pair specifically because rose-600 clears full AA (4.70:1) with *white* text at all sizes (the doctrine's default-to-white rule), unlike the repo's own documented default purple (`#6E56CF`, 3.73:1, AA-fails small text) — avoids inheriting that known pitfall while staying in the assigned rose/pink family.

① **Font-weight trio** — invented as 400 / 600 / 800 (`font-normal` / `font-semibold` / `font-extrabold`), explicitly *not* this catalog's common 400/700/800 (`font-bold`) because the brief's own default example uses 400/600/800 for other candidates too; grepped the whole folder at the end to confirm `font-bold`, `font-medium`, `font-black`, `font-light` etc. never appear.
② 400 = all running/body copy. 600 = all UI labels — eyebrows, captions, stat labels, question prompts, pill/button labels, testimonial names. 800 = the one display headline per section + the two large tabular-nums stat/ghost numerals.
③ No serif, no second display face — `--font-display-mono` (JetBrains Mono Display) used only on the 5 large Latin headline moments (H1, the two H2s, the ghost "27", the logo wordmark), never on body copy.

① **Body-copy container widths** — invented per-paragraph using the mandated 0.44em formula (`chars = width ÷ (0.44 × font-size)`), never `ch`.
② `BODY_WIDTH_BASE = max-w-[496px]` for all 16px (`text-base`) paragraphs → 496 ÷ (0.44×16) = 496 ÷ 7.04 ≈ **70.5 chars**. `BODY_WIDTH_SM = max-w-[430px]` for all 14px (`text-sm`) paragraphs → 430 ÷ (0.44×14) = 430 ÷ 6.16 ≈ **69.8 chars**. Both sit just under the 70-char target, well clear of the 75-char hard ceiling. Used on: Hero subhead (base/496), ValueSplit intro + card bodies (sm/430 for the intro paragraph; card bodies are capped `max-w-[300px]` and run well under 70 chars by inspection since they're short), SocialProof testimonial quotes (base/496), ClosingCTA body copy (sm/430).

① **Node-locked vs. available vs. selected visual encoding (no color-alone, no glow)** — invented the three-tier state system.
② Locked: dashed `zinc-700` border, transparent fill, `Lock` icon (zinc-500, decorative), `text-zinc-400` label (never below the dark-surface floor), `cursor-not-allowed`, real `disabled` attribute (removed from tab order, which is correct for a non-interactive state). Available: solid `zinc-600` border, `text-zinc-300` label, subtle white-tint fill, hover brightens border/bg. Selected: `border-2` + solid `#E11D48` fill + white text + a `Check` icon — so selection is legible by icon + fill + border-weight together, not by hue alone.
③ Every state change is driven by border-style/width, fill, and an icon in addition to color, satisfying "never convey meaning by color alone," and every emphasis is fill/border/weight-based rather than any box-shadow/blur glow.

① **Restart affordance + "Show the math" disclosure** — invented as the 4th/5th required interactions beyond the three quiz clicks.
② Restart (header of the tree card) resets all three answers to `null` in one click, instantly dimming the whole lit path back to its initial state. "Show the math" is a disclosure button (`aria-expanded`) on the completed leaf that reveals the three raw multiplier factors used to derive the sellers/days numbers, both focus-ring-audited (`FOCUS_RING` applied, text on the dark card background re-checked at `text-zinc-400`/`text-zinc-200`, both already-verified contrast tiers, so the one interaction beyond the default view does not introduce a new, unaudited surface).
③ Restart demonstrates the tree is genuinely re-enterable state (not a one-shot animation); the math disclosure reinforces the determinism claim the whole page makes, and together with scroll-triggered `Reveal` on ValueSplit/SocialProof they bring the interaction count to 6 (3 quiz picks + restart + math toggle + scroll reveal), clear of the 4-minimum.
