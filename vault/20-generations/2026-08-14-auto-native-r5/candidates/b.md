# Candidate b — Order status (evolve-r5-b)

A vertical status-stepper timeline for a single post-purchase order — four ordered steps (Payment confirmed → Seller shipped → In transit → Delivered) connected by a rail line, each with an actual/estimated date and a tap-to-expand detail line, plus an item summary card and a tap-to-reveal courier/tracking card, ending in a fixed bottom "Confirm receipt" action once Delivered is reached. Structurally distinct from every listed macro bucket: it is not a chat-style chronological thread (no bubbles, no back-and-forth authorship), not a checklist of independently-togglable items (exactly one step is ever "current" and step order is fixed, not user-decided), not a plain always-scrolling settings list (it has a genuinely fixed bottom action band, conditionally present), and not a filter-chip feed (there is no filtering — the four steps are a complete, non-filterable sequence).

## 브리프에 없던 것

① Decide: whether the dummy order's `current` step should sit mid-timeline (e.g. "In transit") or all the way at the final step ("Delivered"), given the round's r3 lesson demands the terminal "Confirm receipt" control be a genuinely fixed, reachable, functional control once available.
② Decided: set the single dummy order's current step to "Delivered" (the final step), so the fixed bottom band and its functional `onPress` are actually present and pressable in the rendered/judged screen, rather than leaving that control un-exercised. The component still computes `currentIndex`/`nextStep` generically from `step.status`, so if the data were changed to an earlier current step, the band would correctly disappear and a "Next: <step>, estimated <date>" banner would take its place instead — the pre-delivery "no terminal action yet" path exists in code, it's just not the path this round's dummy data exercises.
③ Why: r3's lesson explicitly warns against a terminal action that is "disabled/dead" or hard to reach; the safest reading for a single-snapshot dummy screen was to make the control observably functional rather than only theoretically correct in an unreached code branch.

① Decide: how to render the connecting vertical line between step circles in a `FlatList` (no single continuous line element ships with RN), and how to color it to reflect progress (done vs. not-yet-reached segments).
② Decided: each row owns two line segments (above and below its own circle) inside a fixed-width `rail` column; the segment is `tokens.color.accent` if it connects two steps that have both been reached (`status !== "upcoming"`) and `tokens.color.border` otherwise, with the very first/last segments painted `tokens.color.bg` (screen background) to fake a rounded, closed-off endpoint instead of a hardcoded `"transparent"` keyword.
③ Why: neither GENERATION.md nor the catalog specifies a stepper/timeline vocabulary (the closest precedent, `HandoffCheckScreen`, uses flat dashed-border check markers with no connecting rail, since its six checks aren't ordered). I extended that screen's marker-shape idiom (border style/fill communicates state, not color alone) to a two-segment rail, and chose `tokens.color.bg` over the `"transparent"` keyword to keep every color value traceable to an actual token or a real screen-background token rather than a special-cased non-token constant.

① Decide: how to format the order's price so the Won sign is safe against the r4 caution about `tabular-nums` + `₩` rendering artifacts, while still matching the rest of the app's `₩`-prefixed KRW convention (used in `watchlist/data.ts`, `detail/data.ts`, `account/data.ts`, `notifications/data.ts`).
② Decided: `formatWonAmount()` in `data.ts` returns only the comma-grouped digit string (no `₩`), and the component renders the `₩` as its own sibling `<Text>` node immediately before the digits, inside the parent price `<Text>` — and no `tabular-nums`/`fontVariant` style is applied anywhere in the file.
③ Why: r4's caution is explicit and low-confidence-but-avoid; taking the more conservative of its two offered mitigations (separate sibling text) costs nothing here since this screen has no scrolling numeric ticker that would have benefited from tabular alignment in the first place.

① Decide: what counts as "informational" vs. "interactive" for a timeline screen, i.e. how many genuinely functional (non-decorative) controls to give the user beyond the required terminal action, since the screen is explicitly framed as "primarily informational."
② Decided: two more interactions beyond Confirm receipt — (a) tapping any step row toggles an expanded detail paragraph for that step (`accessibilityState={{expanded}}`), and (b) tapping the courier/tracking card toggles a revealed sub-panel with carrier phone and last-scan location.
③ Why: the task's hard rules require "a couple of genuinely interactive controls" beyond the terminal action; expand/collapse-on-tap was explicitly given as an example in the brief itself ("expand/collapse a step's detail, tap tracking reference to reveal courier info"), so I implemented exactly those two named examples rather than inventing unrelated ones.
