# Strata — headcount & budget allocation console

## Structure

Strata is a finance/FP&A console for a mid-size company (Northwind Inc., ~322 headcount, ~$6.7M quarterly spend) that allocates budget across six departments and five cost types. Standard app shell (256px left sidebar with brand lockup, workspace switcher, two nav sections, user footer; 44px topbar with a ⌘K search trigger opening a real command palette, a primary "New budget request" action, notifications and avatar menu; mobile = drawer nav). Inside the main content area there is deliberately **no narrow master-list rail** — the treemap itself is the primary navigation surface, replacing where a list would normally sit. Top to bottom: page `<h1>` + a grouping toggle (By department / By cost type) and a quarter toggle (Q4 2026 / Q3 2026); a single bordered strip of three inline metrics (total spend, budget variance, flagged line items — deliberately *not* four elevated KPI cards in a row); the **Allocation Treemap** itself, full-width and the single largest element on the page, built from a hand-written deterministic slice-and-dice layout algorithm (recursive half-total bisection in a fixed 280×120 logical box, coordinates rounded to exactly 2 decimals, so tile area is always an exact function of value — never a hand-typed overlapping rectangle); and below it a selection-synced **Department/Cost-type Detail** panel with three subsections — a proportional-bar breakdown of the other dimension, a six-quarter spend sparkline, and a sortable related-budget-line-items table. Every treemap tile always shows its label and dollar value as real text (sized by a four-tier font scale keyed to the tile's own area fraction); hovering or focusing a tile additively overlays a crosshair (two thin guide lines meeting at the tile's center) plus a small tooltip card with share-of-total and budget-variance context — screen-reader users get the same variance/share facts via an `sr-only` span already inside the button, so the tooltip is never the only place that information exists. At `sm` and below the recursive rectangle layout gives way to a vertical stack of full-width proportional bars (same data, same buttons, same severity colors) so no tile ever shrinks below legibility and nothing scrolls horizontally.

**Theme**: true light — `zinc-50` app canvas, `white` cards with `zinc-200` borders and `shadow-sm`, never cream/paper. **Accent**: a single rose, reserved for primary actions/active segmented-control states and — the one semantic use inside the data viz — the treemap's budget-variance severity ramp (`zinc-100` fill = within budget; `rose-200`/`rose-400`/`rose-600` = mild/moderate/severe overspend, each fill/text pairing individually contrast-checked: rose-600 uses white text at 4.7:1, rose-400 uses zinc-900 text at 6.5:1 because white on rose-400 fails at 2.7:1). **Typography**: body and all Korean/English copy stays on `--font-sans` (Pretendard); `--font-display-grotesk` appears only on the sidebar wordmark and the page `<h1>` — nowhere else; exactly three rendered font-weight values are used anywhere on the route (`font-normal` 400, `font-medium` 500, `font-semibold` 600), applied directly to every leaf element including every `<th>`'s inner button so no UA-default bold leaks in.

**Interactions (≥4, all real client state)**: (1) treemap cell hover/focus → additive crosshair + tooltip, keyboard-reachable via Tab; (2) treemap cell click → sets the selected department or cost type, which re-renders the entire detail panel below (breakdown bars, sparkline, records table); (3) grouping toggle (By department / By cost type) re-slices the same underlying actual-spend matrix into a different treemap partition; (4) quarter toggle (Q4 2026 / Q3 2026) re-slices the same matrix along the other axis and updates every derived KPI/variance figure; (5) records table column-header sort (Line item / Quarter / Amount / Status) with real `aria-sort` cycling; (6) a "pin for comparison" affordance on each record row, whose pinned-set state lives inside `RecordsTable.tsx` — genuinely independent of, and never reset by, the treemap's selection state one level up; (7) the ⌘K command palette, searchable across departments, cost types and budget line items, which focuses-restores to its trigger button only on a real open→closed transition (`wasOpenRef` pattern, never on mount).

**Completeness vs. reference products**: closer to a focused Mercury/Ramp-style spend-ops surface than a full Coinbase-grade exchange console — it covers one coherent workflow end-to-end (survey spend by two dimensions and two quarters, drill into a category, inspect its line items, flag/compare records) with real empty states, real focus management and full keyboard paths, but intentionally does not attempt a settings surface, multi-entity consolidation, or a write-capable approval flow (the "New budget request" primary action opens an honest inline draft-started note rather than faking a persisted write).

## 브리프에 없던 것

① 도메인 4종(클라우드 비용/마케팅/스토리지/헤드카운트) 중 구체적으로 무엇을 만들지 ② 헤드카운트·예산 할당 콘솔("Strata", 부서×비용유형 매트릭스) ③ 브리프가 옵션으로만 제시했고, 기존 라운드(r44/a)가 이미 클라우드 비용-트리맵을 다뤄 겹침을 피하고자 선택.

① 부서 6개·비용유형 5개의 실제 달러 금액, 분기별 타깃(예산) 값 ② 손으로 작성한 2개 분기(Q4/Q3 2026) × 6부서 × 5비용유형 = 60개 리프 값 + 부서별/비용유형별 고정 타깃 ③ 브리프는 "현실적이고 결정론적인 더미 데이터"만 요구; 트리맵 셀 합계가 상위 합계와 정확히 재구성되도록(그리고 과소/과다 예산 사례가 둘 다 나오도록) 구체적 숫자는 직접 설계.

① "over budget" 심각도 등급을 몇 단계로, 어느 임계값으로 나눌지 ② 3단계(mild ≤5%, moderate ≤15%, severe >15%) + "within"(≤0%) ③ 브리프는 "over-budget 셀을 rose로 강조"만 요구했고 구체적 단계 수·경계값은 없었음; 각 단계별 배경/텍스트 조합을 실제로 대비비 계산(4.5:1 기준)해 통과하는 Tailwind 스텝만 골라 역산.

① 6분기 스파크라인에 쓸 과거 분기 수치(브리프는 2개 분기만 요구) ② Q3 2025~Q4 2026까지 6개 분기 고정 배열, 마지막 값은 반드시 Q4 2026 실제값과 일치하도록 수기 작성 ③ "trend"라는 단어가 브리프의 디테일 패널 요구사항에 있었지만 2개 분기 토글만으로는 의미 있는 추세선이 안 나와서, 별도의 고정 히스토리 배열을 도입.

① 트리맵 모바일 "simplify" 요구를 구체적으로 어떻게 구현할지 ② `sm` 미만에서 절대 좌표 사각형 레이아웃을 완전히 포기하고 수직 스택 막대 리스트로 전환(같은 버튼/같은 데이터, 폭만 값 비례) ③ 브리프는 "셀이 스택/단순화될 수 있다"고만 했고 구체적 구현 방식은 정하지 않았음; 6~8개 셀을 390px에서 사각형 분할하면 가독성이 깨질 것으로 판단해 막대 리스트를 선택.

① 상단 KPI를 몇 개의 카드로, 어떤 레이아웃으로 보여줄지 ② "4개 KPI 카드 그리드" 금지 패턴을 피해 1개의 테두리 카드 안에 3개 지표를 `divide-x`로 나눠 배치 ③ 브리프가 명시적으로 금지한 "sidebar + 4 KPI cards in a row" 기본형을 피하기 위한 결정.

① 아바타를 실제 사진으로 쓸지 여부 ② 이니셜 배지(생성형 CSS, `next/image` 전혀 사용 안 함)로 대체 ③ 브리프가 "사진이 거의 필요 없을 것"이라 명시했고, 가짜 인물 사진을 쓰는 것보다 정직한 이니셜이 더 적절하다고 판단.
