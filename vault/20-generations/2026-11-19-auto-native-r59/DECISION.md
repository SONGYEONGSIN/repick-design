# auto-native-r59 — DECISION

## §0 라운드 수 확정 / 타깃

이 실행은 스케줄된 2-라운드 연속 요청의 **2번째**(1번째는 `auto-landing-r57`, 승자 a, 커밋·푸시 완료). `round-budget.mjs`는 매 호출마다 독립적으로 1을 반환(미채움 0종). 오늘은 월요일이 아니므로 native 고정 주기 미적용 — 타깃은 "이번 실행에서 이미 생성한 타입(landing) 제외"한 `[dash, native]` 풀에서 균등 난수 → **native**. `reassign-queue.md`에 target:native 대기 항목 없음.

## §2 GENERATE — 서브에이전트 치환 고지 (round A와 동일)

전용 `designer`/`comparator` 에이전트 정의가 이 환경에 없어 `general-purpose` Agent로 대체. 역할 지시는 `native/GENERATION.md` 전문 + 과거 라운드 교훈을 조립해 각 designer 프롬프트에 그대로 담아 전달.

## §3 HARD GATE

`native/node_modules` 미설치 상태였음(이 실행의 환경 고유 부트스트랩 — 루트/`app`만 설치돼 있었음) → `npm install` 선행. 등록(`native/screens.ts`·`screens.json`)은 3개 후보 완료 확인 후 오케스트레이터가 중앙에서 일괄 처리(슬러그 `evolve-r59-a/b/c`). **12/12 게이트 1차 클린** — 1-fix 불요.

## §4 JUDGE 패널

3렌즈 블라인드(`general-purpose` Agent). 스크린샷: Expo Web export(`EXPO_PUBLIC_SCREEN=<slug>`) → serve 8091 → Playwright 390×844·768×1024 캡처, 후보당 2프레임, 0 blank.

**사전 고지 사항**: 후보 a는 자진신고로 `native/src/evolve/r48/c`(BulkPriceDropScreen)와의 매크로 유사성(다중선택+할인%+선택개수밴드)을 밝혔다. 렌즈3에게 이를 그대로 믿지 말고 직접 검증하도록 명시 지시했다.

### 렌즈1 (DNA/접근성) — **b > a > c**
핵심: b는 "막힌 지점이 없는 화면"이라는 자기 상황에 맞춰 밴드를 아예 두지 않은 선택(사유를 코드 주석에 명시)이 가장 정확한 적용. a는 선택개수파생 밴드(형태 d)를 교과서적으로 구현했으나, `confirmationDoneButton`("Start New Campaign")이 `minHeight`/`hitSlop` 없이 `space(2)`(8pt) 패딩 + 13pt 텍스트로 계산상 44pt 미달(세 후보 중 유일한 구체적 터치타깃 결함). c는 메커니즘은 깔끔하나 상시 노출 "확인 바"가 GENERATION.md §3이 승인한 5개 밴드 형태(a~e) 중 **어느 것에도 정확히 들어맞지 않는다** — 선택은 항상 기본값(`"starter"`)이 있어 "0에서 부재"(형태 d)가 될 수 없고, 막힌 지점도 없고(형태 a 아님), read-only 기록 화면도 아니다(형태 b 아님). 렌즈1은 이를 "승인되지 않은 6번째 기본형태"로 명시 지적 — 밴드가 실제로 일을 하긴 하지만(눌리면 진짜 확정 처리) 형태 적합성 면에서 가장 약함.

### 렌즈2 (모바일 완성도) — **c > b > a**
핵심: a는 **스테퍼·Apply·Start New Campaign·체크박스 행 전부**에 `({pressed}) => [...]` 눌림 피드백이 전혀 없음(세 후보 중 유일하게 전면적 결여). b·c는 둘 다 눌림 피드백 정상 구현. c는 모든 화면 수치를 `data.ts`와 대조해 전부 일치 확인(탭별 7.5%/4.0% 수수료, "Upgrade to unlock" 힌트가 Starter에서만 표시 등), `confirmedTierId`를 `selectedTierId`와 분리해 확정 후에도 계속 탭을 둘러볼 수 있게 한 설계를 긍정 평가. b는 768px에서 리스트-버튼 사이 빈 공간이 다소 미완성처럼 보이는 경미한 결점.

### 렌즈3 (화면유형 차별성) — **b > a > c**
핵심: **a vs r48/c를 소스 레벨에서 직접 대조해 자진신고를 독립 검증** — a는 "하나의 공유 스칼라 + 전체화면 1회성 커밋(되돌리기 없음)", r48/c는 "영속적 per-id 맵 + 프리셋칩 즉시 커밋 + 행별 실행취소"로 reachable-state 구조 자체가 다름을 확인(명명·스타일키 전혀 겹치지 않음) — 자진신고 타당. 다만 a의 +/- 스테퍼 위젯 자체는 `native/src/membership/MembershipTiersScreen.tsx`의 볼륨 다이얼과 동일한 위젯 모양이라 "화면 메커니즘은 신규, 그러나 구성요소 위젯 하나는 카탈로그 기존"이라는 단서를 붙임. b는 `r49/c`(체크리스트, per-row 버튼+3상태+리스트 유지)·`r48/b`(읽기전용 타임라인, advance 메커닉 없음)와 명확히 구분되는 가장 깨끗한 차별성("외부 버튼 1개가 고정 큐를 단조증가 카운터로 전진시키고, 완료 시 전체 콘텐츠가 터미널 요약으로 통째 교체"). c는 클론은 아니지만 "선택자가 하단 콘텐츠를 게이트하고 확인으로 끝난다"가 이 카탈로그의 가장 흔한 매크로 패턴(Membership의 훨씬 풍부한 버전 포함 4개 이상의 유사 탭/필터 화면 확인)이라 가장 좁은 차별성.

## 집계

렌즈1=b, 렌즈2=c, 렌즈3=b → **b가 1위 표 2개(렌즈1+렌즈3)로 2:1 다수결 승.** 완전 3파전 동률 아님(렌즈2가 b를 2위로 평가, 최하위가 아님 — tie-break 예외 불필요).

승자 b에 대해 어느 렌즈도 규칙 위반을 지적하지 않음 — **§3-1 정제 조치 불요**. (렌즈1이 지적한 a의 터치타깃 결함, 렌즈2가 지적한 a의 눌림피드백 결여는 전부 패자 a에 대한 것이며, a는 순수 판정 패배이지 게이트 탈락이 아니므로 재배정 큐 대상 아님.)

## 승자: candidate b — "Warehouse Intake Scan"

고정 6건 매물 매니페스트를 순서대로, 전역 단일 `Pressable`("Scan next package")을 반복해서 눌러 1씩 전진시키는 정수 카운터 하나가 전체 상태. 완료 시 스캔 UI(진행줄+리스트+버튼) 전체가 읽기전용 "Intake complete" 요약 화면으로 **통째 교체**(밴드가 아니라 화면 자체가 터미널 상태로 전환). 밴드가 아예 없는 것을 GENERATION.md §3이 승인한 형태 그대로("할 일이 없으면 자리를 비운다") 가장 정확하게 적용한 사례. 라이브 리전 컨테이너는 상시 마운트, 전환 문장에만 `alert`.

## 미확인 범위

3렌즈 공통: 각 후보의 "확정/완료" 상태 자체는 스크린샷으로 캡처되지 않음(스크린샷은 초기 상태만) — 소스 검증은 전부 완료했으나 렌더 확인은 초기 상태에 한함. App.tsx 앱 셸 배선, 실제 VoiceOver/TalkBack 디바이스 트레이스는 3렌즈 전원 미확인.
