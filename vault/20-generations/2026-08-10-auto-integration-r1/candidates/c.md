# c — 승인 전에 다 펼친 권한 명세서 (Tidemark × HubSpot)

**컨셉 1줄** — 연결 버튼 앞에 붙이는 "동의 화면의 사전 공개본": HubSpot이 넘기는 스코프 8개를 한 줄씩 펼쳐, 각 스코프가 없으면 죽는 기능·보관 기간·Super Admin 승인 여부·회수 경로까지 조작 없이 읽히게 두고, 스코프 스위치는 **자기에게 매인 기능만** 끈다.

## `integration` 타입이 무엇인가 (프로파일 0건 → 이 라운드의 정의 초안)

`integration`은 **이미 쓰는 도구와 이 제품을 연결했을 때 무엇이 어떻게 흐르는지 보고, 연결을 시작하는** 단일 연동 화면이다.

- `catalog`와의 분기: 카탈로그는 **고르게** 한다(N개 나열·필터·검색). integration은 **하나가 실제로 무엇을 하는지** 보인다 — 목록이 아니라 계약서다.
- `developers`와의 분기: 그쪽 독자는 API를 직접 호출한다. 이쪽 독자는 **코드를 쓰지 않고 연결을 승인하는 사람**(RevOps 리드 + 그를 막아서는 보안 검토자)이다.
- 이 타입의 성패는 "멋진 로고 두 개와 화살표"가 아니라 **거래 조건이 얼마나 빨리 읽히는가**다. 핵심 증명 = *무엇을 주고(스코프) 무엇을 받는가(기능)*. 이 페이지는 그 둘을 **같은 행에 물리적으로 붙여** 증명한다.

## 구성

1. 상단 밴드 3장 — `Leaves HubSpot (read 5)` / `Tidemark writes back (3)` / `Never requested (5, 취소선 + 사유)`. **조작 0에서 거래 전모가 읽힌다.** "요청하지 않는 것"을 동급 카드로 둔 것이 보안 검토의 첫 질문을 선점한다.
2. 카운터 4칸 — 8 scopes / 13 months / 3 Super Admin / 60s revoke (`tabular-nums`).
3. **The grant sheet** — 스코프 8행. 각 행: 스위치 + 스코프명(mono) + 정확히 무엇을 만지는지 1문장 + Read/Write(아이콘+단어) + 승인 주체 + **매인 기능 칩** + 보관 기간. 표가 아니라 `ul` + `md:grid-cols-[...]`로 짜서 데스크톱 가로 스크롤·모바일 클리핑을 원천 제거.
4. 기능 카드 8장 — 스코프를 끄면 **그 스코프에 매인 카드만** 취소선 + `Off — needs crm.objects.deals.read`.
5. **Where the data actually sits** — Stored / Passes through only / Never collected 3탭(국소).
6. Taking it back — 60초·24시간·30일 3단 회수.
7. CTA — "HubSpot 동의 화면에 여기 없는 스코프가 뜨면 취소하고 신고하라"(검증 가능한 약속).

**인터랙션 4종** — ① 스코프별 grant 스위치(국소 의존성 소거 + `aria-live` 카운터) ② 행별 실제 필드 공개(`aria-expanded`) ③ 현재 선택을 보안 검토용 텍스트로 클립보드 복사 ④ 데이터 잔류 3탭. 전부 `'use client'` 실동작·결정론·`motion-reduce:transition-none`.

## 브리프에 없던 것

**① "요청하지 않는 스코프"가 요청하는 스코프만큼의 지면을 가져야 한다.**
브리프는 "요청하는 스코프를 하나하나 펼치라"고만 한다. 그런데 보안 검토자가 실제로 먼저 묻는 것은 *무엇을 안 가져가는가*다 — 긍정 목록은 아무리 길어도 "그럼 첨부파일은? 견적서는?"을 못 막는다. `crm.export`·`files`·`tickets`를 **취소선 + 거절 사유**로 상단 3분의 1에 두자 페이지의 신뢰 곡선이 바뀌었다. 코어에는 "색만으로 의미 전달 금지"는 있어도 **"부재를 명시적으로 렌더하라"**는 규칙이 없다. `integration`·`paywall`·`profile`처럼 **약속이 상품인 타입**에 공통으로 필요한 항목으로 보인다.

**② 스코프 표에 필요한 열은 5개인데, `page-brief-core` §4의 `table-fixed` + % 배분은 그 5개를 390px에서 못 버틴다.**
스코프명(mono·30자 이상 비줄바꿈)·설명 문장·방향·기능 칩·보관 기간을 한 표에 넣으면 데스크톱은 되지만 모바일에서 `table` 셀이 최소폭을 못 내려간다. 답은 "가로 스크롤 허용"이 아니라 **표를 포기하는 것**이었다 — `ul` + `md:grid-cols-[6rem_1.45fr_7rem_1fr_8.5rem]`, 모바일에서는 라벨 붙은 스택. 코어 §4는 "표를 쓰면 이렇게 하라"만 말하고 **"열이 5개를 넘으면 표를 쓰지 마라"**는 임계를 말하지 않는다. `caption`/`scope`를 지키려다 오버플로를 만드는 후보가 반복해서 나온 이유가 여기 있다고 본다.

**③ "국소 조작" 요구는 데이터 모델에 선행 조건을 건다 — 스코프↔기능이 N:M이어야 한다.**
브리프는 "스코프 하나를 끄면 그것에 매인 기능만 죽게"라고 인터랙션 층위에서 금지선을 긋는다. 그런데 스코프와 기능이 1:1이면 이 조작은 **켜고 끄기의 나열**일 뿐 아무것도 증명하지 못한다. 실제로 설득력이 생긴 지점은 `Pipeline forecast`가 `deals.read` **와** `owners.read` 둘 다를 요구하고, `deals.read`가 3개 기능을 동시에 지탱하는 **비대칭**이 보일 때였다 — "이 하나가 이렇게 많이 걸려 있다"가 곧 스코프의 정당화다. 즉 국소성은 인터랙션 규칙이 아니라 **데이터 설계 규칙**이다: `requires: string[]`이고, 최소 한 개 기능은 2개 이상을 요구해야 한다. 프로파일에 넣는다면 "국소 조작" 항목이 아니라 "의존 그래프" 항목으로 써야 한다.
