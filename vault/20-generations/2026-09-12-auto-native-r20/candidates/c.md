# Candidate c — Saved Filter Builder

`native/src/evolve/r20/c/SavedFilterBuilderScreen.tsx` + `native/src/evolve/r20/c/data.ts`

## Concept

A screen for assembling a multi-facet search filter — category, price band, a multi-select set of condition chips, a distance radius, and a sort preference — with a live, deterministic match-count estimate that recalculates from a fixed lookup table as facets change, plus a tiny fixed "new this week" sample count (never a scrollable results list). The user can name the combination and flip on "Notify me of new matches" to save it as a recurring alert rather than a one-off search. The screen is deliberately upstream of both `watchlist` (which tracks already-saved individual items) and `match` (which shows a list of AI-generated match results): this screen only ever produces a count and a set of criteria, never a list of items.

## 브리프에 없던 것

1. **Price range input shape.** ① The brief says "price range (min/max)" without specifying free-text/slider vs. discrete bands. ② I decided on five fixed price bands (Any / Under ₩50,000 / ₩50,000–₩150,000 / ₩150,000–₩300,000 / ₩300,000+) rather than two numeric min/max inputs. ③ The determinism rule requires the count preview to come from "a small fixed lookup table … keyed by facet combination." A free-numeric min/max pair has effectively infinite combinations, which is incompatible with a finite fixed table; discrete bands keep the table small, finite, and honestly "looked up" rather than reverse-engineered from a formula disguised as a table.

2. **How condition multi-select interacts with the count table.** ① The brief doesn't say whether the count table should be keyed by every possible subset of the 4 condition chips (16 subsets) or something coarser. ② I keyed the primary table by (category × price band × radius) — 175 fixed entries — and applied a separate small fixed multiplier keyed only by *how many* condition chips are selected (0–4), not which ones. ③ Keying by exact subset would require 16× more table rows for a distinction (which specific conditions, not how many) that a user skimming an estimate wouldn't notice; the count-based multiplier stays a real fixed lookup table while keeping the file readable.

3. **Whether naming the search is mandatory to save.** ① The brief says "User names the filter" but doesn't say whether an empty name should block saving. ② I made the name optional — saving with an empty name falls back to the label "Untitled search" — and gated the Save control purely on the "at least one facet is set" threshold the brief explicitly calls out. ③ The brief's own accessibility section frames the actionability transition specifically as the zero-facet → one-facet crossing; conflating that with a second, unrelated text-validation condition would blur the one live-region transition the spec asks for into two different reasons, weakening it for screen-reader users.

4. **Distance unit and radius steps.** ① Not specified. ② Chose kilometers with four fixed steps (5/10/25/50 km) plus "Any distance." ③ Matches the ₩-won pricing already implying a Korean-market context, and a small fixed step set (rather than a continuous slider) keeps the radius facet compatible with the fixed-lookup-table determinism requirement, same reasoning as point 1.

5. **Bottom control placement (no fixed band).** ① The brief flags this as an open decision and points at GENERATION.md §3's explicit allowance for no band at all. ② I chose no fixed bottom band — Save lives inline at the end of the scrollable facet list, right next to the one live-region sentence stating why it is or isn't enabled yet. ③ The screen's gate is a single continuous threshold, not an itemized checklist (rules out the blocked-workflow form used by verification/disputes/authentication/condition/pickup and won the last three native rounds), not a completed read-only record (rules out the always-on action bar form), and not a selection-count-over-a-list-of-items bar (rules out relist's form) — none of the three catalogued band forms fit, and forcing one on to "look complete" would be the "decorative disabled button" anti-pattern §3 warns against.

6. **"New this week" sample stat.** ① The brief allows, but doesn't require, "at most a tiny fixed sample count" as a hint of what matches. ② Added one small fixed number per category (1–9) shown next to the main estimate, sourced from its own tiny lookup table, never a list of items or brands. ③ Gives the preview a touch of texture beyond a bare integer without drifting toward `match`'s territory of listing actual matched items.
