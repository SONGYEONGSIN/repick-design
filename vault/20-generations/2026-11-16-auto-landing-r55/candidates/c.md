# Candidate c — Meetpoint

Meetpoint is a resale marketplace landing page built around a single idea: you should know whether
your offer has a shot before you send it. The hero headline — "Know your gap before you send an
offer." — sits beside the Offer vs. Ask Negotiator, a dual-handle drag control on one shared $0–$800
price axis. "Your offer" and "Seller's minimum" are two independently draggable handles on the *same*
bar (not two separate sliders); the band between them visually is the gap. Moving either handle live-
recomputes a signed dollar gap, a gap percentage, and a real threshold-derived outcome label ("Gap too
wide" / "Likely to be accepted" / "At or above ask"), and the hero's own listing card (a Pentax film
camera) restates the live ask as its asking price and recomputes its discount percentage off the same
number — so the device's state is woven through the hero's product-preview proof, not just shown in
isolation. The "Value, three ways" section holds the offer fixed and swaps only the assumed seller
posture (firm / open / motivated) across three preset cards, each computed through the exact same
`computeNegotiation` function the live handles use, with a "Try this seller" button that pushes that
preset back into the shared state so the hero negotiator updates to match. The closing CTA headline and
body sentence are both generated by `outcomeSummary(result)` on the live `offer`/`ask` state — there is
no hardcoded "Great deal!" string anywhere; every textual restatement of the gap, in the hero chrome,
the three seller cards, and the closing section, calls the same two pure functions
(`computeNegotiation`, `outcomeSummary`) on whatever the current handles say. Visually the page is a
near-monochrome dark editorial layout (Pretendard-only, no display face) with a single vivid orange
accent used sparingly for the eyebrow, the live gap stat, icons, borders, and the two CTA fills — never
for the body copy, which stays off-white gray for readability and near-monochrome discipline.

## Brief gaps

1. **What I decided**: the exact accent hex. **Decision**: `#FF7A33` (a vivid red-leaning orange, hue
   ≈24°), not the default `#6E56CF`. **Why**: assigned hue is "orange," with an instruction to avoid
   this round's most-saturated catalog colors (`amber`, `teal`). `#FF7A33` sits clearly outside amber's
   yellow-orange band (~38–45°) and far from teal (~180°), and is vivid/saturated enough to read as a
   confident "orange" rather than a muddy brown. Picked by hand-tuning RGB until the hue landed in the
   20–25° range and the resulting luminance cleared AA at body-text size against the dark bg (see
   contrast math below) — arbitrary within that constraint, not sourced from a named palette.

2. **What I decided**: full contrast math for the chosen accent, both roles (white-on-fill AND
   dark-ink-on-fill), as the brief requires whenever the hue is changed from the default. **Decision /
   math** (sRGB → linear → WCAG relative luminance, `contrast = (Lmax+0.05)/(Lmin+0.05)`):
   - `L(#0B0B0F)` bg/ink = 0.00345; `L(#FF7A33)` accent = 0.35419 (R=1.0 linear, G≈0.19463 linear,
     B≈0.03310 linear); `L(#FFFFFF)` white = 1.0.
   - **Accent vs bg**: (0.35419+0.05)/(0.00345+0.05) = **7.56:1** — clears 4.5:1 body-text AA at any
     size (the default purple's worked example only clears the 3:1 large-text floor at this step), so
     one accent hex is reused for text/icons/borders/fills without needing a separate lighter tint.
   - **White text ON the `#FF7A33` fill**: (1.0+0.05)/(0.35419+0.05) = **2.60:1** — fails even the
     large-text 3:1 floor. White is never used on an accent-filled surface on this route.
   - **Dark ink (`#0B0B0F`) text ON the `#FF7A33` fill**: (0.35419+0.05)/(0.00345+0.05) = **7.56:1** —
     clears body AA comfortably. Every accent-filled control (both CTA buttons, the "likely"/"at or
     above ask" outcome chip) uses dark-ink text, never white.
   - **Why this is the opposite of the brief's default worked example**: `#6E56CF` is a mid-luminance
     purple where white reads easily on the fill and dark ink is the one that only clears large text.
     `#FF7A33` is bright enough (high R channel) that the relationship inverts — white fails at any
     size, ink passes at any size. This is an empirical result of the chosen hue, not an assumption
     carried over from the default, which is why I calculated it explicitly rather than reusing the
     brief's example pairing. Reference: `tokens.ts` lines 1–45 hold the full derivation, including the
     muted (`#A1A1AA`, 7.67:1) and body-copy (`#C7C7CF`, 11.68:1 on bg / 10.81:1 on panel) grays.

3. **What I decided**: body-column character-count arithmetic, per the brief's 0.44em/char rule (never
   `ch`). **Decision / math**:
   - Hero subhead, 18px: 0.44×18 = 7.92px/char → 70 chars ≈ 554px, 75-char ceiling ≈ 594px. Container
     used: 540px → 540/7.92 = **68.2 chars/line** (under target, well under ceiling).
   - Section body copy, 16px: 0.44×16 = 7.04px/char → 70 chars ≈ 493px, ceiling ≈ 528px. Container
     used: 480px → 480/7.04 = **68.2 chars/line**.
   - Testimonial quotes, 14px: 0.44×14 = 6.16px/char → 70 chars ≈ 431px, ceiling ≈ 462px. Container
     used: 420px → 420/6.16 = **68.2 chars/line**.
   - All three ship as literal pixel `max-w-[...]` values (`tokens.ts`: `PROSE_WIDTH_HERO`/`_BODY`/
     `_CARD`), never `max-w-[70ch]`, since `ch` tracks the digit "0"'s advance (~35% wider than
     Pretendard's mixed-script average) and would silently over-budget the line.
   - **Why 68.2 and not exactly 70**: picking round 540/480/420px container widths landed consistently
     a hair under the 70-char target with comfortable ceiling headroom, which felt more robust against
     font-metric variance than chasing the ceiling exactly — arbitrary choice of round container
     numbers, not derived from a specific further constraint.

4. **What I decided**: the device's price axis bounds and threshold. **Decision**: a fixed $0–$800
   shared axis, default state offer=$420 / ask=$620 (gap $200, 32% of ask → "too wide"), and an
   outcome threshold of gap ≤ 0% → "at or above ask", 0–8% of ask → "likely to be accepted", >8% →
   "gap too wide". **Why**: arbitrary but chosen so the default state starts in the least-favorable
   outcome (persuasive — there's visible room to improve by dragging), and 8% is a round, plausible
   "close enough to likely land" threshold for a secondhand marketplace; the brief requires a real
   threshold function of both handles rather than hardcoded strings, which this is (`model.ts`,
   `computeNegotiation`) — the specific percentage itself isn't sourced from any external convention.

5. **What I decided**: no `--font-display-*` variable is set anywhere (Pretendard-only). **Decision**:
   per my assignment ("Display face: none"), this is explicitly used as the sanctioned choice rather
   than a fallback — confirmed no display font var appears in any file in this route. **Why**: direct
   instruction in the brief's per-candidate assignment, not an invention on my part, but noted here
   since it's a deviation from most of the catalog, which does pick a display face.

6. **What I decided**: brand name "Meetpoint" and the specific listing categories (camera, mid-century
   sideboard, commuter bike, dive watch). **Decision**: invented, English-only names consistent with
   the page-brief-repo's English-only binding. **Why**: the brief leaves product/brand naming open;
   chosen to read as a believable general secondhand marketplace rather than reusing any real brand or
   the literal Korean "repick" name, and picked four visually distinct categories so the product-preview
   grid reads as genuinely varied rather than four variations on one object type.
