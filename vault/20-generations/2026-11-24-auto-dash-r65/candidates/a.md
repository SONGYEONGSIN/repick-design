# Candidate a — Tracewave

Tracewave is an APM / distributed-tracing console a backend team at "Northwind Commerce" uses to watch service health and trace slow requests; the layout is a genuine 3-pane market skeleton — a 296px left rail listing six services (each row carrying its own compact request-rate sparkline and a healthy/degraded/down status), a flex-1 center pane dominated by one multi-series p50/p95/p99 latency chart with a 6h/24h/7d segmented toggle and a keyboard-and-mouse crosshair that reports exact values as live text, and an always-visible right-hand table of that service's recent slow traces, sortable by duration via real `aria-sort`; selecting a service in the rail is the one fan-out wired to exactly the chart and the trace table, nothing else. Theme is zinc-950/900 dark with white/10 borders and no glow/grain; the single accent is violet-400/300 used for the dominant latency line, pressed toggle/pill states and focus rings, verified by hand against the dark surfaces (zinc-950/900) at 6.5:1+ for every colored text and non-text UI use. Per this round's assignment the display-font whitelist was deliberately skipped — the wordmark, hero numbers and every heading stay on `--font-sans` (Pretendard) throughout, a conscious restraint choice rather than an oversight.

## 브리프에 없던 것
- ① The brief left the chart's x-axis units unspecified for "6h/24h/7d" while only giving hourly-ish example labels. ② I generated one canonical 24-hourly-point array per service and derive all three views from slices/aggregations of that *same* array (6h = last 6 points, 24h = all 24, 7d = 7 chunked daily aggregates via `reduce`), renaming the toggle to 6h/24h/7d instead of 1h/24h/7d. ③ Arbitrary, but made specifically to guarantee every displayed number is honestly traceable to one source array (the catalog's repeated "summary number disagrees with detail rows" failure mode), rather than fabricating a separate finer-grained 1h dataset.
- ① No spec for what the primary action button ("New monitor") or the nav items outside Overview (Traces/Alerts/Settings) should actually do. ② Primary action opens a real 2-field modal that creates a monitor and shows a toast; the three non-Overview nav items switch to a minimal real stub panel with a working "Back to Overview" button. ③ Convention — this catalog's hard rule explicitly bans decorative/dead-looking interactive controls, so every chrome affordance needed real wiring rather than being left inert.
- ① Status semantics (healthy/degraded/amber/down) needed colors, but the round assigns a single violet accent family. ② Used standard semantic emerald-400/amber-400/rose-400 only for status dots/text/badges (never for brand/interactive accent, which stays strictly violet). ③ Convention — status color is informational semantics, not the page's "accent," and all three were hand-checked at 6.5:1+ contrast against zinc-950/900.
- ① The brief didn't specify how the always-visible third column should degrade on a 390px phone without becoming "a drawer over the center pane" (the explicitly forbidden pattern). ② Used a single responsive CSS grid (`grid-cols-1` → `lg:grid-cols-[300px_1fr_380px]`) so mobile simply stacks all three sections in normal document flow (rail → chart → trace table), with the whole page scrolling, while desktop gets fixed-height independently-scrolling columns. ③ Arbitrary engineering choice, made to satisfy the "real third column, not a drawer" anti-recurrence rule while still passing the 390px overflow sweep.
