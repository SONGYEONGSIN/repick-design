### A mobile hero-fold finding, found before ranking (bears on all three lenses)

All three candidates share near-identical Hero shells and an **identical** compact
`ListingCard` component (badge grid: Match / Condition / Seller / Discount). At this project's own
measurement standard — 390×900, the exact viewport `capture-shots.mjs` uses for its `390` frame —
the three diverge sharply in how much of that badge grid is actually visible without scrolling:

- **b** (`b-390.png`): all four badges' **labels and values** fully visible (Match 91%, Condition
  Grade A, Seller Verified, Discount 28% off).
- **a** (`a-390.png`): two of four badge **values** visible (Match 92%, Condition Grade A); the
  other two rows are cut to label-only (Seller, Discount) at the very bottom edge.
- **c** (`c-390.png`): **zero** of four badge values visible — the frame cuts off mid-way through
  rendering just the first badge's label ("MATCH"), nothing else.

Root cause, traced in source: the proof card markup is byte-identical across all three (same
compact 80px-thumbnail layout). What differs is each candidate's own compact **device**, which sits
directly above the proof card inside the same Hero column and competes for the same vertical
budget: **a**'s device is an SVG chart (`viewBox 0 0 600 200`, i.e. ~0.33× its own rendered width in
height); **b**'s is an SVG tree (`viewBox 0 0 600 260`, ~0.43×) plus two question-chip rows; **c**'s
is a real `next/image` at `aspect-ratio: 4/3` (0.75× its own width) — nearly double **a**'s device
height and still taller than **b**'s once **b**'s two button rows are added back, because an SVG
`viewBox` scales purely by the stated ratio while **c**'s photo claims a fixed, much taller aspect
regardless of content. This is not a hard-gate violation (sweep's overflow checks and Lighthouse's
`target-size`/`color-contrast` don't measure "is badge N visible in the first 900px"), so it did
not surface in §3 — it is exactly the class of defect `design-principles` §Landing 구조 기본형 names
("증명 카드가 히어로 다음 섹션이 아니라 히어로 컴포넌트 자체 안에 있는가") extended one level: being
*structurally* inside the Hero component is necessary but, at mobile widths, not sufficient if a
sibling element inside that same component consumes enough of the fold's height first.

This is real and **differentiates** the three (it is not a shared, non-enforceable violation under
`curation-criteria` Q13 — the three ARE different here), so it legitimately informs the lenses
below rather than being set aside.

### Lens 2 — commercial SaaS polish (Linear / Stripe / Vercel)

Ranking: **a > b > c**.

**a**'s restraint is the most commercially confident of the three: a single accent, a dark
near-monochrome canvas, and a milestone table (`ValueSplit`) that states nine concrete day/price
pairs under both certificate states — the specificity reads like a real fintech projection tool
(a Stripe-revenue-chart register of trust), not a marketing illustration. **b**'s tree is the most
visually distinctive artifact of the three and the "Different device"/"Change condition" actions
give it a genuine multi-step-product feel (closer to a real triage flow a support team would
ship), but it is also the busiest-looking of the three (more simultaneous visual elements: 13
nodes, 12 edges, two button groups, a verdict row) — polished, but closer to an explainer diagram
than a > single, confident device. **c**'s concept (flagging *widens* the range) is the most
intellectually elegant of the three, and the seller/buyer reframing toggle is a nice, cheap,
genuine touch — but in the renders actually in hand this round, the self-inspection photo fails to
load in all captures (an accepted, disclosed sandbox limitation, not a code defect — `next/image`,
`alt`, and the fixed `aspect-ratio`+background-color reservation are all present and correct per
`page-brief-core` §3) and, because **c** chose a large 4:3 photo as its primary device visual
rather than a small thumbnail, that placeholder rectangle reads as far more visually prominent and
unfinished in this round's actual screenshots than **a**'s or **b**'s small 80px thumbnail
placeholders. Commercial-polish judgment is about the artifact in front of the viewer, not only the
code that produced it, so this counts against **c** here even though it is explicitly not a rule
violation.

### Lens 3 — archetype/structural differentiation (this catalogue)

Ranking: **b > a > c** (close).

Per `curation-criteria` Q6 ("무엇이 값을 바꾸는가 × 무엇이 값을 보여주는가" combination table):
**b** is novel on **both** axes simultaneously — no prior candidate has a second discrete-select
question whose *option set itself* depends on the first answer (every prior stepper/toggle in this
catalogue asks a fixed question shape repeatedly, or toggles independent booleans), and no prior
candidate renders its device as a decision-tree diagram. **a** is novel mainly on the output axis —
plotting the control's own dimension (time) as the chart's literal x-axis, with the marker
continuously riding that same axis, is new (distinct from the static gauge at `/v8`, the
re-normalizing radial gauge at `/v21`, and the 2D-scatter-from-two-sliders at `/v24`, none of which
make the slider's own value the chart's axis) — but the input mechanism itself (one range slider) is
this catalogue's single most common device. **c** is novel mainly on *semantic direction* — raising
a concern *widening* the estimate rather than narrowing it is a genuine, checkable inversion of
`/v16`'s "confirming narrows the range," and distinct from `/v23`'s bundle-builder (which only ever
narrows toward a discount as more items are added) — but the input mechanism (a fixed grid of
toggle chips) closely resembles this catalogue's existing fixed-category-toggle pattern (`/v20`
Assay's pipeline, `r58/b`'s 3-boolean lookup), so the novelty sits entirely on the output side.
**b**'s double-axis novelty edges both.

> card than a photo-based device claiming a fixed `aspect-ratio` such as 4/3 (0.75× its width).

> across all three compared candidates).

is explicitly NOT claimed as a reproduction of) `auto-landing-r57`'s delta about a product card's
own image orientation consuming mobile fold budget — that prior delta was about the *proof card's*
image; this one is about the *device's* image, a related but distinct element competing for the
same budget. Per the skill's reproduction-claim-verification requirement, I am not asserting these
are "the same defect," so no L1→L2 promotion is claimed on reproduction grounds here.
