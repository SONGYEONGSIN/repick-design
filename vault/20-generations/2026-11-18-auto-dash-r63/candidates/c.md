# Candidate c — Weir

Weir is an API gateway and rate-limit/quota console for developers running a payments-style API: a two-region master-detail (never three) pairs a sortable, filterable key rail — seven API keys, each with a compact mini-bar of its own intraday request shape — against a main pane dominated by an hour-of-day × endpoint request-volume heatmap for whichever key is pinned. A Key overview card above the heatmap (requests today, quota remaining, peak hour, endpoints in scope, and a quota bar) and the heatmap/table below it all read the exact same per-key hourly request matrix, so nothing on the page is a hand-placed duplicate of a number the drill-down also shows. One key (Checkout, pinned by default) runs at 117%+ of its daily quota, rendered with an explicit ceiling tick, a hatched overflow segment past it, and an "N.NN× over" label rather than a bar that silently caps at 100%. Five-plus real interactions: rail search + status filter + usage/name sort; a pinned-key selection that updates the overview card and the heatmap/table; a keyboard-reachable (arrow-key roving tabindex) crosshair hover/focus inspector on the heatmap, reporting through one shared `aria-live` readout rather than per-cell tooltips; a Heatmap/Table view toggle with a full accessible table fallback (6 four-hour buckets, `table-fixed` + `colgroup`); and a ⌘K command palette. Light theme only, pure white/zinc-50 surfaces, emerald-700/600 as the single accent, Pretendard body copy with `--font-display-wide` reserved for the "Weir" wordmark alone.

## 브리프에 없던 것

**① Brand and domain invention**
① The brief specified the domain (API gateway / rate-limit console) and the layout but not a product name, and the catalog's existing-work list ruled out every water/flow/ledger-adjacent name already in use (Portlane, Ledgerline, Ledgerwell, Trussline, Fluxgate, Conduit, Openhour…).
② Named it **Weir** — a small dam that regulates a river's flow — which maps directly onto "rate limiting" without reusing any existing name, and is short enough to work as a one-word, latin-only display wordmark.
③ A literal metaphor for the product's job (controlling throughput) reads as more deliberate than an abstract or compound name, and a one-syllable word sets cleanly in a single display weight without needing letter-spacing tricks to look intentional.

**② Heatmap row dimension and the two independent selection states**
① The brief allowed hour × day-of-week *or* hour × endpoint for the heatmap's y-axis, and separately asked for two selection states that never touch each other, verifiable from the code.
② Picked endpoint rows (not day-of-week), and made the heatmap's own hovered-cell state a `useState` declared *inside* `Heatmap.tsx` itself — never lifted to the client orchestrator, never passed as a prop in either direction — while `pinnedKeyId` lives only in `WeirClient.tsx` and is passed down as data, never read back. Switching the pinned key remounts `<Heatmap key={pinnedKey.id} .../>` instead of adding an effect to reconcile stale row indices across keys with different endpoint counts.
③ Endpoint rows tie the dominant chart to the domain (which endpoints a key calls, not which weekday) and keeping the hover state local to one file's closure is a stronger, more legible proof of independence than two state variables sitting side by side in the same component with a comment promising not to cross — a reviewer can see the boundary by reading one function's scope.

**③ Over-ceiling quota encoding uses one shared scale, not a per-row autoscale**
① The brief requires an explicit multiplier/escalation treatment for any quota metric that can exceed 100%, and a naive per-row bar (fill width = min(pct, 100)%) would make every key's bar look visually identical to "full" once it crosses the ceiling.
② `QuotaBar` fixes every bar to the same 0–120% scale, so the 100% ceiling tick lands at the same horizontal position on every row; an over-quota key gets a diagonally-hatched overflow segment past that tick plus an explicit `"{(pct/100).toFixed(2)}× over"` label, computed from the same `pct` the bar renders, never a separate hand-typed string.
③ A shared scale makes the exceeded key's bar visibly different in *shape*, not just in a color swap at the exact same fill length as every "healthy" bar — which is what a naively-capped bar would produce, defeating the whole point of flagging it.

**④ Table-fallback granularity deliberately coarser than the heatmap's own resolution**
① The catalog rule mandates a real `<table>` fallback with every row/column labeled and valued for any heatmap whose cells aren't all individually labeled, and separately bans a horizontal scrollbar on a desktop table, only allowing a `min-w` scroll escape for mobile.
② `UsageTable` rolls the same 24-hour matrix into six 4-hour buckets (`BUCKETS`/`bucketTotal`, defined once in `data.ts` and reused by the rail's mini-bar) instead of rendering all 24 hourly columns; the heatmap itself keeps full hourly resolution, since its cells don't need to fit inside fixed pixel columns the way table cells do.
③ A 25-column (1 label + 24 hour) `table-fixed` table has no honest column-width budget at ~650px of main-pane width at 1280px — numbers like "1,204" need real room — so matching the heatmap's resolution exactly in the fallback would force either a forbidden desktop scrollbar or illegibly narrow cells; coarsening the *table's* grouping (never the underlying data) resolves that without touching the chart.
