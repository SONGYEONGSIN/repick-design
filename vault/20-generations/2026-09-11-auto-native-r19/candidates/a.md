# auto-native-r19 · candidate a — Shipment Pickup (Shipping Label & Pickup Scheduling)

One-line concept: after a sale is confirmed for an item the seller is shipping, a linear three-stage screen — confirm package weight/dimensions (drives a real billable-weight calculation), choose a carrier/service tier (rate table keyed off weight bracket), then schedule a carrier pickup window and get a label reference — using the blocked-workflow band form because scheduling genuinely cannot happen until both measurements are confirmed and a carrier is chosen.

## Files
- `native/src/evolve/r19/a/ShipmentPickupScreen.tsx` — default-exportable screen component.
- `native/src/evolve/r19/a/data.ts` — deterministic dummy data: sale record, weight/dimension step ranges, the weight-bracket table, the per-carrier/tier rate table (cents, parallel array to the brackets), pickup windows (each tagged to the carrier whose local route covers it), and a pure `buildLabelRef` function.

## Mechanics (why this isn't decorative)
- Billable weight = `max(actualWeight, dimensionalWeight)`, where `dimensionalWeight = (L×W×H) / 139` (139 is the standard inches/pounds DIM divisor real carriers use). This picks a bracket from `WEIGHT_BRACKETS`.
- Each `ServiceOption` in `SERVICE_OPTIONS` carries a `ratesCents` array parallel to the bracket list — a real rate table, not a flat number. The displayed price for every carrier row is `ratesCents[bracketIndex]`, so it changes live as the seller adjusts weight/dimensions (before they've locked measurements in, rows show `—` rather than a price, since showing a price against unconfirmed numbers would misrepresent the calculation).
- Carrier rows are visually and functionally locked until measurements are confirmed; pickup-window rows are locked until a carrier is chosen, and the window list itself is filtered to `PICKUP_WINDOWS` whose `carrierName` matches the chosen carrier (different couriers cover different routes/times) — changing carrier after a window was picked clears the window if it's no longer valid for the new carrier.
- On successful scheduling, `buildLabelRef(serviceId, windowId)` deterministically composes a label reference from the fixed order number + a per-service code + the window id (e.g. `RPX-48221-GLS-W1`) — no `Math.random`/`Date.now`.

## Band form used: (1) blocked-workflow state machine
Chosen because the screen has a genuine two-part gate before the terminal action ("cannot schedule pickup until weight/dimensions confirmed AND a carrier is chosen"), exactly the shape band-form (1) is for.
- The bottom `dock` (my own naming — not reusing `band`/`bandBlocked` from prior screens) states a real sentence naming the first unresolved requirement, e.g. "Confirm the package weight and dimensions — carrier rates are calculated from it" or "Choose a carrier and service tier to lock in a price" or "Pick a pickup window before booking the carrier".
- Tapping the dock while blocked calls `jumpToStage`, a real `scrollToIndex` call against the section `FlatList` (with an `onScrollToIndexFailed` fallback), landing on the exact unresolved step card, which also gets a highlighted border (`cardActiveBlock`).
- Exactly one live region on the whole screen: the `dock` container carries `accessibilityLiveRegion="polite"`, and the headline `Text` inside whichever state is active (`dockBlockedTitle` / `dockReadyTitle` / `dockDoneTitle`) carries `accessibilityRole="alert"`, so every forward-progress transition (locked → ready → booked) announces once, from one place.
- Once both gates clear, the same control becomes the real "Schedule Pickup" action (not a placeholder) — pressing it computes and stores the label reference and flips to a static, non-pressable confirmation state (so there's no dangling `accessibilityHint` promising an action a no-op button doesn't perform).

## Brief gaps — what I had to invent/decide
- **Which quantities are "confirmed weight/dimensions"**: the brief said confirm weight/dimensions but not the input mechanism. I chose stepper buttons (`+`/`−`, 0.5 lb / 1 in increments) over a numeric `TextInput`, for touch-target reliability and determinism (arbitrary choice, precedent: other evolve screens favor stepper/chip controls over free text for anything that feeds a downstream calculation, e.g. r18c ConditionAssessmentScreen's discrete inputs).
- **The actual rate formula**: the brief said "a real, non-decorative calculation, e.g. a rate table or formula keyed off weight bracket + carrier" and left the specifics open. I invented the billable-weight-via-DIM-divisor mechanic (a real, well-known shipping-industry formula: `max(actual, L×W×H/139)`) crossed with a 5-bracket × 5-service rate table, because it's the actual thing "weight/dimensions affecting cost" would mean in production and gives the "why is this blocked" gate genuine substance (you can't show a real price before the inputs it depends on are settled).
- **Whether "confirm weight/dimensions" needs an explicit confirm action vs. just having default values**: I added an explicit "Confirm weight & dimensions" button that must be pressed (and is invalidated back to unconfirmed the instant any stepper is touched afterward) rather than treating the presence of default values as automatically "confirmed" — otherwise the blocked-workflow gate would be trivially already-satisfied at first render, which would contradict the brief's instruction to use band form (1) meaningfully.
- **Whether pickup windows are carrier-specific**: not stated in the brief. I made `PICKUP_WINDOWS` carrier-tagged (different couriers cover different date/time slots) rather than one generic list, so that choosing a carrier has a visible, real downstream effect on step 3, not just a cosmetic one.
- **What "generate a label reference" means without a real shipping API**: I implemented it as a pure deterministic string-composition function (`buildLabelRef`) rather than a fetch/mutation, consistent with the determinism rule (no network, no random IDs) — precedent: other evolve screens (e.g. DisputeCenterScreen's `NEW_CASE_ID`) also use fixed/derived identifiers rather than simulating a backend call.
- **Screen/file naming**: the brief didn't name the component. I named it `ShipmentPickupScreen` (file `ShipmentPickupScreen.tsx`) and deliberately used original state/style-key vocabulary (`blocker`, `dock`, `dockBlocked`/`dockReady`/`dockDone`, `jumpToStage`, `measureLocked`) rather than the `bandBlocked`/`bandBlockedTitle`/"Tap to review" wording used in DisputeCenterScreen and SellerVerificationScreen, per the DNA note about not reusing blocked-workflow vocabulary verbatim.
- **Structure (accordion vs. linear)**: existing blocked-workflow screens (disputes, seller verification) use an expand/collapse accordion card list. I chose a linear, always-expanded three-step form instead (steps 2 and 3 are visually locked/dimmed rather than hidden behind a collapsed header) since that reads more like a physical prep checklist and further differentiates the screen shape from prior art per the duplicate-avoidance note.
