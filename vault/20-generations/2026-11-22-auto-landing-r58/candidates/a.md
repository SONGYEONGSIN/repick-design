# Candidate A — Bulk Trade-In Tier Counter

**One line:** An unbounded item counter that crosses fixed bulk-tier thresholds, recomputing average payout, running total and tier badge from a single shared derivation — a cumulative, tier-crossing control rather than a continuous score or a flat lookup.

## Concept

Repick's bulk-resale pitch is "trade in by the box, not the item." The device is the **Bulk Trade-In Tier Counter**: a single +/- (and arrow-key) counter for "how many items are you trading in," starting at a non-trivial default of **6** (inside the Bulk Dealer tier). Crossing the fixed thresholds — 1–4 / 5–9 / 10+ — changes the named tier (Starter Trade / Bulk Dealer / Wholesale Partner), and that tier changes the average payout per item. One function, `deriveTradeIn(count)` in `lib.ts`, is the only place that:

1. computes per-item average payout from the tier table,
2. multiplies into a running total payout,
3. picks the tier name/badge,
4. writes the one-sentence summary ("Trading in 6 items puts you in the Bulk Dealer tier — $45 average payout per item, $270 total.").

Every place that number appears on the page — the hero counter card, the desktop-only progress-to-next-tier caption, and the Closing CTA — calls this same function against the same lifted `count` state (`Client.tsx`). There is no second control anywhere that can move the tier, the average, or the total.

## Structure

1. **Header** — slim wordmark + anchor link, kept under 60px to protect the mobile fold budget.
2. **Hero** (`Hero.tsx`) — oversized asymmetric headline (`clamp(2.1rem, 8.5vw, 4.5rem)`, mono display face), subhead, single CTA, the counter (`TradeInCounter.tsx`), and a no-photo proof `dl` (AI match %, condition grade, verified-seller, before/after retail price) — all literally inside Hero's render tree, in that document order, so the mobile single-column stack never separates or reorders them.
3. **Product preview** (`ProductPreview.tsx`) — category filter chips (All/Cameras/Footwear/Watches/Furniture) over a 4-card grid; each card has a fixed-aspect photo, a AI-match/condition/verified badge row *below* the image, and an expandable "Why this match" reasoning disclosure.
4. **Value, three ways** (`ValueSplit.tsx`) — three cards tying the device's mechanics (per-item pricing, verified buyers, bulk tiers) to commercial value.
5. **Social proof** (`SocialProof.tsx`) — three static testimonials with fixed-id Unsplash portraits.
6. **Closing CTA** (`ClosingCTA.tsx`) — cites the live `count`/`tier`/`avgPayout`/`totalPayout` from the same `result` object the hero counter produced, and links back to `#trade-in-counter` rather than to a disconnected, unfiltered section.

## Why this mechanism is a different topology

The catalog's existing devices are either continuous weighted sums (sliders/gauges feeding a score) or fixed small-enumeration steppers (discrete positions on a short, bounded scale). The Bulk Trade-In Tier Counter is neither:

- **Range is open-ended.** There's no maximum — the `+` button and `ArrowUp` key have no ceiling. A weighted-sum meter or a 4-position stepper both enumerate a small, fixed state space; this counter's reachable states are unbounded.
- **Output is tier-crossing, not continuous.** The badge and the per-item average don't glide — they snap at `threshold` boundaries (1, 5, 10) defined once in `TRADE_IN_TIERS`. The number you see (total payout) is continuous-looking, but the *rate* behind it is a step function of the same single input, which is the genuinely new wrinkle: one scalar input produces both a continuous output (total) and a discrete, named output (tier) from the same derivation.
- **It's cumulative/ordered, not a flat lookup.** Per the open-delta note on reachable-state richness: this isn't "pick 1 of N, get a canned row back." Every unit added or removed moves the *same* running total and can cross a tier boundary, and the desktop progress bar (`itemsToNextTier`, hidden below `sm` to protect the mobile fold) makes that distance-to-next-tier explicit — itself a derived value, not hand-typed.

## 브리프에 없던 것

1. **Accent hue and exact shade per use.** The brief assigns "green" but not which shade for which purpose. I computed WCAG contrast for every accent/background pairing rather than assuming the brief's violet-tuned "white on accent fill" guidance would transfer:
   - `green-500` (#22C55E) text/icon on bg `#0B0B0F`: **8.62:1** — safe for any text size directly on the page background.
   - `green-400` (#4ADE80) on bg: **11.27:1** — used for emphasis numbers (e.g. total payout) and links; comfortably exceeds the 4.5:1 tint target.
   - `green-300` (#86EFAC) on bg: **≈14:1** — reserved for the `focus-visible` outline color so keyboard focus is unmistakable against the dark page.
   - White text on `green-500` fill: **2.28:1** (fails even the 3:1 large-text floor). White on `green-600` fill: **3.30:1** (fails 4.5:1 for small text). White on `green-700` fill: **5.01:1** (passes). **Decision:** I deviated from the brief's "always use white on accent fill" example — that guidance holds for a mid-tone saturated accent like the DNA default violet, but green at Tailwind's 500/600 weight is unusually *light* (luminance ≈0.41), so white text on it under-performs. I use `green-700` (not `green-500`/`600`) as the only solid CTA-button fill, with white text (5.01:1), and reserve `green-500` fill for *small badge chips* with **dark ink** (`#0B0B0F`) text instead of white — dark-on-`green-500` measures the same 8.62:1 computed above (the ratio is direction-symmetric), which is the opposite pairing from the brief's worked example but is the one that actually passes for this hue/weight. I verified both directions rather than assuming either.
   - Non-text boundary check: `green-700` fill vs. page bg is **3.92:1**, clearing the 3:1 UI-component floor so the button reads as a distinct control at rest.
2. **Line-length math and container width.** Using the mandated 0.44em/glyph metric (not `ch`, not 0.5em): at a 15px body size, chars-per-line = container-px ÷ (0.44 × 15) = container-px ÷ 6.6. I standardized body/intro paragraphs on `max-w-md` (448px CSS, but the Hero subhead's *actual* rendered width is capped tighter by the 390px viewport minus 16px side padding, i.e. ≈358px) → 358 ÷ 6.6 ≈ **54 chars/line**, safely under the 70–75 target band. I rewrote the Hero subhead to ~99 total characters specifically so it wraps to exactly two lines at that width (99 ÷ 54 ≈ 1.8 lines) rather than spilling into a third line and blowing the mobile hero-fold budget. The wider `max-w-md` intro paragraphs in Product Preview/Closing CTA (448px, but at ≥640px viewports where they actually render at that width) land at 448 ÷ 6.6 ≈ **68 chars/line** — inside the target band. I had originally reached for `max-w-lg` (512px) for those two paragraphs, computed it at ≈77.6 chars/line at 15px, caught that it broke the <75 ceiling, and dropped to `max-w-md`.
3. **Non-trivial default value for the counter.** The brief says "like 3, not 0" but doesn't fix a number. I picked **6** — inside the middle "Bulk Dealer" tier, not sitting on a threshold edge — so the very first paint already shows a named tier (not the entry-level "Starter Trade," which would under-sell the bulk angle) with headroom to demonstrate both directions (down into Starter Trade, up into Wholesale Partner). `DEFAULT_ITEM_COUNT = 6` is the single constant the Reset control also targets, so every reset reproduces exactly this state.
4. **Tier thresholds and payout schedule.** The brief specifies the *shape* (1–4 / 5–9 / 10+) as an example, not the dollar figures. I invented $38 / $45 / $52 average-per-item at each tier — a modest, round, monotonically increasing schedule that makes the "bulk pays more per item" story legible without claiming false precision.
5. **Keyboard model for an unbounded counter.** ARIA doesn't have a native unbounded-range widget; I used `role="spinbutton"` with `aria-valuemin` set but **no `aria-valuemax`** (per the ARIA spec, omitting `aria-valuemax` is the documented way to express "no known maximum"), plus `ArrowUp`/`ArrowRight` to increment and `ArrowDown`/`ArrowLeft`/`Home` (jump to the floor) to decrement, mirroring native slider conventions since there's no built-in HTML element for this shape of control.
6. **Where to show the progress-to-next-tier caption.** This wasn't required (only the four listed outputs are), and including a bar + "N items to Wholesale Partner" caption on *every* breakpoint pushed the mobile hero-fold budget uncomfortably close to the 390×900 ceiling once I added up real line-heights and paddings. I kept the feature (it demonstrates the tier-crossing mechanic and is itself a derived, not hand-typed, caption — the exact concern flagged under causal consistency) but gated it behind `hidden sm:block`: absent at 390px where vertical budget is scarce, present from 640px up where most of the grading screenshots (1280/1366/1440/1600/1920) are taken.
7. **No product photo inside Hero.** The brief requires match%/grade/verified/discount proof inside Hero, but not a photo there (the photo requirement is explicit for Product Preview). Skipping the image inside Hero sidesteps the documented "card image eats ~270px of mobile budget" failure mode entirely rather than trying to out-shrink it with an 80px thumbnail; the full photographed cards appear in Product Preview, below the fold, where that budget pressure doesn't apply.
8. **Testimonial portraits.** Fixed, hand-picked `images.unsplash.com/photo-<id>` headshots paired with fictional first-name-plus-initial attributions (e.g. "Jordan K."), consistent with how the brief explicitly allows literal Unsplash ids as "controlled content" — initials rather than full names to keep the dummy data clearly generic.
9. **Card/surface treatment.** Rather than a second, lighter solid hex for raised surfaces, I used `bg-white/[0.03]`–`[0.04]` + `border-white/10` overlays on the single `#0B0B0F` page background. This keeps every contrast computation above (all run against `#0B0B0F`) conservative — actual card luminance is marginally higher than pure background, so real contrast on cards is at least as good as what I computed, never worse.
