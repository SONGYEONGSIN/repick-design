# Candidate b — Counterfeit Report Wizard

A true ordered 3-step stepper (persistent "Step N of 3" header with completed/current/upcoming dots, explicit Back/Next navigation, exactly one step's content visible at a time) for reporting a suspected counterfeit item: pick one fixed reason, write a ≥20-character note with a live remaining-characters count, then review and submit — submission flips the step-content area in place into a "Report submitted" confirmation, with no native `Alert` and no navigation away.

## Component / heading (for gate registration)

- Default-exported component: `CounterfeitReportWizardScreen`
- File: `native/src/evolve/r54/b/CounterfeitReportWizardScreen.tsx`
- Sibling data file: `native/src/evolve/r54/b/data.ts`
- Exact rendered heading text (real `<Text accessibilityRole="header">`, always on screen regardless of step, including the submitted confirmation state): `Report a Counterfeit Item`

## Brief gaps

1. **What item the report is "about"** — the brief specified the wizard's internal shape but not whether the report is anchored to any order/listing context. Invented a single fixed `REPORTED_ITEM` (brand, title, order ref, seller) shown as one persistent, non-interactive line under the title, visible across every step — it is pure context, never a gate input, so it can't be confused with the authentication-escalation screen's order card (which *is* load-bearing there).

2. **Exact reason list copy** — the brief gave four reasons in loose/example phrasing ("e.g. ..."). Fixed the exact four labels verbatim from the brief's own examples (quality defect, missing/incorrect markings, serial mismatch, Other) plus one short help line per reason, invented, to give step 1 enough visual weight without adding a fifth option the brief didn't ask for.

3. **Minimum/maximum note length and placeholder copy** — the brief fixed the minimum at "≥20 characters" but left the ceiling and example text open. Set `MAX_NOTE_LENGTH = 500` (generous but not unbounded, enforced via `TextInput`'s `maxLength`) and wrote one deterministic placeholder example sentence in the component (not `data.ts`, since it's UI copy rather than dummy data).

4. **Step-dot tap-to-jump** — the brief only required Back/Next; it didn't say whether the step dots themselves are tappable. Added it, but restricted to steps already reached (`index <= currentStepIndex`) — tapping ahead into an unvalidated future step is never possible, and each dot is a sibling `Pressable` (not nested inside another interactive wrapper), so the row itself carries no `accessible={true}`.

5. **Live-region split for the step-of-N heading vs. step title** — the brief says the "Step 2 of 3"-style text should carry `accessibilityRole="alert"` on transitions. Implemented that on the "Step N of 3" line specifically, and put `accessibilityRole="header"` on the separate step-title line (e.g. "Describe what you found") instead of double-stacking both roles on one node — this keeps heading semantics intact for screen-reader navigation while only the position indicator re-announces on change.

6. **Character-count-remaining live region** — the brief explicitly offered a choice ("use `polite` scoped to just that text, OR be silent and rely on the Next button's disabled state — pick one and justify it"). Chose silent: the step-content container already holds the screen's one `accessibilityLiveRegion="polite"` region (for step transitions and the submitted confirmation), so a second nested live region on the character count would violate the "no more than one live region at once" rule, and re-announcing a number on every keystroke would be noisy. The Next button's `accessibilityState.disabled` is the thing a screen-reader user actually acts on; the remaining-characters text is a sighted-user convenience only.

7. **Confirmation-state reference number and copy** — the brief didn't specify what the in-place "submitted" state shows beyond "Report submitted". Added a fixed `CASE_REFERENCE` ("CR-30842") and a one-line "reviewed within 2 business days" note, both deterministic literals in `data.ts`, to make the confirmation state feel like a real terminal state rather than a bare headline.

8. **Review step's recap format** — the brief said step 3 lists "the choices from steps 1-2" but not the layout. Used two bordered label/value blocks (Reason, Your note) plus a short footnote reiterating that Back still works pre-submit — chosen over a single paragraph so the recap is scannable and visually distinct from the step 1/2 input surfaces it's summarizing.

## Non-duplication check

- **`native/src/evolve/r44/a/AuthenticityEscalationScreen.tsx`** (nearest domain neighbor — also a buyer reporting a problem with a received item to Trust & Safety / the authentication team). Architecturally different: that screen is a single `ScrollView` with every field (issue-area chips, photo evidence grid, description box) visible and editable simultaneously, gated by one `CaseStage` ("incomplete"/"fileable"/"filed") blocked/ready/done band that jumps the scroll position to whichever requirement is unmet — there is no step index, no "step N of M" header, and no Back control (there is nothing to go "back" from, since nothing is ever hidden). This screen has a `currentStepIndex` into a fixed `WIZARD_STEPS` array, exactly one step's content rendered at a time, a persistent 3-dot step header, and a real Back action that un-hides a previous step's content. The only structural overlap is the domain (counterfeit/authenticity reporting) and the shared, already-validated surface-transition doctrine (flip the surface in place on a terminal action instead of popping an `Alert`) — the state shape, control flow, and header chrome are unrelated, and no style-key names are shared (`caseBand*` vs. this screen's `stepDot*`/`stepperSegment`/`footer`).
- **`native/src/authentication/ItemAuthenticationScreen.tsx`** and **`native/src/certificate/AuthenticationCertificateScreen.tsx`** (named explicitly as nearest neighbors to check). Confirmed, read in full: `ItemAuthenticationScreen` is a pre-listing authentication *submission* — a `FlatList` of five required-photo rows plus a declaration checkbox, gated by the same blocked/ready/done band family (`bandBlocked*`/`bandReady*`/`bandDone*`), with no step index and no Back. `AuthenticationCertificateScreen` is a completed, read-only *result* display with a persistent always-available action bar (Share/Download), explicitly not a state machine because nothing on that screen is blocked. Neither has an ordered, one-step-visible-at-a-time flow with a numbered step header or backward navigation; this screen is a different architecture from both (a guided, multi-step *intake* wizard, not a single-screen requirement checklist or a static record view), and reuses none of their style-key names.
- **`native/src/evolve/r49/c/SellerOnboardingChecklistScreen.tsx`** (named explicitly as the structural edge case to check). Confirmed the distinction holds: that screen shows *all* steps expanded/visible at once in a single scrollable list (done/current/locked rows, each with its own status tag), has no `currentStepIndex`-style single-step view, and has no Back — once a step is marked done there is no control that returns to it. This screen is its structural opposite by design: only one step's content is ever rendered, the step header shows position but never expands every step's full content inline, and Back is a first-class, always-available (except post-submission) action. The only shared idea is "ordered steps with a visible progress indicator," which the brief's own distinction confirms is not the same architecture as a true stepper.

Honest note: the step-dot tap-to-jump (item 4 above) and the step-position header are, at the macro level, "progress indicator + sequence," the same *idea* `SellerOnboardingChecklistScreen`'s row statuses also express — but the two screens never show more than one step's content at a time vs. always-all-visible, which is the dimension the brief calls out as the deciding one, and that dimension is opposite between the two screens.
