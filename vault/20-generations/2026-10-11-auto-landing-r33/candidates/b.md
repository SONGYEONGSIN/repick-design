# Candidate B

한 줄 개념: 스니커즈 한 모델의 12개월 치 종가 기록을 월×가격대 캘린더 히트맵("Ledger Calendar")으로 펼치고, 등급·정품·판매자 인증 토글이 셀 커버리지와 median/beats% 헤드라인 통계를 실시간으로 재계산해 Value 3-split과 클로징 CTA 버튼 라벨까지 같은 state가 그대로 흘러가는 구조.

## 브리프에 없던 것

- 캘린더 축 구성 (월×가격대, 방향)
  무엇: "주=열/일=행" 또는 "월×가격대 행" 중 어느 쪽을 쓸지, 가격대가 위/아래 어느 방향으로 읽히는지 브리프엔 선택지만 있고 지정이 없음.
  선택: 12개월(열) × $20 단위 6개 가격대(행)로 정하고, 가격 사다리처럼 비싼 가격대를 위쪽에 배치. 라벨 열은 6.5rem 고정, 모바일에서는 min-width 560px의 overflow-x-auto 스크롤 컨테이너로 처리.
  이유: 레퍼런스 없는 임의 선택. 모바일 390px에서 12열을 억지로 22px까지 찌그러뜨리기보다, 라벨이 읽히는 폭을 유지한 채 가로 스크롤을 허용하는 쪽을 택함(브리프가 지목한 overflow-x-auto 리스크는 감싸는 섹션에 contain:layout을 줘서 처리).

- 셀 밀도 색상 스케일 (0/1/2/3+)
  무엇: 셀당 거래 건수를 색 강도로 바꾸는 구체적 임계값·색상이 브리프에 없음.
  선택: 데이터셋의 실제 최대 셀 카운트가 3이라, 0(흰색)/1(연한 그린 #DCF2E3)/2(중간 그린 #5FAE7C)/3(베이스 그린 #176B41) 4단계로 고정.
  이유: 레퍼런스 없는 임의 선택. 실제 데이터 분포에 맞춘 임계값이라 어떤 필터를 켜도 색 단계가 의미 있게 유지됨.

- 96건 판매 기록의 생성 규칙
  무엇: "결정적(deterministic) 데이터"라는 제약만 있을 뿐, 실제 월·가격·등급·인증 분포를 어떻게 구성할지는 브리프에 없음.
  선택: 월별 가격대를 bell-shape 사이클로 고정하고, 등급별 가격 오프셋(A는 +7, C는 −7)을 더한 뒤, 인덱스 기반 modulo로 인증 여부를 배정. Math.random 등 런타임 난수는 전혀 쓰지 않고, 오프라인에서 한 번 계산한 값을 리터럴 배열로 데이터 파일에 박아 넣음.
  이유: "필터를 켤 때 그리드 커버리지(72→17칸)와 beats%(65%→77%)가 실제로 눈에 보이게 달라져야 한다"는 브리프 요구를 만족시키면서도 재현 가능해야 했던 가장 단순한 방법.

- "이 리스팅이 몇 %를 이기는가" 지표의 방향
  무엇: "this-listing's percentile position"이 구체적으로 무엇을 보여줄지(더 싼 쪽 비율인지 더 비싼 쪽 비율인지) 브리프에 없음.
  선택: "comp 중 가격이 이 리스팅보다 높은 비율"(= 이 리스팅이 이기는 비율)로 정의하고, Value 섹션 문장과 클로징 CTA 문장·버튼 라벨에 동일한 숫자를 그대로 echo.
  이유: "이 가격이 시장보다 낫다"는 셀링포인트로 직관적으로 읽히는 방향을 택함.

- 정적 데이터를 "live-refresh처럼" 읽히지 않게 쓰는 카피 톤
  무엇: 브리프가 "실제로 안 하는 일(예: 매주 재수집)"을 암시하는 카피를 명시적으로 금지했는데, 정적 96건 데이터를 어떤 어휘로 표현할지는 지정이 없음.
  선택: 헤더/본문 전체에서 "96 closed resale sales, the last 12 months"처럼 과거형·고정 건수로만 서술하고, "live", "real-time", "updated weekly" 류의 단어를 전혀 쓰지 않음.
  이유: 브리프의 명시적 경고를 그대로 따름 — 디바이스 자체가 가격 기록이라 이 함정에 걸리기 쉽다는 지적을 반영.

- 액센트 대비 수치 (브리프 요구사항 — 계산 기록)
  베이스 그린 #1E7A4C: 화이트 대비 5.33:1 / 다크 잉크(#15171A) 대비 3.37:1.
  작은 텍스트·eyebrow 라벨·호버용 진한 변형 #176B41: 화이트 대비 6.53:1 / 다크 잉크 대비 2.75:1.
  이유: 베이스 색 자체가 화이트 위 작은 텍스트에서도 4.5:1을 넘어 별도 밝은 틴트 없이 재사용 가능했고, 라벨·포커스링·호버 상태엔 더 진한 변형을 추가로 둠.

- 포커스 가시성 구현 (Tailwind v4 bare ring 버그 회피)
  무엇: bare ring/outline-none 조합이 투명하게 렌더되는 문제를 캘린더 셀처럼 상태가 많은 요소에서도 어떻게 피할지.
  선택: ring/ring-offset 유틸리티를 전혀 쓰지 않고, 필터 토글·72개 캘린더 셀을 포함한 모든 포커스 가능 요소에 focus-visible:outline-2 + outline-offset-2 + 실제 색상(#176B41)만 적용. 셀의 "현재 보고 있는 칸" 강조는 ring 대신 box-shadow 인셋으로 별도 처리.
  이유: 브리프가 명시한 정확한 해법을 그대로 채택 — 임의 선택이 아니라 지정된 해법을 따름.

- 캘린더 셀 접근성 패턴 (roving tabindex + 커서/호버 분리)
  무엇: 72개 셀을 전부 개별 tab-stop으로 둘지, "마우스 호버"와 "키보드 포커스"를 어떻게 구분할지 브리프는 방향(roving-tabindex, 인접 live region)만 제시하고 구체 구현은 없음.
  선택: 72개 셀을 하나의 roving-tabindex 그룹(동시에 tabIndex=0은 1개)으로 묶고, 실제 DOM focus를 옮기는 cursor state와 마우스 호버에만 반응하는 hovered state를 분리. 각 셀엔 custom aria-label 대신 sr-only span만 넣어 label-content-name-mismatch 자체를 발생시키지 않게 하고, 별도 aria-live 영역이 focus·hover 양쪽 변화를 모두 읽어줌.
  이유: 브리프가 명시한 "aria-label 대신 sr-only span" 해법과 "roving-tabindex + 인접 live region" 권장을 그대로 따르면서, 호버가 실제 키보드 포커스를 가로채 tabIndex 부기가 어긋나는 부작용을 피하려 함.
