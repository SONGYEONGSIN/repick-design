# Candidate A — Threadline

**One-line concept**: Threadline is an integration-analytics console for a workflow-automation SaaS — an "Integration Rank Leaderboard" tracking which of 8 connected apps (Slack, Google Sheets, HubSpot, Stripe, Notion, GitHub, Salesforce, Zendesk) ranks highest for active workspace connections each week, rendered as a hero bump chart with inline headline stats and a full sortable fallback table.

- Macro shell: **hero + inline-stats**, chart-forward, rail-free. Top to bottom: slim 3-tile KPI strip → one large hero card (`bump-chart.tsx`: period-range control + two always-visible headline stat blocks + the bump chart itself) → one fallback-table card (`leaderboard-table.tsx`).
- Theme: dark (`zinc-950`/`zinc-900` surfaces, `border-white/10`, `zinc-50`/`zinc-400` text) · accent: plain Tailwind **sky** (`sky-300`/`-400`), used only for the active nav pill, focus ring, primary Export button, the selected chart line/labels, and the active segmented/filter state · display face: `--font-display-mono`, used only for the "Threadline" wordmark, the page `<h1>`, and the hero card's two headline numbers.
- Dominant visualization: a **bump chart** (rank-over-time, rank 1 at top, 8 parallel lines across 8 weekly periods) — the single largest, most prominent element on the page, per the hero+inline-stats shell assignment.

## Interactions (4 required, 4 implemented + shell extras)

1. **Chart selection — the mandated no-detail-component mechanic** (`bump-chart.tsx`) — a real HTML `<button>` per integration, laid over the chart by percentage (so it tracks the fluid SVG at any width) at that line's current end-point. Clicking or focusing one (`Enter`/`Space`, real `FOCUS_RING` outline) toggles `selectedId`, a `useState` that lives *only* inside `BumpChartHero` and is read by nothing else on the page. Selecting a line: highlights only that polyline (`stroke-sky-400`, dims the rest to `stroke-zinc-700`/`stroke-zinc-500`), and prints that entity's own rank as a number at every one of its vertices, inline, right along the line. There is no separate detail panel anywhere — the chart **is** its own detail view, which is the best tier on the "selection fan-out" axis.
2. **Period-range toggle** (`bump-chart.tsx`, `SegmentedControl`) — "Last 4 weeks" / "All 8 weeks" recomputes the chart's visible period window *and* the "Biggest Mover" headline stat (`biggestMover(startIdx, endIdx)`), so the toggle visibly changes a real number (+6 spots over 8 weeks vs. +4 spots over 4 weeks for the same integration), not just the chart's x-axis.
3. **Fallback-table sort + independent category filter** (`leaderboard-table.tsx`) — 3 `aria-sort` columns (Integration / Rank / Δ vs last week), ascending/descending toggle, plus a separate category-pill filter (All / Workspace & Docs / Revenue & CRM / Engineering / Customer Support). Both live in `LeaderboardTable`'s own `useState` and never read or write the chart's `selectedId`, and the chart never reads the table's state either — two fully separate interaction surfaces on the same page.
4. **Live mini-chart** — a deterministic 8-week `Sparkline` of each integration's connection count, shown per row in the mobile card list (and reusable in the desktop view), always paired with the same series as real sortable numbers in the table next to it.

Bonus (not counted toward the 4): a **Tabs** control inside the fallback table ("Rank by week" / "Connections by week") switches which 8-column matrix is shown without ever mounting two tables/scrollers at once.

Shell extras, all with real `onClick`: ⌘K command palette (filters a static command/action list — exporting the CSV is a real action, navigation items just close the palette, so it never becomes a second consumer of any chart/table state), primary "Export leaderboard CSV" button (builds and downloads a real `Blob` of every entity × period rank and value), notifications popover, account menu, workspace switcher, mobile nav drawer.

## Font/weight discipline

- Rendered weights, route-wide: exactly 3 — `font-normal` (400), `font-medium` (500), `font-semibold` (600). Grepped across all 9 files in the folder for `font-(thin|extralight|light|bold|extrabold|black)`: zero matches.
- Every heading (`h1`, both `h2`s) gets an explicit `font-semibold` class rather than relying on any default; every `<th>`/`<caption>` that carries direct text gets an explicit weight class too, so none of them can fall back to the browser's UA-default bold.
- All numbers are `tabular-nums`; all 11px labels are `uppercase tracking-[0.06em]`.
- Dark-surface secondary text never drops below `text-zinc-400` anywhere on the route (grepped for `text-zinc-500`/`text-zinc-600`: zero matches) — the one place a label needed to look "dimmed" (an unselected chart line's end-label while another line is active) uses `opacity-50` on that same safe `text-zinc-400` token instead of a darker gray step.

## Bump-chart fallback table

`leaderboard-table.tsx` sits in normal document flow directly below the chart card — present in the DOM at first paint, reachable by scrolling or by Tab, no click/toggle needed to reveal it. On `sm:` and up it is one real `<table>` (`<caption>`, `scope="col"`/`scope="row"`, `aria-sort` on the 3 sortable columns) with the full entity × period matrix: Integration, current Rank, Δ vs last week, then one column per week showing either rank or connection count (via the Rank/Connections tab) — the exact same numbers the chart's lines and the hero's headline stats are built from, with `min-w-[980px]` on the `<table>` element itself (never on a cell) inside its own single `overflow-x-auto` wrapper. Below 640px it swaps to a `sm:hidden` card list carrying the same current rank, Δ, sparkline, and a "first week rank → last week rank" summary line, so the route never has two independent horizontally-scrolling containers at once.

## Always-visible headline readouts

The hero card shows two stat blocks in `text-3xl` `--font-display-mono` numbers — strictly larger than the KPI strip's `text-xl` tiles, so the KPI row never outweighs the chart — neither gated behind hover: "Current #1" (today's rank-1 integration, computed straight from the data, untouched by any selection state) and "Biggest Mover · {range}" (the integration with the largest absolute rank delta across the currently toggled window, with its exact `Rank X → Rank Y` and a signed `RankDelta` chip). Both update deterministically; neither depends on the chart's click/focus selection, so they're never empty and never only readable on hover.

## Why the selection mechanic has no separate detail component

`BumpChartHero` owns one `useState<string | null>` (`selectedId`), initialized to the current #1 integration so the very first paint already demonstrates the mechanic rather than showing a blank, unselected chart. Clicking or focusing any integration's name button toggles that same state; everything that changes in response — which polyline is drawn on top with the accent color and thicker stroke, which line's vertices print rank numbers, which other labels dim — renders *inside this one component*, over the same chart, in place. No `selectedId` is threaded to the table, the KPI strip, the command palette, or any other file; nothing outside `bump-chart.tsx` ever reads it. This is the "no separate detail component at all" tier: the chart is its own detail view, and deselecting (clicking the same line again) is equally local.

## 브리프에 없던 것

1. ① The concrete product/domain and the 8 entities for a bump chart — the brief named example domains ("sales reps/regions/SKUs/integrations by period, or a feature/plan popularity ranking") but left the specific choice open.
   ② Invented **Threadline**, a workflow-automation SaaS, and an "Integration Rank Leaderboard" ranking 8 real third-party integrations (Slack, Google Sheets, HubSpot, Stripe, Notion, GitHub, Salesforce, Zendesk) by weekly active workspace connections.
   ③ "Integrations by period" was explicitly offered as an example in the brief, and a workflow-automation product (à la n8n/Zapier) gives the ranking a believable business reason to exist (which integrations to prioritize for support/SDK investment) rather than being an arbitrary leaderboard.

2. ① How to guarantee every rank shown anywhere on the page is arithmetically consistent with every other rank/delta shown, since the brief calls out derived-statistic consistency as a pitfall no tool catches.
   ② Hand-authored only ONE matrix — `values` (active connections, 8 entities × 8 weeks) — in `data.ts`, and derived every rank, every delta, the current leader, and the biggest mover from that one matrix via pure sort/compare functions (`rankAt`, `rankDelta`, `biggestMover`, `currentLeaderId`). No rank or delta is ever hand-typed as a separate literal.
   ③ A single source of truth makes the "two numbers that imply a relationship" pitfall structurally impossible rather than something to double-check by hand — the hero's "Rank 8 → Rank 2" and its "+6 spots" badge, for instance, are two reads of the exact same underlying sort, not two independently authored numbers that happen to agree.

3. ① How to keep every on-chart label a constant, legible, real pixel size, given the chart's SVG must scale fluidly with its card (no horizontal scrollbar, full-width hero) across 390px phones through 1920px+ monitors.
   ② Discovered partway through building that CSS pixel font-sizes set on SVG `<text>` scale with the SVG's own `viewBox`-to-viewport transform, so a "9px" label would render at roughly 4px on a narrow phone and 15px on an ultrawide monitor. Rebuilt the chart so the SVG carries *only* geometry (gridlines, polylines, vertex dots) and every piece of text — period labels, per-vertex rank numbers, and the integration-name buttons — is a real HTML element laid over the SVG by percentage position, unaffected by the viewBox scale.
   ③ Not specified by the brief beyond "deterministic coordinates rounded to 2 decimals" (which still holds — the percentage math is derived from the same rounded coordinates); this was a correctness issue only discoverable by reasoning through how SVG's coordinate-system scaling actually interacts with CSS font-size, not something either the brief or a static check would catch.

4. ① Whether the rank axis (left side, "#1".."#8") needed its own tick labels inside the chart, given the fix above also meant that reserved margin had to host real, constant-size HTML text.
   ② Dropped the rank-axis tick labels entirely. Rank position is already encoded by each line's vertical position (the whole point of a bump chart), the selected line prints its own exact rank at every vertex, and the fallback table gives every exact rank anyway.
   ③ An 8-step margin reserved only ~4% of the chart's width — at phone width that is a handful of physical pixels, nowhere near enough to host legible constant-size text without colliding with the plotted lines; removing it let the freed width go to the lines themselves instead, and nothing authoritative was lost since the table already carries the exact numbers.

5. ① Which two periods "this period's biggest mover" should compare, since the brief's own example phrase ("biggest mover this period") doesn't specify whether "period" means the single latest step or the whole visible window — and the single latest week-over-week step turned out to be a weak, barely-distinguishable "mover" in the hand-authored dataset.
   ② Defined "Biggest Mover" as the largest absolute rank delta across the *currently toggled* window's two endpoints (last 4 weeks' start→end, or all 8 weeks' start→end) rather than always just the latest two weeks.
   ③ This makes the headline stat meaningfully responsive to the period-range toggle (the exact delta changes from +4 to +6 for the same integration when the range changes), satisfying the brief's requirement that it be a real, non-hover-gated readout, and gives the toggle an effect worth noticing beyond just re-stretching the x-axis.

6. ① What should happen when the fallback table needs to show both "rank per week" and "connections per week" for 8 weeks — a literal 16-column matrix (8 rank + 8 value columns) was judged too wide even for a horizontally-scrolling table, and picking only one metric would drop real, brief-mandated data ("entity×period rank/value values").
   ② Added a `Tabs` control ("Rank by week" / "Connections by week") that swaps which single 8-column matrix is shown, with only ever one panel mounted (never two tables, never two scrollers) — reusing the existing `Tabs` component from the brief's required component system rather than inventing a new control.
   ③ This keeps the table at a manageable, honestly-labelled 11 columns at any one time while still making every rank *and* every value reachable through the same component, satisfying "same entity×period rank/value values" without a second page-level horizontal scroller.

7. ① The exact 1920px right-edge arithmetic and content cap for this shell.
   ② Reused `max-w-[1600px]`: sidebar `w-64` = 256px fixed, so at 1920px the main column is 1920 − 256 = 1664px wide; a 1600px inner cap introduces only ~32px of margin per side, comfortably under the 40px ceiling, and only engages at all past 1664px.
   ③ Recomputed from this candidate's own shell geometry (same 256px sidebar as the rest of this app family) rather than assumed, per the brief's instruction that such thresholds are worked examples, not a universal constant — it happens to land on the same number as a prior round because the sidebar width is the same, not because the number was copied without checking.
