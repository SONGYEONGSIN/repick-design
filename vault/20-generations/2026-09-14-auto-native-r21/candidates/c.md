# Candidate c — Invite Friends (referral share code + tier reward ladder + invite roster)

A growth-loop screen: a share-code card up top (copy/share), a stacked milestone/tier reward ladder as the visual centerpiece showing progress toward the next unlockable tier (tap a tier to expand its full reward detail), and a virtualized list of invited friends each carrying a per-invite status chip (pending / joined / first sale / rewarded).

## 브리프에 없던 것
- Qualifying-invite rule: the brief lists 4 per-invite statuses but never says which ones count toward tier progress. Decided: "joined", "first_sale", and "rewarded" count; "pending" (invited but not yet signed up) does not. Chosen because it mirrors how referral programs work in the wild (the referred person has to actually join before the referrer gets credit) and keeps the ladder from double-crediting a friend who never confirmed.
- Tier thresholds/count/rewards: brief only gave example shapes ("Invite 3 → X", "Invite 10 → Y"). Invented 3 tiers (3 / 5 / 10 invites) with escalating reward types (wallet credit → shipping labels → wallet credit + priority verification) to make the ladder read as a real progression rather than a single milestone, and to give the "tap a tier" interaction more than one node to be meaningful on.
- Reward amounts (₩10,000 / ₩50,000) and "3 free shipping labels": arbitrary but plausible marketplace-reward magnitudes, invented since no monetary anchor was given anywhere in the brief.
- Dummy roster composition (7 friends, mix of all 4 statuses, dates spanning Jul 10–Sep 10 2026): chose counts so the current state lands exactly on a tier boundary (5 qualifying invites = Tier 2 just unlocked, Tier 3 five away) — deliberately picked so the progress-ladder UI has something non-trivial to show (a just-crossed threshold + a clear next target) rather than an all-zero or all-maxed demo state.
- Live-region content: GENERATION.md required exactly one `accessibilityLiveRegion="polite"` covering tier-progress changes and also said per-invite status changes ("friend joined") are not optional to announce. Decided to put both transition kinds as two separate `accessibilityRole="alert"` `<Text>` lines inside the single progress-summary container (one for "which tier + how many invites to next", one for "most recently-qualifying friend + their new status") rather than adding a second live region, since the brief explicitly forbids mounting two at once. This is a static screen so neither line fires a real transition — documented in the component's header comment per the brief's own allowance for that.
- ₩ glyph handling: picked option (a) from GENERATION.md — a literal space between "₩" and the digits (`₩ 10,000`) — over "KRW" text, since the ladder reward copy reads more naturally with the symbol and the fix is a one-character gap.
- Copy/Share button behavior: since `expo-clipboard` isn't in this project's `package.json` dependencies, neither button performs a real clipboard write or opens a native share sheet — each just flips local visual feedback text ("Copy Code" → "Copied", "Share Link" → "Ready to Share"), same convention TradeProposalScreen uses for its "Send" action. Per GENERATION.md I omitted any `accessibilityHint` that would promise clipboard/share-sheet behavior, keeping the `accessibilityLabel` limited to naming the code/link itself rather than claiming an effect.
- Tier-node "locked/next/unlocked" visual states and their icon+text pairing (state label text alongside the indicator, never color alone): invented state machine and copy ("Unlocked" / "In progress" / "Locked") since the brief only said the ladder must show current position + what's needed next, not how to render 3 discrete states.
- Equal-width ladder track segments (one per tier, not proportional to actual threshold numbers): simplification decision — proportional width would need real layout measurement in RN without extra libraries; equal segments keep the bar simple while the actual thresholds are always spelled out in the tier rows' text underneath, satisfying the "not just a bare percentage" requirement through text rather than bar geometry.
