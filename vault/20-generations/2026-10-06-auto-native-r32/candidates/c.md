## Concept
A seller builds a case against a one-star review by checking specific policy grounds and writing a substantive account, watches a live "what Trust & Safety will see" preview compose itself from those same fields, then tracks the appeal through a with-Trust-&-Safety queue into a fixed removed/upheld decision — with any post-submission edit auto-retracting the case back to draft.

## 브리프에 없던 것

1. ① What counts as "real substance" for the explanation gate, beyond "any text". ② Required both a character floor (40) and a word floor (8 words), checked together via `meetsExplanationBar`. ③ A single length check is trivially gamed by repeating one character or pasting whitespace-padded junk; pairing length with a word-count check (not just `.length`) forces at least a short multi-word sentence, which is closer to "real substance" than either check alone.

2. ① How the "estimated review time" should be computed so it's deterministic, not a hand-wavy constant. ② Pure function `estimateReviewWindowHours(groundCount, explanationLength)`: base 24h + 6h per flagged ground + 4h per 120 characters of account, capped at 72h. ③ Arbitrary but principled and inspectable — more grounds plausibly means more cross-referencing against order records, and a longer account plausibly means more reading time for the reviewer; capping avoids an absurd headline number for a very long submission.

3. ① How to pick the fixed resolved outcome without it reading as a coin-flip. ② Hardcoded `DUMMY_DECISION.outcome = "removed"` in `data.ts`, paired with a specific `decidedNote` that directly references one of the five grounds (the "refund never requested" ground), so the outcome reads as caused by the case rather than arbitrary. ③ Arbitrary choice per the brief's "pick one deterministically, don't make it random" instruction; tying the decision note's content to one of the actual grounds makes the dummy data feel internally consistent rather than generic.

4. ① Whether "Withdraw Appeal" should be offered once the case is already resolved (settled), given it's framed as irreversible. ② Restricted the withdraw control to the `withTrustSafety` (in-queue) phase only; the `settled` phase shows the outcome with no withdraw action. ③ Once Trust & Safety has already decided, there's nothing left to withdraw — offering a withdraw button next to a final decision would promise a side effect ("undo the decision") the code doesn't perform, which the accessibility rules explicitly forbid.

5. ① Whether any edit during "settled" (post-decision) should also retract, or only edits during "withTrustSafety". ② Any edit to grounds or explanation while `phase !== "forming"` retracts to `forming`, regardless of whether the case was merely queued or already decided. ③ The brief says "edits their selection/explanation after already submitted" without carving out the resolved phase; treating both non-draft phases uniformly avoids a stale "REVIEW REMOVED" badge sitting next to inputs the seller has since changed, which is exactly the stale-badge failure mode the brief calls out.

6. ① Where to put the single live region on screen, since the band's content already changes per phase. ② Placed it as its own thin status strip between the scrollable content and the bottom band, always rendered (empty string when nothing has just happened), rather than reusing band text as the live region. ③ The band is phase-dependent structured UI (buttons, decision copy) that stays non-empty even with no recent transition; putting the live region there would have forced either a permanent `role="alert"` or awkward retrofitting, so a dedicated, normally-empty strip was cleaner for the "alert only when content just changed" rule.

7. ① How to implement "jump to the first unresolved requirement" without a reliable native measure API inlined in the brief. ② Captured each section's `onLayout` y-offset into a ref and called `ScrollView.scrollTo({ y })`, then additionally called `.focus()` on the explanation `TextInput` when that's the unmet target. ③ This is the standard non-animated-library RN pattern for scroll-to-section and keeps the promised accessibilityHint ("Scrolls to the first missing requirement") strictly true to what the code does.
