## HARD GATE
1st pass (combined 3-route dispatch, then re-run per-candidate individually to localize the combined run's a11y-attribution ambiguity — `worstLighthouse` doesn't attribute a failing audit to a specific route when multiple routes are gated together, a known limitation from this session's prior rounds): **a clean (0 violations)**. **b failed 2 gates**: `focus` 29 violations + `a11y` `color-contrast` (score 96, a promoted hard-fail audit). **c failed 1 gate**: `focus` 11 violations.

**Root cause for both focus failures (b and c), confirmed empirically via direct Playwright `getComputedStyle` after a real keyboard `Tab`**: the exact dead-focus-idiom `page-brief-core.md` §2 already documents — an unconditional `outline-none` class paired with `focus-visible:outline-2 focus-visible:outline-offset-2 focus-visible:outline-[color]` renders `outline-style: none` even though `outline-width`/`outline-color`/`outline-offset` all compute correctly, because Tailwind v4's shared `--tw-outline-style` custom property gets pinned to `none` by the unconditional class and the focus-visible variant never overrides it back. **Both designers independently fell into this despite the orchestrator's GENERATE prompt including an explicit verbatim warning about exactly this pitfall** (see questions-queue entry below) — the round's own sibling candidate `a` (`PriceSlider.tsx`) correctly avoided it from the start by never applying `outline-none` at all, with an in-code comment explaining why, and became the fix pattern handed to b and c.

**b's additional a11y failure**: `GeneratedCopy.tsx:82`'s live tagline `<p>` used the base accent `text-[#0d9488]` (self-computed by the designer at 3.75:1 against white) at `text-xl` (20px/weight 600) — Lighthouse measured 3.74:1, below body-text AA (4.5:1); the text doesn't qualify for the 3:1 large-text exception (needs ≥24px or ≥19px true-bold/700weight, and this page's brief-mandated 3-weight cap tops out at 600).

**1-fix**: b — removed `outline-none` from 5 locations (`Hero.tsx`, `ToneToggle.tsx`, `GeneratedCopy.tsx`, `ClosingCTA.tsx`, `CategorySelect.tsx`), kept all `focus-visible:*` classes intact; swapped `text-[#0d9488]` → `text-[#0f766e]` (5.48:1, already used elsewhere) on the one flagged node. c — removed `outline-none` from the single shared `FOCUS` constant in `tokens.ts` (all interactive elements consume this one constant, so one edit resolved all 11 violations). Re-gate (per-candidate individually): all 3 clean, 0 violations, a11y 100 across the board.

## 질문 강제 생성 (신규)
**Q — an explicit, verbatim GENERATE-prompt warning about the `outline-none`/`focus-visible:outline-*` dead-focus-idiom was not sufficient to prevent two of three designers from reproducing it independently in the same round** (target: landing, 공통 가능성 — this exact pitfall is already documented in `page-brief-core.md` §2 for dash-side history; this is its first confirmed landing-side reproduction, and notably the GENERATE prompt for this round quoted the pitfall near-verbatim from that doc). Candidates b and c both wrote `outline-none` alongside `focus-visible:outline*` despite the orchestrator's prompt explicitly describing the exact failure mechanism (shared `--tw-outline-style` custom property, with a direct citation of the pattern) before any code was written; candidate a (same round, same prompt-author, independently blind) avoided it from the start by simply never applying `outline-none`. **잠정 가설**: a prose warning in the GENERATE prompt, even when specific and pre-emptive, has a documented failure rate for this particular pitfall (2/3 this round) — possibly because the fix (omit `outline-none` entirely) is a *negative* instruction ("don't add X") that's easy to default back into from habit/training-data convention, rather than a positive pattern to copy. Two directions worth future observation: (가) keep relying on the GENERATE-prompt warning + gate catching it as a 1-fix (current behavior, cheap, costs exactly one extra fix-cycle round-trip per occurrence, observed twice this round) (나) consider whether a static-check rule could catch `className` strings containing both `outline-none` and `focus-visible:outline` as a GENERATE-time or gate-time pattern match, independent of rendering — cheaper to run than the current render-based `focus` gate for this specific sub-case, though the broader `focus` gate would still be needed for other dead-focus-idiom shapes (e.g. the v4 `ring`+`ring-offset` transparency case) that aren't textually detectable this way.
