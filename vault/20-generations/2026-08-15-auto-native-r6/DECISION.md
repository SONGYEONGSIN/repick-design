## 렌즈1 — DNA 준수

**순위: c > b > a**

- **c**: 유일한 종결 액션 화면이자 r3/r5 상태기계 밴드 패턴을 정확히 재현 — 차단 사유를 문장으로 명시(`c/SellerVerificationScreen.tsx:61-86`) + 탭 시 미해결 지점 점프(`scrollToIndex`, `:110-113,119-126`) + `accessibilityRole="alert"`(`:464`) + `accessibilityLiveRegion="polite"`(`:452`). ₩ 미사용이라 r4 위험 무관. hitSlop 8pt·RN 고유 a11y 롤 전부 정확.
- **b**: r4 델타(tabular-nums+₩ 위험)를 정확히 회피 — `data.ts:170-176`에서 ₩ 표시 다수(전 grep 결과 tabular-nums 0건)임에도 전혀 적용 안 함, 스크린샷 클린 렌더 확인.
- **a**: **r4 델타가 경고한 정확히 그 결함이 시각적으로 재현됨** — 모든 통화 표시(₩90,000·₩168,000·+₩168,000·-₩450,000·+₩520,000)가 `a-390.png`·`a-768.png` 양쪽에서 취소선처럼 보이는 렌더링 아티팩트를 보임. 코드 자체 주석(`a/data.ts:172-173`)은 "₩ 기호를 형제 Text 노드로 분리했다"고 주장하나 실제 구현(`PayoutsScreen.tsx:181-184,144-148`)은 ₩ Text를 tabular-nums 부모 Text의 **자식**으로 중첩 — RN 스타일 캐스케이드가 fontVariant를 자식 Text에 상속시켜 형제 분리가 실질적으로 이뤄지지 않음. 자기 주장(주석)과 실제 렌더가 불일치하는 점이 렌더링 결함 자체보다 더 우려됨.

## 렌즈2 — 모바일 완성도

**순위: c > b > a**

- **c**: 밴드가 3상태(blocked/ready/done)를 정확히 오가며 실제 상태기계로 동작, 리뷰 단계의 섹션별 Edit 점프, 제출 후 필드 수정 시 정직하게 draft로 강등. KYC 체크리스트 카피("All four corners visible, no glare...")가 실제 플로우처럼 읽힘.
- **b**: 고정 검색+필터 헤더가 실제 매 프레임 일 수행(라이브 필터링 + "X of 12" 카운트), 칩 선택이 색만이 아닌 보더+체크마크+볼드로 신호. 약점: 768px에서 `numColumns={2}` 고정이라 그리드가 재배열 없이 카드만 커짐(브리프가 경고한 "늘어난 모바일 레이아웃" 실패 패턴), 썸네일이 전부 회색 박스+2글자 모노그램(placeholder급).
- **a**: 구조는 셋 중 가장 정교(만료 후 상태 정직 반영·기간 필터 자체 빈 상태·pull-to-refresh 타임스탬프 토글)하나, 화면의 존재 이유인 통화 수치 전부가 시각적으로 "취소선"처럼 보이는 결함이 거의 실격급.

## 렌즈3 — 화면유형 차별성

**순위: c > a > b**

- **c**: 단일 FlatList가 4스텝을 아코디언으로 감싸고 각 카드 내부에 2단 중첩 서브리스트를 갖는 신규 매크로 패턴 — `handoff`(평면 단일레벨 체크리스트)·`listing`(스텝마다 별도 FlatList 스왑)과 구조적으로 상이함을 소스로 확인. 하단 밴드는 의도된 재사용(r3/r5 검증 패턴)이라 감점 대상 아님.
- **a**: `order-status`(순차 타임라인, 종결 전용 액션)·`detail`(숫자+차트, 리스트 없음)과 데이터 형태가 상이해 매크로 차별성은 확보. 다만 methodCard 확장 토글(`:242-274`, "Details"/"Hide" 레이블)이 기존 `order-status`의 courierCard(`:163-208`)와 구조·레이블까지 거의 동일 — 레이어를 낮춘 재수렴(진단 정보, 순위 미반영).
- **b**: `watchlist` 리스킨은 아님(실제 검색·필터 로직 확인) — 그러나 매크로 실루엣(고정 헤더+스크롤 FlatList, 하단 밴드 없음)이 `watchlist`·`match`와 동일 계열로 갤러리에서 가장 흔한 형태. 칩 비주얼도 기존 `notifications`의 CategoryChip과 근친. pull-to-refresh 메커니즘도 a와 거의 동일 코드(같은 라운드 내 중복 최초 구현).
