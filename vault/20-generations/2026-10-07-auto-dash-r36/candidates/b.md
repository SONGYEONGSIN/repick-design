# Candidate B — Meshwire

Meshwire is a dark, restrained service-topology console for an infra/SRE team: a full-width, deterministic concentric-ring dependency graph of 17 services and 26 calls between them (grouped by tier or by latency), a dismissible node-inspector popover, and an independent bottom incident timeline — backed end-to-end by a complete, sortable adjacency-list table as the graph's required accessible fallback.

## 브리프에 없던 것

1. ① **브랜드/제품 정체성**: 브리프는 "제품을 자유롭게 발명하라"고만 했고 이름·업종을 지정하지 않음.
   ② "Meshwire"라는 이름과, 커머스 스택(결제·카탈로그·검색 등)을 호출하는 API 게이트웨이 토폴로지라는 구체적 제품 서사를 선택.
   ③ n8n/Coinbase류의 실제 ops 콘솔이 다루는 전형적 도메인(서비스 메시 관측성)에서 착안한 임의 선택 — 특정 실제 회사를 모사하지 않음.

2. ① **그래프의 정확한 데이터셋**(노드 몇 개, 어떤 서비스, 어떤 엣지)은 브리프가 "현실적이고 결정론적인 더미 데이터"만 요구하고 구체적 토폴로지는 규정하지 않음.
   ② 3단 티어(Edge 3 / Service 8 / Data 6 = 17 노드)와 26개 호출로, 모든 노드가 최소 하나의 엣지에 연결되도록(고아 노드 없음) 직접 설계.
   ③ 실제 커머스 마이크로서비스 아키텍처(게이트웨이→서비스→데이터스토어)의 통상적 3계층 구조를 임의로 본뜸 — 코드로 고아 노드 없음을 직접 검증.

3. ① **동심원 레이아웃의 정확한 반지름·각도·스태거 오프셋 공식**은 브리프가 "고정 좌표를 직접 계산하라"고만 하고 수치는 지정하지 않음.
   ② `TIER_RADIUS={edge:110, service:205, data:275}`, 티어별 각도 스태거(`0°/20°/10°`)를 임의로 정하고 `Math.cos/sin`으로 산출한 모든 좌표를 `r2()`로 소수 2자리까지 반올림.
   ③ 링마다 스포크가 일직선으로 겹치지 않게 어긋나게 배치하는 것은 d3의 radial-tree 류 예제에서 흔히 쓰는 가독성 관행을 본뜬 임의 선택(수치 자체는 측정값이 아님).

4. ① **"by latency" 뷰가 정확히 무엇을 재계산해야 하는지**는 브리프가 "색상이나 레이아웃 그룹을 결정론적으로 바꿔라"는 방향만 제시.
   ② 각 노드의 자체 지연시간(`selfLatencyMs`)을 `<15ms / 15–40ms / >40ms` 3구간으로 나누고, tier 뷰와 동일한 3개 링 반지름을 재사용해 노드를 재배치하도록 설계.
   ③ 두 뷰가 "다른 기하"가 아니라 "같은 3개 링 사이의 재배정"이 되도록 한 것은 임의 선택 — 시각적 일관성(레이아웃이 통째로 바뀌는 느낌을 피함)을 위한 것.

5. ① **엣지의 relationship(관계 타입)을 클릭 없이도 알 수 있게 하라**는 완성도 요구사항이 있었지만, 상태(색상)와 관계(패턴) 두 신호를 동시에 "색상 단독 아님"으로 어떻게 분리할지는 지정되지 않음.
   ② 엣지 색상=상태(healthy/degraded/down), 엣지 두께=상태의 비색상 짝, 엣지 대시 패턴(실선/파선/점선)=관계 3대분류(sync/async/data-access)로 채널을 분리.
   ③ 지도/다이어그램에서 선 스타일로 범주를 구분하는 통상적 관행(실선=동기, 파선=비동기)을 본뜬 임의 설계 — 6가지 관계 전체는 툴팁·인스펙터·테이블에서 항상 확인 가능하게 유지.

6. ① **390px 모바일에서 그래프 캔버스를 어떻게 처리할지**는 브리프가 "단순화된/줌된 뷰 또는 테이블을 1차로" 둘 중 선택하라고 위임.
   ② 그래프를 `min-w-[760px]`로 고정해 작은 화면에서는 가로 스크롤(그래프 카드 내부에만 한정, 페이지 레벨 가로 스크롤은 없음)되게 하고, 테이블은 항상 전체 너비·스크롤 없이 렌더링.
   ③ 노드 탭 타겟이 화면폭에 비례해 줄어들면 터치하기 어려워지므로, 물리적 크기를 보존하는 쪽(스크롤)을 선택 — 테이블은 이미 1차 접근성 폴백이므로 축소 없이 유지.

7. ① **노드의 tier(모양)와 status(코너 마커)에 모두 "모양" 채널을 쓸 때 충돌 여부**는 지정되지 않음.
   ② 노드 몸체 모양(사각/원/다이아 = tier)과 코너의 작은 상태 마커 모양(원/삼각/사각 = status)을 크기·위치가 다른 별개 채널로 분리해 중첩 사용.
   ③ 두 채널이 크기·위치로 명확히 구분되면 같은 모양 어휘(원/사각/다이아)를 재사용해도 모호하지 않다고 판단한 임의 설계 — 범례에 둘 다 별도로 표기해 확인 가능하게 함.

8. ① **인스펙터 팝오버가 "클릭하면 닫힌다"는 범위**(그래프 전체 vs 카드 전체 vs 페이지 전체)는 브리프가 구체적으로 정하지 않음.
   ② 그래프 카드 내부(다른 노드·엣지·범례 클릭 포함)는 열어둔 채 유지하고, 카드 바깥(사이드바·탑바·테이블·타임라인) 클릭이나 Escape에서만 닫히도록 구현.
   ③ "다른 노드를 눌러 인스펙터를 바로 옮겨 다니는" 흐름을 깨지 않기 위한 의도적 범위 선택 — 과제 설명의 "클릭하면 닫힌다"는 요구는 Escape·외부 클릭·명시적 X 버튼 세 경로로 충분히 충족.

9. ① **울트라와이드(1920px) 캡의 정확한 수치**는 "자신의 셸 기준으로 직접 계산하라"고만 지시됨.
   ② 사이드바 256px + 좌우 패딩 32px×2를 제외한 1920−256−64=1600px를 콘텐츠 `max-w`로 설정 — 여백은 정확히 32px(≤40px 기준 충족).
   ③ 임의의 숫자를 베끼지 않고 이 레이아웃 고유의 셸 폭(w-64 사이드바 + lg:px-8)으로부터 직접 역산.

10. ① **아바타를 어떻게 표시할지**는 "사진 대신 lucide 아이콘이나 이니셜을 쓰라"는 제약만 있고 구체적 처리는 없음.
    ② 사용자 이니셜(`PN`)을 단색 원형 배지로 표시하고, next/image·외부 이미지 호스트를 전혀 사용하지 않음.
    ③ 외부 이미지 호스트 의존성과 무작위 이미지 인덱싱 리스크를 원천적으로 없애는 가장 단순한 선택.
