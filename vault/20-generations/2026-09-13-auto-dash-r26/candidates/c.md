# Candidate c — Ledgerline

결제 운영(payments-ops) 콘솔: 중앙의 라이브 원장(ledger) 피드가 메인이고, 좌우 보조 패널(플랫폼 헬스 + 계정 핀 롤업 / 리전·채널·플랜티어 3단 선버스트+리스트)이 곁을 지키는 피드 중심 레이아웃.

## 브리프에 없던 것

**① Accent hex와 대비 계산**
①색상 팔레트에서 정확히 어떤 hex를 쓸지, 최근 3라운드(blue/teal/amber)와 겹치지 않으면서 라이트 테마의 SaaS/Analytics 계열에 맞는 축을 무엇으로 정할지 결정해야 했다.
②violet-600 `#7c3aed`(텍스트/링크/포커스링/선버스트 주색)와 violet-700 `#6d28d9`(솔리드 버튼 채움)로 정했다. 대비 계산: `#7c3aed` on `#ffffff` = 상대휘도 0.1193 → 대비비 **6.20:1**(본문 AA 4.5 통과). `#6d28d9` 위 흰 텍스트 = 상대휘도 0.0978 → 대비비 **7.10:1**(AAA 수준, 버튼 채움은 텍스트보다 더 큰 헤드룸이 필요하다고 판단해 700을 씀). 선버스트 링1 라벨(흰 텍스트, hsl(262,72%,40~56%) 위)도 별도 계산해 최저 5.87:1 확인.
③violet은 결제/핀테크 톤에 흔하지만 이번 세대 3라운드 사용 계열(blue/teal/amber)과 확실히 구분되고, near-monochrome 선버스트에 필요한 넓은 명도 스펙트럼(40~86% L)을 단일 hue로 확보하기 쉬웠다.

**② 1920px 가용폭 계산**
①"우단 간격=페이지 패딩만"이라는 규칙을 이 특정 셸(사이드바+3단 그리드)에서 어떻게 만족시킬지 정해야 했다.
②사이드바 256px(`w-64`) + 메인 패딩 `xl:px-10`(40px×2=80px) → 1920−256−80=**1584px** 가용폭. `main`에 `max-w-*`를 아예 걸지 않아 콘텐츠가 1584px 전부를 채우고, 우측 여백은 정확히 40px(패딩)만 남는다.
③캡을 두려면 1584보다 커야 의미가 없어지므로, 차라리 캡 자체를 없애는 쪽이 규칙을 가장 확실히 만족시켰다. 1280px에서도 같은 셸로 재계산(944px 가용폭, 3열 중앙칼럼 실측 ~412px)해 피드 테이블 `min-w`를 300px로 낮춰 데스크톱 가로 스크롤바가 안 뜨는지 확인했다.

**③ 도메인·제품 발명**
①"가상 B2B SaaS"를 무엇으로 할지 자유였다.
②Ledgerline: 결제 플랫폼의 운영 콘솔로 정하고, 14개 가맹점 계정(리전×채널×플랜티어)과 18건의 원장 이벤트(charge/refund/payout/dispute)를 계정 목록에서 fold해서 생성 — 트리 합계가 항상 계정 합과 일치하도록 구조를 짰다.
③선버스트가 "계층형 비율"을 요구하므로 자연히 계층 구조가 있는 도메인(지역>채널>티어별 매출 구성)이 필요했고, 결제 콘솔은 동시에 "실시간성 이벤트 피드" 요구와도 잘 맞는 소재였다.

**④ 선버스트 드릴다운 메커니즘의 구체적 설계**
①"링 클릭=드릴다운, 바깥 링 재클릭 또는 breadcrumb=롤업"이라는 브리프 문장을 실제 상태 기계로 어떻게 구현할지(줌 애니메이션형 vs 단순 교체형)는 정해야 했다.
②"교체형"으로 구현: `focusPath`(조상 id 배열) 하나로 현재 루트를 바꾸고, ring1은 항상 현재 루트의 자식들을 0~360°로 재정규화, ring2는 그 손자들을 각 부모 각도 안에서 다시 분할. 허브 원(가운데)이 항상 현재 루트를 표시하고, `focusPath`가 비어있지 않을 때만 허브 자체가 "한 단계 롤업" 버튼이 된다. 리프(더 이상 자식 없는 티어) 클릭은 드릴이 아니라 "선택"으로 분기.
③실제 회전/트랜지션 애니메이션이 있는 진짜 zoomable sunburst는 구현 난이도와 reduced-motion 처리 부담이 컸고, 매 단계 ring1을 풀서클로 재정규화하는 쪽이 "가장 작은 부채꼴도 항상 충분히 크다"는 target-size 안전성까지 같이 얻을 수 있어 더 견고했다.

**⑤ target-size 회피를 위한 ring2 키보드 제외**
①ring2(손자, 최대 12개)의 일부 부채꼴은 화면상 몇 px에 불과해 Lighthouse `target-size`(24px 미만 하드페일) 위험이 있었는데, 이걸 어떻게 처리할지 브리프에 지침이 없었다.
②ring2 부채꼴에서 `tabIndex`/`role="button"`/키보드 핸들러를 아예 빼고 마우스 hover/click만 남겼다. 대신 모든 노드는 ring1을 단계별로 드릴하거나(각 단계는 항상 풀서클로 재정규화되어 충분히 큼), 아래 접이식 리스트(모든 행이 진짜 전폭 버튼)를 통해 키보드만으로도 도달 가능하게 해 "키보드로 못 가는 노드"가 없도록 했다.
③작은 히트타깃에 억지로 포커스를 주는 것보다, "그 지름길이 없어도 동일한 목적지에 다른 두 경로로 갈 수 있다"를 보장하는 편이 접근성 하드게이트와 실사용성을 동시에 지키는 방법이었다.

**⑥ "선택→다중위젯 동기화"의 배치와 파급 범위**
①이 인터랙션을 페이지 어디에 둘지, 그리고 파급 범위를 어떻게 좁게 유지할지 브리프의 예시(요약/KPI 부분 재계산)를 이 도메인에 맞게 구체화해야 했다.
②원장 피드 각 행 끝의 **Pin 아이콘 버튼**(클릭=영속 핀)으로 구현: 핀은 좌측 레일의 `PinnedAccountRollup` 카드 **하나만** 재계산(볼륨·이벤트 수·미해결 분쟁 수)하고, 피드 테이블 자체는 필터·정렬·행 구성이 전혀 바뀌지 않는다. 행 hover/포커스는 완전히 별개의 ephemeral 상태(`hoverRowId`)로, 페이지 상단에 "Quick view" 한 줄만 갱신하고 어떤 지속 상태도 안 바꾼다. 이 둘은 선버스트 자체의 hover(ephemeral 툴팁)/click(영속 드릴다운) 분리, 그리고 기간 토글(히어로 KPI만 재계산)과도 서로 완전히 다른 세 번째 독립 상태로 코드 주석에 명시했다.
③r17→r19에서 감점받은 "단일 selectedId를 형제 위젯에 동일 프롭명으로 threading"과 구조적으로 다르다는 걸 소스를 안 읽는 스크린샷 판정에서도 알 수 있도록, 핀 아이콘 자체를 눈에 보이는 명시적 컨트롤(일반 행 클릭이 아니라 별도 버튼)로 노출하고 핀된 카드에도 "Unpin" 버튼을 눈에 띄게 뒀다.
