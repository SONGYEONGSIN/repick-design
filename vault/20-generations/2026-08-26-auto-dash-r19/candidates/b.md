# r19 · b — Cadence

**한 줄 컨셉** — Cadence(제조 생산라인 스케줄 콘솔)는 6개 생산라인 × 24건 작업지시를 가로축=시간인 풀와이드 간트로 그리고, Week/Month/Quarter 토글이 눈금 밀도가 아니라 **실제 표시 구간(day-offset window)을 재계산해 모든 막대의 픽셀폭을 다시 계산**하며, 라인 행을 고정(pin)하면 그 라인이 맨 위로 재정렬·강조되고 KPI 스트립이 `deriveSummary(focusLineId)` 하나가 반환하는 값 객체로만 재계산된다(원시 `focusLineId`는 간트 자신과 `encoding.ts`만 읽고, KPI·⌘K·원장 테이블은 그 값을 모른다). 순백 라이트 + 단일 cyan 액센트(2단계 depth: 700=텍스트용 5.36:1, 600=장식전용 3.69:1), `--font-display-mono`, Pretendard 3웨이트. 인터랙션 5종 — ① 간트바 호버/포커스 시 전체 행을 가로지르는 시간정렬 밴드 + 상세 툴팁(화살표키·Home/End로 막대 간·행 간 이동) ② 작업지시 원장 테이블 실제 정렬(`aria-sort`)·상태/라인/검색 필터(간트 포커스와 독립) ③ Week/Month/Quarter 스케일 토글(실제 윈도우 리스케일) ④ 라인 핀 선택 → 간트 자신의 정렬·강조·KPI 집계범위 재계산(형제 위젯에 원시 id 미전달) ⑤ ⌘K 커맨드 팔레트(작업지시·라인 점프, 매 오픈마다 새로 마운트되어 내부 state가 절로 리셋).

## 브리프에 없던 것

1. **스케일 토글이 "눈금 라벨만 바꿀 것"인가 "실제 창을 재계산할 것"인가**
   ① 브리프는 "주/월/분기 스케일 전환"이라고만 하고 무엇이 바뀌어야 하는지는 정하지 않았다.
   ② `SCALES.week`는 오늘 기준 ±10/+25일 확대창, `month`는 데이터 전체+2주 여백(기본값), `quarter`는 182일로 확대 축소(같은 데이터가 더 압축돼 보임) — `windowStart/windowEnd`가 바뀌면 `pxPerDay`가 다시 계산돼 모든 막대의 `left/width`가 실제로 재배치된다.
   ③ 단순 눈금 라벨 교체는 "실동작" 요건을 얕게 충족할 뿐이라 판단 — 실제 좌표 재계산 쪽이 게이트의 "결정론 좌표 소수 2자리" 정신과 3렌즈의 "장식이 아닌 인코딩" 기준 둘 다에 더 부합한다고 봤다.

2. **막대 최소 크기(터치 타겟) 대 간트의 날짜 정확도 사이의 절충**
   ① 브리프·게이트는 target-size 24×24px 하한만 요구하고, 초단기 작업지시(6일)가 분기 축소뷰에서 몇 px가 되는지는 지정하지 않았다.
   ② `MIN_BAR_W=26`(px), `BAR_H=32`(px)로 하한을 걸어 아무리 축소해도 막대 히트박스가 24px 밑으로 안 떨어지게 했고, 그 결과 최단 작업(6일)이 분기뷰에서 실제보다 살짝 길어 보이는 왜곡을 의도적으로 허용했다.
   ③ 실제 간트 툴(Jira/MS Project 축소뷰)도 동일 절충을 쓴다 — 날짜 왜곡은 수 px 수준으로 무해하지만, 탭 불가능한 26px 미만 막대는 target-size 하드페일이라 우선순위를 명확히 정했다.

3. **"선택→다중위젯 동기화"를 raw id threading 없이 구현하는 구체 배선**
   ① 브리프는 "타임라인 자신의 인코딩을 재계산하는 방식을 우선 고려"라고만 하고 정확한 코드 경계는 정하지 않았다.
   ② `encoding.ts`의 `buildLineRows(focusLineId)` 하나만 원시 id를 읽어 정렬·강조 순서를 반환하고, `CadenceClient`는 `deriveSummary(focusLineId)`가 돌려주는 `Summary` **값 객체**만 KPI 카드에 넘긴다 — 원장 테이블(`OrderTable`)은 `focusLineId`를 아예 props로 받지 않고 자기 자신의 상태/라인/검색 필터만 갖는다.
   ③ r18 DECISION.md가 "selectedId를 형제 위젯에 각각 threading"을 정확히 반증 사유로 남긴 걸 참고해, 이번엔 소비자를 원천적으로 1곳(간트)+파생값 1곳(KPI)으로 줄이고 원장은 아예 선택 모델을 모르게 분리했다.

4. **5단계 상태 램프의 색+텍스트 대비를 어떻게 동시에 만족시킬 것인가**
   ① 브리프는 "값 라벨 상시노출·다계열은 색+패턴 병행"이라고만 하고 각 상태색의 정확한 톤은 정하지 않았다.
   ② 막대 폭이 넓을 때 흰 텍스트(작업지시 ID·진행률)가 막대 안에 직접 인쇄되므로, 5개 상태색 전부를 "흰 텍스트 4.5:1을 만족하는 가장 밝은 톤"으로 역산해 골랐다(cyan-700/emerald-700/amber-800/rose-800, hold만 zinc-600+점선 테두리로 예외 처리) — 처음엔 더 밝은 톤(amber-500 등)으로 짰다가 흰 배경 대비 3:1 그래픽 하한을 못 넘기는 걸 발견하고 전부 한 단계씩 어둡게 다시 골랐다.
   ③ tokens.ts 헤더 주석에 각 색의 실측 대비값을 직접 기록해 "가정이 아니라 계산"임을 남겼다 — d49(r17 승자)의 워터폴이 같은 방식으로 대비를 문서화해 재현 가능함을 확인했다.

5. **오늘(Today) 마커·호버 링처럼 "장식적이지만 의미를 나르는" 그래픽 마크의 톤**
   ① 브리프·게이트 어디에도 "차트 안의 오늘 표시선"이나 "호버 강조 테두리"의 대비 기준은 명시돼 있지 않다(axe의 color-contrast는 텍스트만 본다).
   ② 처음에 가벼운 톤(cyan-300)으로 짰다가 흰 트랙 배경 위에서 거의 안 보이는 걸 스크린샷으로 확인하고, 텍스트가 아닌 그래픽 마크도 전부 cyan-600(3.69:1) 이상으로 통일했다.
   ③ 자동 게이트가 못 잡아도 사람이 스크린샷을 보면 "오늘 어디야?"가 안 보이는 건 완성도 결함이라 판단 — 렌즈2(상용 SaaS 완성도)가 이런 디테일을 본다는 전제로 선제 수정했다.
