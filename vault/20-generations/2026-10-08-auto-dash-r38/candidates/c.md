# Candidate C — Isobar

Isobar는 다중 리전 엣지/CDN 인프라를 모니터링하는 다크 테마 SaaS 콘솔이다: 중앙 스파인은 14개 엣지 리전의 인시던트·배포·트래픽 스파이크를 보여주는 실시간 활동 피드(12열 중 7열)이고, 지오그래픽 코로플레스는 사이드 패널(12열 중 5열)에 생성형 헥스그리드로 그려진다. 피드 항목 클릭은 오직 지도에 핀 링을 표시하는 한 가지 일만 하고, 지도 리전에 마우스오버/탭포커스하면 React 상태를 전혀 건드리지 않는 순수 CSS 기반의 일시적 툴팁이 뜬다 — 두 메커니즘은 서로 독립적이다.

## 브리프에 없던 것

1. ① **브랜드/제품 정체성과 업종**: 브리프는 "자유롭게 SaaS 도메인을 고르라"고만 하고 이름·업종을 지정하지 않음.
   ② "Isobar"라는 이름(등압선/등고선처럼 지리적 강도 지도를 뜻하는 단어)과, 멀티 리전 엣지/CDN 인프라의 가동률·레이턴시·인시던트를 모니터링하는 운영 콘솔이라는 서사를 선택.
   ③ 지리 데이터가 자연스러운 흔한 ops 도메인에서 임의로 고른 선택 — 실제 CDN 업체를 모사하지 않음.

2. ① **헥스그리드의 정확한 리전 개수·레이아웃·좌표 공식**은 브리프가 "생성형 SVG 헥스그리드, 결정론적 좌표"만 요구.
   ② flat-top 헥스 축좌표(col,row)→픽셀 변환식(`x=1.5·size·col`, `y=size·√3·(row+col/2)`, size=42)을 직접 세우고, 14개 리전(북미 동/서, 남미 북/남, 유럽 북/서/중앙, 아프리카 북/남, 중동·북아프리카, 아시아 남/동/동남, 오세아니아)을 서west→east, north→south의 상대적 나침반 위치에 맞춰 (col,row)를 손으로 배치. 모든 SVG 좌표는 `r2()`로 소수 2자리까지 반올림.
   ③ 실제 대륙 배치를 단순화해 흉내 낸 임의 선택 — 진짜 지도 투영이 아니라 "독자가 라벨로 알아볼 수 있는" 일관된 상대 배치가 목표.

3. ① **14개 리전 × 3개 기간(24h/7d/30d)의 정확한 지표값**(인시던트 수, 가동률, p50, req/s)은 브리프가 "결정론적 더미 데이터, 합계가 일치해야 함"만 요구.
   ② 리전별 값을 직접 하드코딩했지만, KPI 스트립의 4개 수치(평균 가동률, 평균 p50, 총 인시던트, 저하된 리전 수)는 전부 이 리전 테이블 데이터를 `reduce`/`filter`로 런타임에 계산하도록 설계 — 별도로 한 번 더 손으로 합산한 "두 번째 숫자"를 절대 만들지 않음.
   ③ "합계가 항상 일치"라는 요구를 손계산 실수로 깨뜨리는 대신, 코드 구조 자체로 불일치가 원천적으로 불가능하게 만드는 쪽을 선택.

4. ① **4단계 강도 램프의 정확한 색상·경계값과 각 단계별 텍스트 색**은 "색상 램프는 모든 단계에서 AA 안전해야 한다"는 원칙만 있고 구체 수치는 위임.
   ② `tierForIncidents`(0 / 1–2 / 3–5 / 6+)와 `tierForLatency`(<50 / 50–79 / 80–109 / 110+)를 직접 설계하고, 네 가지 채움색(#27272a → #991b1b → #dc2626 → #ef4444) 각각에 대해 흰 텍스트 대비를 손으로 계산 — 세 번째 단계(#dc2626)는 흰 텍스트로 겨우 4.8:1을 통과하지만 네 번째 단계(#ef4444)는 흰 텍스트로 3.8:1(실패)이라는 걸 발견하고 그 단계만 어두운 텍스트(#09090b, 5.3:1)로 뒤집음.
   ③ "가장 어두운 단계만 대비가 안전하다"고 가정하지 않고 네 단계 전부를 개별 검증 — 이것이 바로 브리프가 "deepest step만 확인하지 말라"고 경고한 지점.

5. ① **"피드 클릭은 지도만 바꾸고, 호버는 상태를 전혀 안 바꾼다"는 두 메커니즘의 실제 구현 방식**은 브리프가 원칙만 제시(선택 팬아웃 티어, 에페메럴 정의).
   ② 핀은 `IsobarClient`에 끌어올린 단 하나의 state(`pinnedRegionId`)로, `RegionMap`만 prop으로 받음(Feed·Table·KPI는 이 값을 아예 모름). 호버 툴팁은 React state를 전혀 쓰지 않고 `group-hover`/`group-focus-within` CSS 클래스만으로 투명도를 토글 — 지도의 헥스 자체는 `aria-hidden` 장식용 SVG `<polygon>`/`<text>`이고, 실제 키보드 접근은 헥스 위에 겹친 투명 HTML `<button>`(전체 통계가 담긴 `aria-label` 보유)이 담당.
   ③ 이전 라운드(Fluxgraph) 기록에 "그래프 노드를 포커스 가능한 버튼으로 만들었다가 하드게이트에서 걸렸다"는 교훈이 있어, SVG 마크는 순수 장식으로 완전히 격리하고 실제 접근성 채널은 투명 오버레이 버튼으로 분리하는 쪽을 선택.

6. ① **지도의 "Incidents / Latency" 메트릭 탭**은 브리프에 전혀 요구되지 않음(대시 요구사항은 코로플레스가 "어떤 지표든" 쓸 수 있다고만 함).
   ② 자발적으로 추가 — 같은 3개 링(헥스) 배치를 재사용하되 색상 램프의 입력만 인시던트 수 ↔ p50 레이턴시로 바꾸는 진짜 ARIA `tablist`/`tab`을 구현하고, 레이턴시 임계값(<50/50–79/80–109/110+ms)을 직접 설계.
   ③ "탭"이 컴포넌트 체크리스트에 있는데 세그먼트 컨트롤(시간 범위, 피드 필터)과 구분되는 진짜 용도가 없으면 억지로 끼워 넣는 꼴이 되므로, 선택이 콘텐츠를 바꾸는(패널이 그대로고 내용만 바뀌는) 이 자리에만 진짜 `role="tab"`을 쓰고 공유 패널 하나에 `aria-controls`를 걸어 axe가 요구하는 tab↔panel 연결을 맞춤.

7. ① **1920px 울트라와이드 캡의 정확한 수치**는 "자신의 셸 기준으로 직접 계산하라"고만 지시됨.
   ② 캡을 아예 두지 않기로 결정 — 사이드바 256px + 반응형 패딩(`px-4 sm:px-6 lg:px-8 2xl:px-10`)만으로 메인 영역을 완전히 유동적으로 두면, 1920px에서의 여백은 정의상 패딩 값(2xl 기준 40px) 그대로가 되어 "≤40px" 기준을 계산 실수 없이 trivially 통과.
   ③ 정확한 캡 수치를 역산하다 반올림/센터링 여백 실수로 기준을 넘기는 위험(이전 라운드 기록에 실제로 있었던 실수)을 원천적으로 피하는 쪽을 선택.

8. ① **사이드바 "Settings" 내비 항목**: 앱 셸 요구사항은 "내비게이션 섹션들"이 있어야 한다고만 하고 이 한 페이지짜리 대시보드에 실제 설정 화면이 있어야 하는지는 위임.
   ② Settings 항목을 내비게이션과 ⌘K 팔레트 양쪽에서 제외 — 대신 Overview/Activity feed/Region map/Region stats 네 항목만 두고 전부 실제로 존재하는 앵커(#top/#feed/#map/#region-table)로 연결.
   ③ 존재하지 않는 `#settings`로 스크롤되는 "죽은 링크"를 만드는 대신, 실제로 뭔가가 있는 곳만 내비게이션에 넣는 쪽을 선택.

9. ① **테이블 colgroup 퍼센트와 Status 셀의 글자 처리**는 "퍼센트가 실제로 들어맞아야 한다"는 원칙만 있고 구체 수치는 위임.
   ② 390px 기준 카드 내부 실폭(~326px)에서 각 열 %×326−8(패딩)을 직접 계산해 Region 24 / Status 13 / Incidents 12 / Uptime 18 / p50 16 / Req/s 17로 배분하고, Status 칸은 테두리 pill 없이 `text-xs` 2–4자 코드("OK"/"DEG"/"DOWN")로 — 가장 긴 "DOWN"이 들어갈 여유가 간신히 양수가 되도록 폰트 크기까지 조정.
   ③ 이전 라운드(Fluxgraph) 기록에 있던 "패딩 가진 장식 Badge를 좁은 열에 쓰면 퍼센트를 늘려도 패딩이 여유를 갉아먹는다"는 교훈을 그대로 적용 — 처음엔 Badge 컴포넌트를 쓰려다 계산 중 음수 여유를 발견하고 순수 텍스트로 교체.

10. ① **에페메럴 호버 툴팁이 패널 가장자리 리전에서 뷰포트를 넘지 않게 하는 방법**은 브리프에 전혀 언급 없음.
    ② 각 리전의 좌표(`leftPct`)를 20%/80% 기준으로 start/center/end 3구간으로 나눠, 가장자리 리전은 툴팁을 같은 쪽 가장자리에 고정(`left-0` 또는 `right-0`)하고 가운데 리전만 중앙 정렬(`left-1/2 -translate-x-1/2`).
    ③ 176px 너비 툴팁을 항상 중앙 정렬하면 좌측 끝 리전(북미 서부)에서 음수 오프셋이 발생해 390px에서 페이지 가로 스크롤을 유발할 수 있다는 걸 좌표를 직접 대조하며 발견하고 고침.

11. ① **헥스 테두리 선 투명도와 범례 스와치 테두리**는 "코로플레스는 항상 보이는 숫자/범례를 가져야 한다"는 원칙만 있고 구체 스타일은 위임.
    ② 처음엔 거의 보이지 않는 `rgba(255,255,255,0.08)` 테두리로 설계했다가, 가장 어두운 램프 단계(#27272a)가 카드 배경(zinc-900, #18181b)과 명도 차이가 거의 없어(계산상 대비 ≈1.19:1) 헥스 자체가 "구멍"처럼 보인다는 걸 발견 — 테두리를 `rgba(255,255,255,0.28)`로 올리고 범례 스와치에도 `border-white/25`를 추가.
    ③ 램프의 "강도" 의미는 채움색 간의 차이가 담당하고, 테두리의 역할은 그것과 별개로 "이 모양이 하나의 리전이다"라는 경계를 항상 보이게 하는 것 — 두 역할을 분리해서 풀기로 결정.

12. ① **탑바의 "주요 액션" 버튼이 무엇을 해야 하는지**는 앱 셸 요구사항에 버튼이 있어야 한다고만 명시.
    ② "View all regions" 링크로 구현해 클릭 시 실제로 `#region-table`로 스무스 스크롤.
    ③ 클릭해도 아무 일도 일어나지 않는 죽은 컨트롤을 만들지 않기 위한 선택 — 과거 라운드 심사에서 이 부분이 실제로 점검된 전례가 있음.

13. ① **아바타 이니셜의 접근성 이름 구성 방식**은 "사진 대신 이니셜"이라는 제약만 있고 라벨 구성은 위임.
    ② 이니셜 뱃지는 `aria-hidden`으로 장식 처리하고, 버튼 자체에는 별도 `aria-label`을 달지 않음 — 사이드바 쪽은 이름("Reese Shin")이 버튼의 보이는 텍스트 콘텐츠로 포함되어 그 자체가 접근성 이름이 되고, 탑바 쪽(이니셜만 보이는 좁은 버튼)은 바로 옆의 "Account" `aria-label` 메뉴 패턴을 그대로 따름.
    ③ 라벨을 따로 달면 그 문자열이 보이는 텍스트와 항상 일치해야 한다는 제약을 매번 지켜야 하므로, 보이는 콘텐츠만으로 접근성 이름을 구성할 수 있는 자리에서는 그렇게 하는 쪽이 더 단순하고 안전하다고 판단.
