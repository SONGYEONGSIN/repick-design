# auto-landing-r22 후보 a — The Case File

**한 줄 컨셉**: 히어로 안에서 "인스펙션 강도 × 비교 기간" 두 이산 세그먼트를 조작하면 Exhibit A(신뢰도·추천가·체크리스트·회전일수) 증거 카드가 즉시 재계산되고, 같은 9칸 고정값이 아래 Exhibit B 감도표(클릭 가능한 표)와 클로징 CTA 요약까지 그대로 이어지는 "사건 파일" 형태의 repick 랜딩.

## 브리프에 없던 것

1. **accent 색상 계열 선정과 대비 계산**
   - ① 무엇을 정해야 했나: 최근 3라운드 승자축(sky/teal/amber)과 겹치지 않는 새 accent 계열을 고르고, 정본 기본값(violet #6E56CF)이 요구하는 "큰 면적/대형텍스트는 base accent, 소형은 밝은 틴트, accent 채움 위 소형텍스트는 흰색" 구조를 새 계열에 맞게 다시 계산해야 했다.
   - ② 무엇으로 정했나: 루비/로즈 계열 `ACCENT = #D6336C`, `ACCENT_BRIGHT = #F5A3C7`. WCAG 상대휘도 공식으로 직접 계산: `#D6336C` vs 배경 `#0B0B0F` → **4.26:1**(대형 텍스트·큰 면적 채움만 통과, 본문 크기 미달 — 정본 violet의 3.73:1과 동일한 구조). 흰색 텍스트 vs `#D6336C` 채움 → **4.62:1**(소형 텍스트도 AA 통과). 어두운 잉크(`#0B0B0F`) vs `#D6336C` 채움 → **4.26:1**(19px 미만에서 AA 미달 — 그래서 CTA·세그먼트 활성 버튼·이메일 제출 버튼은 전부 흰색 텍스트로 고정하고 어두운 잉크는 쓰지 않았다). `ACCENT_BRIGHT = #F5A3C7` vs 배경 → **10.24:1**(아이콘·포커스링·소형 강조 텍스트용, 정본 예시의 9.1:1과 같은 여유폭).
   - ③ 왜: 브리프가 "accent 계열은 자유이나 계산해서 문서화하라"고 명시했고, 정본 violet의 3단 구조(큰 면적 accent / 소형 틴트 / 채움 위 흰색)를 그대로 다른 색상에 이식하는 것이 가장 안전하다고 판단했다(관행 재사용). 계산은 sRGB 상대휘도 공식(선형화 후 0.2126R+0.7152G+0.0722B)을 손으로 적용했다.

2. **본문 폭 px 계산 (65~75자, `ch` 단위 금지)**
   - ① 무엇을 정해야 했나: 브리프가 명시한 "Pretendard 영문 혼합 평균 자폭 0.44em" 상수로 70자 목표를 px로 역산해야 했다(`ch`는 금지).
   - ② 무엇으로 정했나: 본문 16px 기준 `70 × 0.44 × 16 = 492.8px` → **492px**를 모든 본문 단락(히어로 서브헤드, Exhibit B 인트로, 클로징 문단)에 `max-w-[492px]`로 통일 적용. 이메일 폼은 별도로 `max-w-[380px]`(라벨+입력 UI, 산문 아님이라 자수 계산 대상 아님).
   - ③ 왜: 정본 v21 코드(같은 저장소, `(marketing)/v21`)가 동일한 폰트 크기·같은 0.44em 상수로 이미 492px를 쓰고 있어 계산이 일치함을 확인했고, 관행과 계산 둘 다 일치하므로 그대로 채택했다.

3. **390px 셀 겹침 회피 — 지난 라운드 실패(cell-overlap) 재발 방지**
   - ① 무엇을 정해야 했나: `table-fixed` 전환이 지난 라운드에서 390px 모바일 셀 텍스트 겹침을 낳았던 전례가 있어, Exhibit B 감도표(4열×4행)를 같은 함정 없이 구현해야 했다.
   - ② 무엇으로 정했나: `min-w-[500px]`를 **`<table>` 엘리먼트 자체**에만 걸고(`<td>`/`<th>` 어디에도 min-width를 걸지 않음), `<colgroup>`으로 28%/24%/24%/24% 퍼센트 열배분, 셀은 기본 `whitespace-normal` + `px-3 py-3` 패딩으로 줄바꿈을 허용했다. 표는 항상 `overflow-x-auto` 래퍼 안에 두어, 데스크톱(컨테이너 폭이 500px보다 훨씬 넓음)에서는 스크롤이 전혀 생기지 않고 390px(사용 가능 폭 약 342px < 500px)에서만 래퍼 내부 가로 스크롤이 걸리게 했다. **검증 방법**: 500px 최소폭을 4열로 나누면 라벨열 140px·데이터열 각 120px이 되고, 그 안에 들어가는 가장 긴 문자열("Forensic", "$532 · 6d", "97%")의 11~15px 텍스트가 한 줄에 20자 이상 들어갈 공간이 있음을 자로 재듯 계산해 겹침이 물리적으로 불가능함을 확인했다. 실제 브라우저 렌더링 스크린샷 캡처는 이 세션(Read/Grep/Write만 허용, dev 서버 실행은 오케스트레이터 담당)에서 직접 실행할 수 없었으므로, 대신 (a) `<table>`에만 min-width가 걸려 있는지 grep으로 재확인, (b) 콜그룹 퍼센트 합이 100%인지 산술 재확인, (c) 위 폭 계산을 라인별로 다시 검산하는 방식으로 정적 검증했다 — 이 세 가지 모두 통과했다.
   - ③ 왜: 재배정 지침이 정확히 이 실패(테이블 가로 오버플로 → `table-fixed` 전환 → 390px 셀 겹침)를 지목했고, 지침이 제시한 해법(모바일 전용 스크롤 래퍼 + `<table>` 자체 min-width)을 문자 그대로 따랐다.

4. **Exhibit A/B 9칸 고정값 매트릭스 설계**
   - ① 무엇을 정해야 했나: "강도(3) × 기간(3)" 조합마다 신뢰도·추천가·회전일수가 어떤 방향으로 움직여야 그럴듯한지 정해야 했다(브리프는 두 축의 존재만 요구, 구체적 수치·방향성은 없음).
   - ② 무엇으로 정했나: 신뢰도는 강도·기간 둘 다에 비례해 상승(78→97%), 추천가는 강도에 비례해 상승하되 기간이 넓어질수록 완만히 하락(오래된 저가 매물이 평균에 섞임), 회전일수는 둘 다에 반비례해 감소(14일→4일). 모두 하드코딩된 9칸 표(`METRICS` 상수)로, 조작 시 계산이 아니라 이 표에서 읽어오기만 한다.
   - ③ 왜: "조작=가치체감"을 만족시키되 "죽은 마크업"(고정된 하나의 숫자만 보여주는 위장 인터랙션)이 되지 않도록, 9개 조합 모두가 서로 다른 값을 갖고 방향성이 일관되게(더 깊은 검수·더 넓은 비교 = 더 믿을 만함) 설계했다. 무작위 대신 고정 표를 쓴 것은 기계 검증 규칙(Math.random 금지, 결정론)을 따른 것이다.

5. **체크리스트 깊이(4/6/8개)와 forensic 단계의 flagged 항목**
   - ① 무엇을 정해야 했나: "통과 체크리스트"가 강도에 따라 어떻게 달라져야 하는지, 전부 통과로만 채울지 정해야 했다.
   - ② 무엇으로 정했나: Standard 4개 → Deep 6개(상위 집합에 광학/기계 검사 추가) → Forensic 8개(센서 이미징·소유이력 대조 추가)로 설계했고, Forensic의 "센서 이미징" 한 항목만 `flagged`(먼지 미세 흔적, 화장품적 결함으로 통과에는 영향 없음)로 표시해 "가장 깊은 검수가 항상 완벽한 결과만 보여주는" 부자연스러움을 피했다.
   - ③ 왜: 색상만으로 pass/flagged를 구분하지 않기 위해 아이콘(CheckCircle2/AlertTriangle)과 텍스트("Passed."/"Flagged.")를 병행했고, 더 깊은 검수일수록 더 많은 것을 발견한다는 서사가 "Forensic이 비쌀 이유"를 뒷받침하도록 의도했다.

6. **디스플레이 활자 배정 확인**
   - ① 무엇을 정해야 했나: 배정된 `--font-display-grotesk` 하나만 쓰고 두 번째 디스플레이 계열을 섞지 않아야 했다.
   - ② 무엇으로 정했나: h1·h2(디스플레이용, Exhibit B/클로징/소셜프루프 대형 스탯)에만 인라인 `style={{ fontFamily: "var(--font-display-grotesk)" }}` + `fontWeight: 800`을 적용했고, 본문·라벨·버튼 텍스트는 전부 Tailwind 기본(`--font-sans`, Pretendard)로 남겼다.
   - ③ 왜: 저장소 `globals.css`를 확인한 결과 `--font-display-grotesk`가 `@font-face`로 이미 전역 등록되어 있어 추가 `next/font` import 없이 CSS 변수만 참조하면 되는 구조였다(v16 관행 그대로).

7. **폰트 웨이트 정확히 3종 확정 (400 / 600 / 800)**
   - ① 무엇을 정해야 했나: "웨이트 정확히 3종"을 렌더 실측 기준으로 지켜야 했는데, 초안에는 Tailwind `font-bold`(700)와 인라인 `fontWeight: 800`이 섞여 4종이 될 뻔했다.
   - ② 무엇으로 정했나: `font-bold`(700) 사용을 전부 `font-semibold`(600)로 교체해, 최종적으로 `font-normal`(400, 본문) / `font-semibold`(600, 라벨·버튼·강조 텍스트) / 인라인 `fontWeight:800`(디스플레이 헤드라인·대형 스탯) 3종만 남겼다. 모든 `<th>`·`<caption>` 등 브라우저 기본 굵기를 가진 엘리먼트에도 `font-semibold`를 명시해 UA 기본값(bold=700)이 섞이지 않게 했다.
   - ③ 왜: 기계 검증이 렌더된 실제 웨이트 종수를 세기 때문에, 흔히 놓치는 `<th>` 기본 굵기와 Tailwind `font-bold` 잔존을 grep으로 전수 검사해 제거했다.

8. **본문 소재 선정 (시계, 소매가 $780)**
   - ① 무엇을 정해야 했나: repick이 중고거래하는 구체적 매물을 정해야 했다(브리프는 마켓플레이스 성격만 지정).
   - ② 무엇으로 정했나: "Vintage Chronograph, Steel Case and Bracelet"라는 범용 시계 매물로 정하고, 이미지는 저장소 내 다른 승격작(v21)이 이미 검증해 쓰고 있는 동일 Unsplash 고정 ID(`photo-1523275335684-37898b6baf30`)를 재사용했다. 소매가 $780을 기준으로 9칸 추천가($480~$532)의 할인율을 `Math.round(((780-price)/780)*100)`로 매번 계산해 32~38% 범위가 나오게 했다.
   - ③ 왜: 시계는 "Forensic 단계의 소유이력 대조(도난/분실 등록 조회)"라는 카피와 자연스럽게 맞물리고, 이미 저장소에서 렌더가 검증된 이미지 ID를 재사용해 깨진 이미지 리스크를 최소화했다.
