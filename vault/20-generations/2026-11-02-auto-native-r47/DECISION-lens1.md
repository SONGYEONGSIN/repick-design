# Lens 1 (DNA/brief compliance) — auto-native-r47

## Ranking
1. a — the only candidate whose bottom band is genuinely a blocked-workflow state machine, and it implements the hardest requirement in §3/§4 correctly and in full: the jump action really scrolls (`FlatList.scrollToIndex`) *and* moves accessibility focus to the exact blocking row (`AccessibilityInfo.setAccessibilityFocus` via a per-question node ref), not a relabel.
2. c — correctly recognizes this screen does *not* fit a global band at all (independent, repeatedly-destructive per-row redemptions) and applies the catalog's row-level destructive-confirm idiom instead, with the single-live-region invariant enforced across rows by construction (`activeRewardId`/`rowPhase` as one shared pair).
3. b — a defensible but looser fit of the "selection-derived contextual bar" form (built for a single nullable id, not the documented `selectedCount > 0` multi-select case), and its terminal action (`Confirm & Buy`) is a true no-op with zero feedback of any kind — technically compliant with the a11y-hint rule but the weakest demonstration of "the band does work."

## Per-candidate detail

### a — `native/src/evolve/r47/a/InstantTradeInScreen.tsx`, `data.ts`
**Band shape (§3).** This screen is a genuine blocked workflow (an offer cannot be computed/revealed until every condition question is answered), so the state-machine band is the correct form, not a reused habit. The band runs three real shapes in sequence — `blocked` → `primed` → `offered`→(`accepted`|`declined`) — driven by a single derived `phase` (`InstantTradeInScreen.tsx:132-138`), not a boolean toggle.
- **Jump action genuinely works**: `jumpToQuestion` (`InstantTradeInScreen.tsx:140-149`) calls `listRef.current?.scrollToIndex(...)` and then, after a fixed 260ms delay, resolves the specific row's own `View` node via `findNodeHandle` and calls `AccessibilityInfo.setAccessibilityFocus(tag)` — this is the real scroll+focus behavior the brief calls out, not a relabeled button. Rows register themselves via `setRowRef` keyed by question id (`InstantTradeInScreen.tsx:183-186`), so the right row is targeted. `onScrollToIndexFailed` is handled (`InstantTradeInScreen.tsx:263-268`), a reasonable robustness touch for FlatList virtualization.
- **Single blocking-condition type**: all blocking is "which question is still unanswered," so `firstUnanswered` always names the actually-blocking item (`InstantTradeInScreen.tsx:124,168`) — the "route to whichever is actually blocking" requirement is trivially and correctly satisfied since there's only one kind of blocker here.
- **Re-blocking on edit**: changing any answer after reveal resets `revealed`/`decision` (`InstantTradeInScreen.tsx:151-157`), so a stale offer can't be silently accepted — matches the screen's own stated contract in its header comment (`InstantTradeInScreen.tsx:26-27`).
- **Destructive-ish decision as band buttons**: `offered` phase turns the band itself into an Accept/Decline two-button row (`InstantTradeInScreen.tsx:302-336`) inside the already-`accessibilityLiveRegion="polite"` container (`InstantTradeInScreen.tsx:271`) — consistent with the catalog's "band becomes Cancel/Confirm" idiom, applied to an accept/decline decision rather than literally a withdrawal, which is a reasonable extension.

**Accessibility (§4).**
- Exactly one live region on screen: the whole `offerBand` View carries `accessibilityLiveRegion="polite"` (`InstantTradeInScreen.tsx:271`), and in every phase branch only the one sentence that actually changed carries `accessibilityRole="alert"` (`InstantTradeInScreen.tsx:282,297,304,339,357`) — never two alerts in the same phase.
- No `accessible={true}` anywhere in the file (confirmed by repo-wide grep across r47).
- No `accessibilityHint` is used anywhere in this file at all, so there is no possibility of a hint promising unimplemented behavior.
- Radio semantics for condition options are correct: `accessibilityRole="radiogroup"` on the group (`InstantTradeInScreen.tsx:82-85`), `accessibilityRole="radio"` + `accessibilityState={{selected, checked: selected}}` per option (`InstantTradeInScreen.tsx:93-94`).

**Tokens/DNA (§2/§3 top).** All colors route through `tokens.color.*`/`tokens.space()`/`tokens.radius.*`; no hardcoded hex anywhere in the file (confirmed by grep). Accent is used only for selection/emphasis states (selected option marker, offer card border/bg, primed CTA, accept state) — consistent with "near-monochrome + single accent only for emphasis." No emoji, no decorative motion.

**Determinism (§5) / English-only.** `data.ts` is all fixed literals and pure functions (`computeOfferUsd`, `totalDeductionUsd`) — no `Math.random`/`Date.now`/bare `new Date()`. All copy is English.

**RN idioms (§1).** Uses `FlatList` (not `.map()`) for the question list, `Pressable` for every tappable, `SafeAreaView` top wrapper, `StyleSheet.create`. Header notes the style keys (`offerBand*`, `questionRow*`, `optionChip*`) were written fresh rather than copied from other catalog screens' `dockedBar*`/`deadlineDock*` keys — I did not have those other screens open to literally diff key-for-key, but nothing in this file's key names overlaps with anything I saw in b or c, and the names read as domain-specific.

### b — `native/src/evolve/r47/b/StoreCreditTopUpScreen.tsx`, `data.ts`
**Band shape (§3).** Band presence is correctly derived from state, not an imperative flag: `selectedPackage` is `null` until a tile is tapped, and the band's own JSX is gated on it (`StoreCreditTopUpScreen.tsx:168`, `const selectedPackage = findCreditPackage(selectedPackageId)` at `:63`). This is the right instinct (verified visually too — both `b-390.png`/`b-768.png` show the initial, no-selection state with **no band rendered at all**, matching the code).
- However, GENERATION.md's documented third band form is specifically a **multi-select, `selectedCount > 0`-derived** contextual bar (the `r16/b` precedent, explicitly contrasted with "a boolean toggle"). This screen is a **single**, mutually-exclusive radio selection (`CreditPackageTile` uses `accessibilityRole="radio"`, `StoreCreditTopUpScreen.tsx:246`) with a nullable id, not a count. The file's own header comment acknowledges this is "the single-nullable-id shape of the family" (`StoreCreditTopUpScreen.tsx:22-25`) — a reasonable adaptation, but it is not the literal form the brief validates, and a single radio selection driving a CTA bar is arguably just as easily read as the first page of a two-step **blocked purchase flow** (can't check out without picking a package) dressed as form 3. I'm not docking this hard since the presence-derivation logic itself is sound and matches the letter of "band exists iff selection state says so," but it's a looser citation than a's or c's.
- The `select → confirm` step reuses the same single live-region container rather than mounting a second region (`StoreCreditTopUpScreen.tsx:169-218`), which correctly applies the catalog's "band becomes Cancel/Confirm" idiom for a real-money purchase — `Change package` / `Confirm & Buy` (`StoreCreditTopUpScreen.tsx:189-216`).
- **Weakness**: `handleConfirmPurchase` (`StoreCreditTopUpScreen.tsx:77-81`) is a complete no-op — no new phase, no visual or live-region change, nothing. The comment at `:78-80` is honest about why, and because no `accessibilityHint` promises a result (confirmed by grep — only the `Change package` button has a hint, and it is accurate: `:194`, matching `handleChangePackage` at `:73-75`), this does not break the explicit §4 hint rule. But per §3's core test — "a valid band does work; the question is whether pressing it does something real" — the terminal tap does strictly nothing observable, which is a materially weaker demonstration than a's full accepted/declined terminal states or c's "Redeemed… new balance is now N" acknowledgment.

**Accessibility (§4).** Exactly one live region exists on the whole screen (`creditBand`, `StoreCreditTopUpScreen.tsx:169`), gated the same way the band itself is, so it's never duplicated. No `accessible={true}` anywhere (confirmed by grep). The one `accessibilityHint` present is truthful.

**Tokens/DNA.** No hardcoded hex (confirmed by grep); all through `tokens.*`. One point worth flagging for the exercise: `tokens.color.success` is used for the "bonus credit" figure (`StoreCreditTopUpScreen.tsx:349,390`) — tokens.ts documents `success` as the "covered/eligible-green" semantic (`tokens.ts:23`), not a general positive-amount color. This is a plausible, common reuse (bonus = good news) but is outside the color's documented role, and is worth flagging per the task's instruction to check for off-role token use. It is minor and I would not weight it heavily.

**Determinism/English-only/RN idioms.** `data.ts` is fixed literals only, no `Math.random`/`Date.now`/bare `new Date()`. All copy English. Uses `FlatList` with `numColumns={2}` for the tile grid, `Pressable`, `SafeAreaView`, `StyleSheet.create`.

### c — `native/src/evolve/r47/c/PointsRedemptionScreen.tsx`, `data.ts`, `RewardRow.tsx`
**Band shape (§3/§4).** This candidate's defining move is recognizing that a global bottom band is the *wrong* shape for this screen and not building one. Each reward redemption is an independent, repeatable destructive action (irreversible point spend) in a list — exactly the scenario GENERATION.md's §4 addition describes for *row-level* destructive confirm instead of a band ("전역 게이트가 자연스럽지 않은 화면... 행 단위로", citing the `r22/b` Active Sessions precedent). The header comments at `PointsRedemptionScreen.tsx:17-31` and `RewardRow.tsx:1-23` state this reasoning explicitly and it matches the catalog text closely, not just a domain reskin.
- **Single live region, enforced by construction**: `activeRewardId` and `rowPhase` are one shared pair of state on the parent, not a per-row boolean (`PointsRedemptionScreen.tsx:46-47`), so only one row can ever be in `confirm` or `done` phase at a time — `requestRedeem` explicitly finalizes a previous row's "done" acknowledgment before handing the slot to a new one (`PointsRedemptionScreen.tsx:64-76`). This makes "never two live regions at once" structurally guaranteed rather than just locally true per-row.
- Each row's `confirm` phase is itself rendered inside `accessibilityLiveRegion="polite"` with `accessibilityRole="alert"` only on the one sentence that changed (`RewardRow.tsx:92-95`, `126-131`) — correct application of the exact pattern from §4, at row granularity.
- A reward costing more than the balance renders a genuinely disabled control (`disabled` prop, `accessibilityState={{disabled:true}}`) with a visible/announced reason ("Need N more points," `RewardRow.tsx:79-88`) — this is the opposite of the "disabled button with no explanation" anti-pattern §3 calls out, even though it's a row control rather than a band.

**Accessibility (§4).** No `accessible={true}` anywhere (confirmed by grep; `RewardRow.tsx:20-23` states this deliberately). Both `accessibilityHint`s present are accurate: "Opens a confirmation for this redemption, in place" (`RewardRow.tsx:68`) matches `onRequestRedeem` flipping the row to `confirm`; "Spends the points shown and applies this reward" (`RewardRow.tsx:114`) matches `confirmRedeem` actually deducting balance (`PointsRedemptionScreen.tsx:83-94`) — no false promises.

**Tokens/DNA.** No hardcoded hex (confirmed by grep). `tokens.color.accent` is used for the points balance and each reward's cost figure — this is a non-interactive numeric emphasis use, which fits the DNA rule's framing ("near-monochrome + single accent only for emphasis") more literally than treating accent as button-only. `tokens.color.success` is used once, for the "Redeemed…balance is now N" acknowledgment text (`RewardRow.tsx:272`) — closer to a legitimate "successful action completed" reading than b's "bonus" usage, though still outside the literal "covered/eligible" doc comment in `tokens.ts:23`.

**Determinism/English-only/RN idioms.** `data.ts` is all fixed literals (`STARTING_BALANCE`, fixed `REWARDS` array); `formatPoints` uses `toLocaleString("en-US")` on a fixed input, not a clock read. `REDEEM_ACK_MS = 1400` is a fixed constant, not derived from `Date.now()`. All copy English. Uses `FlatList` with `extraData` correctly covering the three pieces of state that affect row rendering (`PointsRedemptionScreen.tsx:114`), `Pressable`, `SafeAreaView`, `StyleSheet.create`.
