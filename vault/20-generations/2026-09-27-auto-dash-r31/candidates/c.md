- 아키타입: 트리/분해 콘솔(신규 매크로 골격), 지배 시각화 = Decomposition Tree — charts.catalog "Root Cause Analysis" 최초 사용
- 테마: light · 액센트: cyan · 디스플레이 활자: `--font-display-grotesk`
- 인터랙션 5종: ① 카테고리/하위카테고리 확장·축소(네이티브 `<button aria-expanded>`, 키보드 자동 지원) ② 리프 pin(클릭/Enter) → 인스펙터 패널만 갱신(narrow scope) ③ 비영속 hover/focus(리프) → readout 줄에 트렌드+마지막 발생 시각 노출, 가드+키보드 페어링 ④ 인스펙터 관련 티켓 테이블 실제 정렬 ⑤ 검색 필터(카테고리/하위/리프명 매치, 하이라이트)
- 항상-노출 값: 트리의 모든 행(카테고리·하위카테고리·리프)이 항상 건수+비중%를 텍스트로 병기 — hover는 "추가" 정보(트렌드·마지막 발생)만 준다는 점에서 r7/r9/r10 계보(상시값 vs hover값 분리)를 트리형에 적용한 사례
- 헤더는 4타일 KPI 그리드 대신 인라인 pill 3개(Total tickets/Resolution rate/Avg resolution) — r27→r28 델타가 지목한 "KPI행이 차트와 공동주역일 때 비용" 위험을 grid 자체를 안 써서 회피
- 기본 상태: 전 카테고리·하위카테고리 기본 확장(데이터가 26행 규모라 완전 펼침이 가독에 무리 없음) + pin 기본값 = 최다건수 리프(Mid-cycle plan proration, 84건) → 인스펙터가 첫 페인트부터 채워짐(r30 델타 회피)

## 브리프에 없던 것

1. **트리를 ARIA `role="tree"`로 마크업할지 여부** — 브리프·코어 어디에도 트리 위젯의 정확한 ARIA 패턴을 지정하지 않는다. 처음엔 `role="tree"`를 컨테이너에 걸었는데, 완전한 `role="group"`/`role="treeitem"` 자식 구조 없이는 axe `aria-required-children`이 걸린다는 것을 게이트로 알게 됐다 — 완전한 tree 패턴을 구현하는 대신 관례를 버리고 평범한 `<div>`+네이티브 `<button aria-expanded>` 조합으로 되돌렸다(시각적 헤딩이 이미 섹션명을 제공하므로 접근성 손실은 없다고 판단).
2. **기본 전체-펼침 vs 부분-펼침** — 스킬 본문 예시("root + 첫 카테고리만 기본 펼침")를 따를지, 데이터 규모(26행)를 감안해 전체를 펼칠지는 정해진 바 없다. 데이터가 작아 전체 펼침이 스크롤 부담 없이 즉시-가독을 높인다고 판단해 전체 펼침으로 정했다 — 접기 인터랙션 자체는 여전히 실동작(collapse 가능)이라 요구된 "확장·축소" 인터랙션 자격은 유지된다.
3. **리프 행의 pin 아이콘 배치** — 브리프는 "pin"이라는 개념만 요구하고 UI 표현은 안 정한다. lucide `Pin` 아이콘을 리프 행 맨 앞에 두고 pin 상태에서 `fill`을 채워 넣어 시각적으로 명확히 구분했다 — 다른 후보(a의 박스 강조, b의 링 fillOpacity)와 겹치지 않는 표현을 의도적으로 골랐다.
