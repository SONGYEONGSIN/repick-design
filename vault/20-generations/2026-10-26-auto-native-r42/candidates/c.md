# Candidate c — Split-Pay Plan Selector

Built `SplitPayPlanSelectorScreen` (`native/src/evolve/r42/c/SplitPayPlanSelectorScreen.tsx` + `data.ts`): a buyer-facing pre-checkout screen for one item purchase, letting the buyer choose a payment-TIMING plan — "Pay in Full" (one charge today, no fee), "Pay in 4" ($30.75 × 4 biweekly, $3.00 fee), or "Pay in 12" ($10.75 × 12 monthly, $9.00 fee) — against a fixed dummy item ("Vintage Leather Moto Jacket, Size M", $120.00). The gate "check" render-string is the header heading, `"Choose How You'll Pay"`. The three plans render as fixed comparison radio-cards via `.map()` over a 3-item array (`PLAN_DEFINITIONS`), each card an `accessibilityRole="radio"` `Pressable` with `accessibilityState={{ selected }}`, single-select against one `selectedPlanId: PlanId | null` state. The band below the cards is gated purely by `const hasSelection = selectedPlanId !== null;`, recomputed every render and used directly in the JSX conditional (`{hasSelection && selectedPlan && <PlanBand .../>}`) — there is no separately-tracked `showBand` flag. A second, independent `confirmed` boolean controls only the band's *content* (pre-confirm date/CTA vs. a confirmed summary with a "Change Plan" escape hatch), and switching to a different plan while confirmed resets `confirmed` to false without touching whether the band is present at all. The one live region on the screen wraps the band's mount point; the `accessibilityRole="alert"` text inside it changes both when the band first appears (plan name + "selected") and when "Confirm Plan" is pressed (plan name + "confirmed").

## Brief gaps

- Decision: what the first-payment date should be and whether it varies per plan. Decided: a single fixed hardcoded date, "Nov 9, 2026", shown identically regardless of which plan is chosen (only the per-installment amount next to it changes). Why: the brief's own example string was this exact date, and in practice the *first* charge timing is the same moment (today/next cycle) no matter which plan is picked — only how many charges follow differs — so varying it per plan would have been invented complexity with no real-world basis.
- Decision: what "Confirm Plan" should actually do, since it must "do something real" but this screen has no real checkout backend to call. Decided: a purely local state flip (`confirmed`) that swaps the band's content to a confirmation summary and exposes a "Change Plan" undo, rather than any navigation or fake async call. Why: this mirrors the existing-codebase convention (seen in sibling evolve rounds) of local-only confirmation swaps for screens with no real network side effect, and avoids writing an `accessibilityHint` that would promise navigation that doesn't happen.
- Decision: how to price the two installment plans so the per-payment math divides cleanly (since the brief didn't give exact numbers, only "small fee" / "larger fee"). Decided: item price $120.00, Pay-in-4 fee $3.00 (total $123.00 ÷ 4 = $30.75), Pay-in-12 fee $9.00 (total $129.00 ÷ 12 = $10.75) — both exact to the cent with no rounding remainder. Why: arbitrary choice, but constrained to avoid a screen that visibly mis-sums (e.g. 4 × $30.75 must equal the displayed total exactly) since this is a financial screen where that kind of inconsistency would read as a bug.
