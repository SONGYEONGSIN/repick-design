## Concept
An append-only Security Activity Log (logins, failed attempts, device verifications, password changes) with a persistent bottom action bar that genuinely signs other devices out (stamping their rows) and genuinely reports flagged entries, both confirmed in place through a single polite live region — not a sessions manager, not a native Alert.

## 브리프에 없던 것

1. ① How "Sign Out Other Devices" can produce a visible change on a screen explicitly described as read-only/append-only history, without turning it into a sessions-manager. ② Treated each historical `signIn` row as still "open" until stamped, and had the action add a `sessionEndedIso`/`sessionEndedDisplay` field onto that specific row (rendered as a muted "Session ended …" line) rather than deleting/mutating the row's core content or inventing a parallel "sessions" list. ③ Followed the brief's own parenthetical literally ("marks all non-current device rows as signed-out with a timestamp") — it already resolves the read-only-history vs. live-action tension without needing a second data model.

2. ① Whether "Report Suspicious Activity" needs the same destructive Cancel/Confirm treatment as sign-out. ② Made it a single-press, immediately-executing action (no confirm step) since it's additive/non-destructive (nothing is lost, sessions aren't ended), while sign-out keeps the two-button confirm row. ③ The brief only mandates the Cancel/Confirm pattern for "destructive/irreversible" actions; reporting doesn't fit that, so adding a confirm step there would be unearned friction.

3. ① How to visually separate three severities (plain sign-in, password-changed, new-device-verified, failed-login) into just "normal vs. flagged" per the brief while still giving each kind distinct meaning. ② Mapped `signIn`→neutral (no tint), `passwordChanged`→success tint (a deliberate, positive security action), `deviceVerified`→warning tint (flagged, but not malicious), `signInFailed`→danger tint (flagged, worst case). "Flagged" = warning ∪ danger. ③ Reuses the existing success/warning/danger token triad instead of collapsing everything into a binary red/not-red, which better matches a real security log's gradations while staying within the token palette (no new hues).

4. ① Whether the live region should be a single static container or should swap between idle/active content types. ② Kept exactly one `View[accessibilityLiveRegion="polite"]` containing exactly one `Text` node whose content toggles between a static idle hint ("No pending security alerts…") and the dynamic confirm/result message, applying `accessibilityRole="alert"` only when a message is present. ③ Directly satisfies the "exactly one live region, alert role only on the node whose content just changed" rule without needing to mount/unmount separate alert nodes per action.

5. ① What "now" means for timestamps stamped by the two actions, given no `Date.now()`/`new Date()` is allowed. ② Hand-picked one fixed constant (`ACTION_NOW_ISO` / `ACTION_NOW_DISPLAY`, Oct 6 9:00 AM) in `data.ts`, placed just after the most recent historical entry (8:02 AM same day), used for both actions' stamps. ③ Keeps full determinism while still reading as "this just happened, chronologically after everything else in the log."

6. ① Device/location vocabulary for entries not tied to a real backend shape. ② Invented `deviceName` ("MacBook Pro — Chrome"), `location` ("city, region, country" or "Unknown location (VPN detected)" for the suspicious case), `summary` (plain-English sentence per row) and `kind`/`severity` as separate fields (kind = what happened, severity = how to render it) from scratch. ③ Arbitrary but internally consistent naming, chosen to avoid any overlap with a hypothetical "sessions" screen's field names per the brief's instruction.
