# Candidate c — Pickup & Inspection Schedule

A calendar-centric ops console for repick's logistics team: a month/week calendar of inspector capacity is the hero, with always-visible per-day booked-hours + pickup-count, a pinned-day detail panel, a week-scoped capacity sparkline that only updates on a week change, and an independent, self-contained sortable Pickup Queue table for the current operating week.

## 브리프에 없던 것

**Product framing**
① What internal product/team to invent ② "repick Ops — Pickup & Inspection Schedule," a logistics-ops console for scheduling item pickups/on-site inspections across a metro hub ③ The brief's suggested angle (pickup & inspection scheduling console) maps directly onto a calendar without forcing task-board semantics, and gives every metric (inspector hours, grading backlog) a concrete operational meaning instead of generic "events."

**Fixed reference "today"**
① The brief explicitly bans `new Date()`/`Date.now()` even for "today," and calls this out as the single most tempting trap in a calendar concept ② Hardcoded `TODAY_ISO = "2026-08-31"` in `data.ts`, one day after this generation's run date (2026-08-30) ③ I verified via a from-scratch civil-calendar algorithm (Howard Hinnant's `days_from_civil`/`civil_from_days`, pure integer math, no `Date` object anywhere) that 2026-08-31 is a **Monday** — which lets it double as day 1 of its own week, so the default "pinned week" is clean (Mon Aug 31 – Sun Sep 6) instead of starting mid-week. I hand-verified this independently against a known anchor (2026-01-01 = Thursday, derived by counting days-of-year from 2024-01-01 = Monday, a leap year, +366 mod 7) before trusting the algorithm.

**Accent color vs. state colors**
① Brief requires a single deliberate accent, warns off violet/indigo (overused) and cyan/rose (used in the project's last two dash rounds), and separately warns not to let capacity-state colors collide conceptually with the brand accent ② Brand accent: **teal-700 `#0f766e`** (used only for interactive/brand meaning: active nav pill, primary button, focus outline, "today" bubble, selected-day border). Capacity-intensity tiers use **zinc/amber/red only** — teal never appears in a capacity tier ③ Computed contrast (WCAG relative-luminance formula, by hand): teal-700 text/icon on white = **5.47:1** (passes 4.5:1 body-text floor); white text on teal-700 background = same ratio by symmetry, so the active nav pill and primary button are both compliant. I rejected teal-600 (`#0d9488`) as the primary interactive color first — its contrast on white is only 3.74:1, which fails the text floor even though it would pass the 3:1 non-text-UI floor — and demoted it to icon-only/large-scale use.

**Capacity-intensity tiers + contrast audit**
① Need 5 always-visible day-cell states (none/light/moderate/busy/over) with a bg+text pairing each, all auditable against the brief's zinc-600/amber-800/red-700 floor rule for tinted (non-white) surfaces ② `none`: bg `zinc-50`, text `zinc-400` (this tier is intentionally faint — "closed, nothing to read" — so it's the one deliberate exception to the floor, and it never carries the numeric hours value, only an em-dash). `light`: bg `zinc-50`, text `zinc-600`. `moderate`: bg `zinc-100`, text `zinc-700`. `busy`: bg `amber-50`, text `amber-800`. `over`: bg `red-50`, text `red-700`, plus a `TriangleAlert` icon (color is never the sole signal for the one state that matters most operationally) ③ Hand-computed contrasts: zinc-600 on zinc-50 = **7.41:1**; zinc-700 on zinc-100 = **9.49:1**; amber-800 on amber-50 = **6.84:1**; red-700 on red-50 ≈ **6.0:1**. All clear the brief's own reference number (zinc-600 on a zinc-100-class surface ≈ 7.18:1) with margin, so I standardized on the darker zinc-600/700 steps everywhere rather than trying to shave it closer to 4.5:1.

**Selection-propagation split (the brief's hard-won lesson)**
① Brief explicitly forbids "one selectedId threaded uniformly into 3 sibling widgets" and asks for genuinely different propagation *modes* per action, named and justified ② Implemented four distinct modes, not two: (a) **hover/focus on a day cell → ephemeral tooltip** — local `hoveredIso` state inside `Calendar.tsx` only, shows a precise "Nh/Mh booked (Tier)" string, vanishes on blur/mouse-leave, touches no other component; (b) **click (or Enter/Space) on a day cell → "pin"** — lifts `selectedIso` in `client.tsx`, does a full recompute of `DayDetailPanel` (tabs, item list, inspectors, risk breakdown); (c) **pin's derived week → partial/conditional recompute** — `pinnedWeekStart` is computed via `startOfWeek(selectedCivil)` as a `useMemo`, *not* stored as independent state, so the "Capacity Booked" KPI card and its sparkline only re-render with new values when the Monday actually changes (pinning a different day in the *same* week is a no-op for this widget, by construction rather than by an explicit guard — commented in `client.tsx`); (d) **the Pickup Queue table is deliberately NOT wired to selection at all** — it always shows the fixed current operating week (Aug 31–Sep 6) regardless of what's pinned, because ops staff need a stable reference view while browsing the calendar for planning. That's the fourth, "intentionally unsynced," mode ③ This directly answers the brief's ask for modes tied to *actions* (hover vs. click vs. week-change vs. "don't sync this one") rather than one propagated ID.

**Column-width math (Pickup Queue table)**
① Brief requires summing intrinsic min-content width *before* allocating `%` columns, and forbids any horizontal scroll container that coexists with the calendar's own reflow ② At the table's typical desktop inner width (~916px at a 1280px viewport, see below), allocated: Time 8% (73px, fits "Mon 09:00"), Item 35% (320px, fits "Herman Miller Aeron Chair" + category subtext), Seller 12% (110px, fits "Michael Yoon"), Inspector 15% (137px, fits a 22px avatar + "Alex Rivera"), Est. Value 12% (110px, fits "₩8,200,000" tabular right-aligned), Risk 8% (73px, fits "Medium"), Status 10% (92px, fits "In Transit") — sums to 100% ③ Below `md` (768px) I did **not** try to compress 7 columns further — instead the table swaps to a stacked row-card list (`<ul>`, not a second table) showing the same sorted/filtered rows, because the brief's own history flags silent text-bleed as invisible to the overflow-scan gate and explicitly forbids two independent wide `overflow-x-auto` containers on one page; a card list sidesteps both by never being a table at that width.

**Sidebar width & ultra-wide cap math**
① Brief requires computing the 1920px right-edge gap from the actual shell, not reusing example numbers ② Sidebar = 260px fixed; main content horizontal padding = `px-8` (32px) each side ③ At 1920px: 1920 − 260 (sidebar) = 1660px available; content is fluid (no `max-w` cap) inside that, so its right edge sits exactly `32px` from the viewport edge — under the brief's ≤40px ceiling — so I deliberately left content uncapped rather than adding an arbitrary `max-w-[...]` that would need its own justification. Verified the same padding math holds down to 1280px (956px content column, ~79px per day cell in month view — enough for a day number + 2-digit count without wrapping).

**Interactions implemented (4 required + 1 bonus)**
① Which of the brief's menu of interactions to build ② (1) Sparkline hover/focus crosshair tooltip (`Sparkline.tsx`) — mouse `mousemove` finds the nearest point; keyboard focus + Arrow Left/Right walks the same point set, both drive one `active` state, so the readout is identical either way; (2) real table sort (5 sortable columns, `aria-sort`, ascending/descending arrow icons as the non-color state signal) + a status filter dropdown; (3) Month/Week segmented-control view toggle, each with its own independent nested navigation (month uses `monthAnchor` + prev/next month, week uses the pinned week + prev/next week, shifting `selectedIso` by ±7 days via the same date-math helpers); (4) the four-mode selection split described above; (5, bonus) a ⌘K command palette with arrow-key navigation, a minimal Tab focus trap scoped to the dialog, and focus restored to the trigger on close ③ I skipped adding a second, decorative sparkline-on-every-KPI-card — two of the four KPI cards get a real sparkline backed by genuine per-day data; the other two (Grading Backlog, Est. Value) show status badges / a plain stat instead, because I didn't want to fabricate a trend series for numbers that don't have one in the mock dataset.

**Font & theme**
① Which of the 3 whitelisted display faces, and light vs. dark ② `--font-display-mono` (JetBrains Mono Display) for the wordmark, page `<h1>`, and calendar month/week title only; everything else stays on Pretendard. Committed fully to light theme (pure white/zinc-50, no dark-mode media query branch) ③ Mono reads as "scheduling console," and a full-time light commitment avoided the fake-light traps (no cream/paper tones anywhere — canvas is `zinc-50`, cards are pure `white` with `zinc-200` hairlines) while keeping the accessibility audit to one palette instead of two.
