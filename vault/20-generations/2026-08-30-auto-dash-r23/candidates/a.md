# Candidate A — Trust Console (disputes/returns triage, master-detail)

One-line concept: an internal repick trust-and-safety console — a left rail of dispute cases (buyer claim vs. seller response) sorts/filters into a right detail pane with the AI re-grade confidence, full claim timeline, evidence, and a resolution action panel; pure-white light theme with amber as the single accent and a dark sidebar chrome.

Files: `app/src/app/dash-evolve/r23/a/{page.tsx,client.tsx,data.ts,ui.tsx,Sidebar.tsx,TopBar.tsx,KpiRow.tsx,CaseRail.tsx,DetailPane.tsx,Timeline.tsx,ConfidenceGauge.tsx,CommandPalette.tsx}`

## 브리프에 없던 것

**Product specifics.** ① Brief only suggested "a disputes/returns triage console" as an angle. ② I invented "repick Trust Console," an internal Trust & Safety desk tool, page title "Disputes queue," 8 fully-authored cases (camera/boots/overcoat/tote bag/headphones/backpack/desk/jacket) with buyer+seller identities, claim text, seller response, AI verdict, and SLA state. ③ The brief explicitly bans "world-building" theatrics but still wants a "service used daily" — a named, coherent internal product with real-feeling case data was the only way to hit that without drifting into either mood-board or generic-Lorem territory.

**Case count = 8, not a round 10.** ① Needed to decide how many rows to build. ② Landed on 8. ③ I only trust Unsplash photo ids already verified to resolve elsewhere in this repo (grepped `app/src/app/(app)/dashboard`, `(marketing)/v10`, `v14`, `dash/d29`) rather than guessing at new ids that could 404 or mismatch their `alt` text. That verified pool gave me 8 clean product-photo categories (camera, boots, overcoat, designer tote, headphones, backpack, desk lamp, denim jacket) with honest alt text — I picked count and item list to fit the assets I could actually confirm, instead of inventing a 9th/10th case around an unverified image.

**Avatars.** ① Needed buyer/seller/agent portraits. ② Reused the same 8 verified `facearea`-cropped portrait ids already used as team avatars in `dash/d29/data.ts`, cycling them across the 17 person-slots (8 buyers + 8 sellers + 1 agent). ③ Same reasoning — no unverified image URLs, and reuse of a few stock portraits across many dummy people is standard practice in this catalog's existing data files.

**Evidence tab: real photo for the listing, generated placeholder tiles for buyer evidence.** ① Each case only has one verified real photo (the listing photo). The Evidence tab conceptually needs "listing photo" + N "buyer-submitted photos." ② Rather than reusing the same real photo again under a different, dishonest label (would misrepresent what's pictured) or inventing more unverified Unsplash ids, buyer-submitted evidence renders as generated placeholder tiles — a dashed border, a `lucide` `ImageIcon`, and "Photo N" — clearly a system placeholder, not a fabricated photo. ③ Honesty over polish: a placeholder that reads as "we don't have this asset in the mock" is better than a real photo captioned as something it isn't.

**Accent color: amber-700/-800 for text and fills, `#B45309`.** ① Brief said avoid violet/indigo (already overused) and suggested amber/blue/teal/lime/sky/emerald as options for a "review pending" trust console, but left the exact choice open. ② Chose amber, specifically `amber-700` (`#B45309`) for any amber *text* or focus ring, `amber-50`/`amber-800` for the amber badge tone, `amber-500/600` reserved for pure decoration (icons, translucent sidebar active-pill fill) never for readable text. ③ Amber reads as "attention/pending" without the danger connotation of red or the cold-neutral read of blue — fits a desk that's mostly triaging "needs a decision" cases rather than reporting failures. Computed contrast (WCAG relative-luminance formula, manual, so treat as approximate): `amber-700` (#B45309) on white = **5.02:1** (passes 4.5:1 for text); `amber-700` on `amber-50` (#FFFBEB) ≈ **4.9:1**; white text on an `amber-700` button fill = same **5.02:1**. `amber-600` (#D97706) on white only comes out to **~3.18:1** — below the text floor — so it is used only for the confidence-gauge arc stroke and progress-bar fills (graphical, 3:1 threshold, not text).

**Semantic red/emerald alongside the single amber accent.** ① The "single-accent" rule bans a 3-color *brand* palette, but a triage console needs a way to say "resolved" vs. "escalated/overdue" that isn't ambiguous. ② Added `emerald-700` for resolved/success and `red-700` for escalated/overdue, both always paired with an icon or text label (never color alone), amber remains the only *decorative/brand* accent (buttons, focus rings, active states, the flagship gauge). ③ Read this as functional status semantics (like a disabled-state gray or an error-state red in any design system) rather than a second brand color — judged this the more honest reading of "single accent" than pretending overdue and resolved look the same.

**Theme: pure-white canvas + a dark (`zinc-950`) sidebar.** ① Brief allows either light or dark for "the dashboard," singular. ② Went with a fully pure-white main canvas (`bg-white`/`zinc-50`, `zinc-100`–`200` hairlines) and a deliberately dark sidebar chrome (`zinc-950`, `white/10` borders, `zinc-400`-floor secondary text) rather than forcing the sidebar to also be white. ③ This is standard in real products in this exact category (GitHub, Notion, Vercel all pair a dark/tinted nav rail with a light canvas) — read as "one committed light theme with a chrome accent," not a light/dark toggle or fake-light confusion; the two DNA rules this must satisfy (pure-white canvas, refined dark surfaces with `white/10` borders) are each satisfied *within their own region* rather than blended into one ambiguous surface.

**Currency: KRW throughout, via `Intl.NumberFormat(..., {currency:"KRW"})`.** ① Brief flagged that ₩ needs Pretendard tabular-nums (not mono, which lacks the glyph) if used at all, but didn't require using it. ② Used it for every amount (`formatKrw`), since repick is a secondhand marketplace and KRW is the more specific, defensible currency choice over a generic USD placeholder. ③ Also let me exercise the exact caveat the brief called out — no `font-mono` anywhere near currency, only the default Pretendard stack with `tabular-nums`.

**Selection propagation split — implemented exactly as the brief's history section asks, not as three parallel `selectedId` props.**
- **Mode A ("pin"), persistent:** clicking a rail row sets `selectedId` in `client.tsx`. `DetailPane` is rendered as `<DetailPane key={selectedCase.id} c={selectedCase} />` — keying by id means the click *remounts* `DetailPane` rather than patching it, so every piece of state living inside it (active tab, the resolution-panel choice) resets to default on every pin change, which is a deliberate, visible partial recompute. `KpiRow` is rendered with **no** `selectedCase` prop at all — it only ever reads the global `CASES` array — so pinning a case *never* recomputes the queue-wide KPI aggregates. Both files carry a code comment stating this split and why (a single case's status shouldn't move the team's SLA-at-risk count). The ⌘K command palette is a second entry point into the *same* Mode A (`onSelect` calls the identical `setSelectedId`) — I deliberately did not treat it as a third mode, since it's just another way to trigger a pin.
- **Mode B ("ephemeral inspector"), non-persistent:** two independent hover/focus interactions never touch `client.tsx` state at all. `ConfidenceGauge.tsx`'s per-pass trend line holds its own `hoverIndex` (local `useState`), shows a floating value tooltip on `onMouseEnter`/`onFocus`, and clears it on `onMouseLeave`/`onBlur` — nothing outside that one component ever knows it happened. `Timeline.tsx`'s per-event `TimestampChip` does the same for the exact timestamp + internal event ref, shown only on hover/focus of that one chip. Both are keyboard-operable (real `<button>`s, not `div onMouseEnter`) so the ephemeral mode is not mouse-only.

**Master-detail breakpoint: side-by-side only from `2xl` (1536px), not `lg`/`xl`.** ① Had to pick where the 12-col grid splits the rail (4 cols) from the detail pane (8 cols) vs. stacking full-width. ② Chose `2xl`. ③ Arithmetic: sidebar is `w-64` (256px), main content padding is `sm:px-6` (48px total). At the `xl` (1280px) breakpoint the rail would only get ≈300px, and the `Amount` column (needs ~78–100px for `₩3,650,000`-scale figures) came out with a single-digit-pixel margin — a "just barely fits" case the brief explicitly calls a failure. Pushing the split to `2xl` (1536px) means the rail is ≥400px at every point the split is active, and everything below `2xl` gets the full, generous stacked width instead.

**Rail table column math (`table-fixed`, no `<colgroup>`, widths on the header `<th>`s only).** ① Had to size three columns (Case / Status / Amount) so nothing bled at 390px. ② Landed on **34% / 32% / 34%**, after two revisions. ③ Math, at the tightest real point (390px viewport → ≈356px table width after page+card chrome): `Status` at 32% ≈ 114px cell → minus 24px cell padding minus 16px badge padding ≈ 74px left for glyphs; the worst single unbreakable word is "Escalated" (≈58px at 11px tabular) — **16px margin**, and `Badge`'s text now also carries `break-words` as a hard backstop in case any future status label doesn't fit at all (prefers wrapping at a space, only breaks mid-word as a last resort — the brief's own "wrap, don't bleed" advice, not the mid-word-truncation antipattern it separately warns against). `Amount` at 34% ≈ 121px minus 24px padding ≈ 97px for `₩3,650,000` (needs ≈70–78px) — 19–27px margin. `Case` at 34% holds a 3-line stack (id, 2-line-clamped title, SLA text) plus an avatar pair + `truncate`d claim-type label (given `min-w-0 flex-1` so it actually shrinks instead of forcing overflow) — I moved the SLA text from an inline flex row next to the id onto its own line specifically because the original inline layout had no wrap boundary and would have bled at the "Overdue Nh" + id combination.

**KPI cards restructured from inline (value + sparkline side by side) to stacked.** ① First pass put the big number and a 72px sparkline in one flex row. ② Recomputing the same way at the 4-up (`xl`, 1280px) breakpoint — the tightest point for a 4-column KPI grid — gave each card only ≈195px of interior width, and `₩5,470,000` (≈144px) + a 72px sparkline + gap didn't fit. Restructured to stack label → value → (sparkline + delta) on separate rows, shrank the sparkline to 64px, and added `truncate`/`min-w-0` as a backstop on the label and value. ③ Removing the horizontal competition entirely is more robust than trying to hit an exact percentage split that only works at one breakpoint.

**Focus ring mechanism differs for the rail's `<tr>`.** ① Brief flags `ring-2`/`ring-offset-*` as dead in this Tailwind v4 setup and prescribes box-shadow or a border/background swap instead; I used a shared `box-shadow`-based `FOCUS_LIGHT`/`FOCUS_DARK` utility everywhere. ② For the case-row `<tr>` specifically (not a button/link/input), I did *not* use the box-shadow utility — `box-shadow` on `display:table-row` is a known unreliable combination across browsers (cell backgrounds can paint over/clip it) — and instead used the brief's other explicitly-sanctioned option: a plain background-color swap, `focus-visible:bg-amber-200`, layered so it still visibly differs from both the resting (`bg-white`) and selected (`bg-amber-50`) states. Documented inline in `CaseRail.tsx`.

**`ProgressBar` animates `transform: scaleX(...)`, not `width`.** ① First draft animated the fill's `width` percentage directly — a layout property, which the motion rules explicitly forbid animating. ② Rewrote it as a full-width child scaled via `transform: scaleX(pct/100)` with `transition-transform`, origin-left. ③ Same visual result, compositor-only, no reflow — and it let me actually use the component somewhere real (the listing-grade score bar in the detail pane's "Listing reference" card) rather than leaving it built-but-unused.

**Resolution action panel.** ① Not in the brief's explicit component list, but the brief's Goal section wants "a service used daily," and a triage console with no way to actually resolve a case reads as inert. ② Added a 3-option button group (Refund buyer / Uphold seller / Request more evidence) + a Confirm button, purely client-side UI state (`useState`, reset per case via the same `key`-remount as the rest of `DetailPane`), disabled and pre-filled for already-resolved cases. ③ No backend exists to call, so I kept this honestly presentational (no fake success toast, no fake persistence) rather than pretending it does something it doesn't.

**Command palette (⌘K).** ① Listed only as a bonus interaction, not required. ② Implemented a real filterable/keyboard-navigable palette (`ArrowUp`/`ArrowDown`/`Enter`/`Escape`) over the 8 cases, wired to the same Mode A pin. ③ Cheap to add correctly once the pin mechanism existed, and it's explicit brief bonus credit.
