# Candidate B — Local Pickup Zones

A seller-facing settings screen where a repick seller manages the small set of named local-pickup spots they offer buyers for in-person handoffs — each zone shows its area/radius note, its availability window, and an enable/disable toggle so a seller can temporarily pause a spot without deleting it. The whole screen is a single `FlatList` scroll with no fixed bottom band or bar, since there is no blocked-workflow state to narrate persistently; intro copy and a live "N of M zones active" summary sit in `ListHeaderComponent` rather than a second ScrollView. Removing a zone never opens a native `Alert`: pressing "Remove" on a row swaps that row's own content in place for a "Remove {zone} from your pickup zones?" prompt with `Cancel` / `Confirm remove` buttons, and that prompt text is the exact string pushed through a single screen-level polite live region, which also announces toggle changes, cancellations and completed removals, clearing itself a couple of seconds after each one so the alert role never gets stuck "on."

## Render-check string
"Manage Pickup Zones"

## 브리프에 없던 것 (What the brief didn't specify)

1. **① What to show per zone besides the toggle and remove control.** **② Two short text lines per zone: an `areaNote` (radius/landmark description, e.g. "Within 300m of the exit gate") and a `scheduleNote` (availability window, e.g. "Weekday evenings only, 6:00 – 9:00 PM"), plus an "Active"/"Paused" status chip next to the zone name.** **③ The brief only said each zone needs "a radius or area note and an enabled/disabled toggle" — a status chip was added on top of the toggle because the UX catalog row "Inactive state: visually distinguish, don't let it look identical to an enabled one" asked for more than just the toggle's own visual position to carry that signal, and the schedule note was added because a pickup zone realistically needs a time window, not just a place, for the screen to feel like a real seller tool rather than a bare toggle list.**

2. **① Whether more than one row can be mid-confirmation at once.** **② Only one row at a time — a single `rowAwaitingConfirm: string | null` at the screen level, not a Set.** **③ Arbitrary simplification: the brief's analogous mechanic is described as a single row converting in place, and allowing several simultaneous confirms would also make the single shared live region ambiguous about which row's prompt it is echoing.**

3. **① Whether toggling a zone on/off should also announce, beyond the required remove-confirm transitions.** **② Yes — every toggle flip produces its own live-region message ("X is now offered/paused as a pickup zone") through the same shared `announce()` helper used for remove/cancel/confirm.** **③ The brief's accessibility rule is "any point where what the user can do next changes state must announce it," and pausing a zone changes whether buyers can select it next, so it was read as in-scope even though the worked example in the brief was specifically about the remove flow.**

4. **① What happens when every zone has been removed.** **② A `ListEmptyComponent` with "No pickup zones yet" copy and a non-functional "Add a pickup zone" button (no `accessibilityHint`, since the button has no real handler yet).** **③ Directly required by the UX catalog row "Empty state: if the zone list could become empty after removals, show guidance + an action, not a blank screen," combined with the brief's own rule to omit a hint rather than write one that promises an unimplemented action.**

5. **① How to build the toggle control itself, since RN's built-in `Switch` wasn't mandated.** **② A custom `Pressable` track/thumb pair with `accessibilityRole="switch"` and `accessibilityState={{ checked }}`, sized to a 44×44 hit area around a visually slimmer 44×26 track.** **③ Arbitrary but token-driven choice (accent vs. border track color, white thumb) to stay inside the near-monochrome + single-accent palette and the 44×44 minimum-touch-target catalog rule, rather than pulling in a native `Switch` whose default theming isn't token-controlled.**

6. **① Exact wording and timing for the transient live-region clearing.** **② A 2.6-second `setTimeout` (`LIVE_MESSAGE_LIFETIME_MS`) that resets the shared `announcement` state back to `""`, re-armed (previous timer cleared) on every new announcement, with cleanup on unmount.** **③ Arbitrary duration chosen to be long enough for a screen reader to finish a short sentence but short enough not to block a quick second action; directly implements the brief's "open refinement" rule that a conditional `accessibilityRole="alert"` must be actively cleared or it gets stuck on.**
