# Candidate C — Fluxgraph

Fluxgraph is a dark service-topology console for a streaming platform's infra team: a full-width, deterministic concentric-ring dependency graph of 16 services and 28 calls (grouped by tier or by traffic volume), a dismissible node-inspector popover, and an independent bottom incident timeline — all backed by a complete, sortable adjacency-list table whose row buttons are the only keyboard path into any node's detail (this concept's prior attempt was dropped at the hard gate for making graph nodes themselves focusable buttons; see items 8–9 below for the two fixes this rebuild applies).

## 브리프에 없던 것

1. ① **브랜드/제품 정체성과 업종**: 브리프는 이름·업종을 지정하지 않음.
   ② "Fluxgraph"라는 이름과, 스트리밍 미디어 플랫폼의 백엔드(재생 API·트랜스코딩·추천·DRM·결제 등)를 모니터링하는 토폴로지 콘솔이라는 서사를 선택. 동일 개념의 직전 시도("Meshwire")가 커머스 스택을 다뤘던 것과 겹치지 않도록 의도적으로 다른 업종을 골랐다.
   ③ 서비스 메시 관측성이라는 일반적 ops 도메인에서 임의로 고른 선택 — 특정 실제 회사를 모사하지 않음.

2. ① **정확한 그래프 데이터셋**(노드 수·구체 서비스·엣지 수)은 브리프가 "12–20개, 고아 노드 없음"만 요구.
   ② 3단 티어(Edge 3 / Service 7 / Data 6 = 16 노드)와 28개 호출로 직접 설계하고, 각 노드가 최소 1개 엣지의 source 또는 target로 등장하는지 글 작성 시점에 직접 대조해 검증(고아 노드 0개).
   ③ 실제 미디어 스트리밍 아키텍처(엣지 게이트웨이 → 애플리케이션 서비스 → 데이터/큐 계층)의 통상적 3계층 구조를 임의로 본뜸.

3. ① **동심원 레이아웃의 정확한 반지름·스태거 각도 공식**은 브리프가 "고정 좌표를 직접 계산하라"고만 하고 수치는 위임.
   ② `TIER_RADIUS = {edge:90, service:175, data:250}` (뷰박스 740×560, 중심 370,280), 티어별 각도 스태거 `{0°, 15°, 8°}`를 임의로 정하고 `Math.cos/sin` 결과를 `r2()`로 소수 2자리까지 반올림.
   ③ 링마다 스포크가 겹치지 않게 어긋나는 배치는 radial-tree류 레이아웃의 통상적 가독성 관행을 본뜬 임의 선택이며, 수치 자체는 이 작업만의 고유값(직전 시도의 110/205/275와 다름).

4. ① **"by traffic" 보조 뷰가 정확히 무엇을 재계산해야 하는지**는 브리프가 "색상/레이아웃을 결정론적으로 바꿔라"는 방향만 제시(지연시간 예시였을 뿐, 다른 지표도 허용).
   ② 지연시간이 아니라 노드별 트래픽(`trafficRpm`)을 `<10k / 10k–50k / >50k rpm` 3구간으로 나누고, tier 뷰와 동일한 3개 링 반지름을 재사용해 노드를 재배정하도록 설계.
   ③ 두 뷰가 "다른 기하"가 아니라 "같은 3개 링 사이의 재배정"이 되게 한 것은 레이아웃이 통째로 바뀌는 느낌을 피하기 위한 임의 선택 — 지연시간 대신 트래픽을 고른 것은 직전 시도와 차별화하기 위함.

5. ① **노드 몸체 모양과 상태 코너 마커 모양의 어휘**는 지정되지 않음(둘 다 "모양" 채널을 쓸 때 충돌 여부도 위임).
   ② 몸체=티어(Edge 삼각형 / Service 원 / Data 사각형), 코너의 작은 상태 마커=상태(healthy 원 / degraded 다이아몬드 / down 역삼각형)로 완전히 분리된 두 모양 어휘를 직접 설계.
   ③ 크기·위치가 다른 별개 채널이면 모양 어휘(원/삼각/사각)를 재사용해도 모호하지 않다고 판단 — 범례에 두 어휘를 모두 표기해 확인 가능하게 함.

6. ① **엣지의 상태·관계 두 신호를 "색상 단독 아님" 원칙 아래 어떻게 분리할지**는 완성도 요구사항만 있고 구체 매핑은 위임.
   ② 엣지 색상=상태(healthy/degraded/down), 엣지 두께=상태의 비색상 짝, 대시 패턴(실선/파선/점선)=관계 3대분류(sync/async/data-access)로 채널을 분리.
   ③ 지도·다이어그램에서 선 스타일로 범주를 구분하는 통상적 관행을 본뜬 설계 — 6가지 세부 관계 전체는 호버 툴팁·인스펙터·테이블에서 항상 확인 가능.

7. ① **390px 모바일에서 그래프 캔버스를 어떻게 처리할지**는 "단순화된 뷰 또는 테이블을 1차로" 둘 중 선택하라고 위임.
   ② 그래프를 `min-w-[640px]`로 고정해 그래프 카드 내부에만 한정된 가로 스크롤을 허용하고(페이지 레벨 가로 스크롤은 없음), 테이블은 축소 없이 전체 너비·스크롤 없이 렌더링.
   ③ 노드 탭 타겟이 화면폭에 비례해 줄어들면 마우스로도 식별하기 어려워지므로 물리적 크기를 보존하는 쪽(스크롤)을 선택 — 테이블이 이미 1차 접근성 폴백이므로 그래프 쪽은 시각 전용으로 과감히 축소하지 않기로 함.

8. ① **FIX #1 적용 범위**: 그래프 노드를 `<button>`으로 만들지 말라는 지시는 명확했지만, 그렇다면 테이블의 행 단위를 "노드 1개=1행"으로 할지 "엣지 1개=1행"으로 할지는 위임.
   ② 행은 엣지(28개) 단위로 유지하되, Source·Target 두 셀 각각에 `min-h-7`(28px) 고정 높이의 실제 "View" 버튼을 넣어, 16개 노드 전부가 어느 행의 Source 또는 target으로 반드시 등장한다는 사실(항목 2에서 검증)로 키보드 접근성을 보장. 그래프 쪽 마크는 `aria-hidden` SVG `<circle>`/`<line>`일 뿐 `tabIndex`·`role`·버튼이 전혀 없음 — 포인터 호버/클릭은 순수 보조 기능.
   ③ 노드를 별도 행으로 또 나열하면 28개 엣지 행과 16개 노드 행이 중복돼 테이블이 두 배로 길어지므로, "인접 리스트"의 본래 의미(각 노드의 연결을 그 노드가 등장하는 엣지 행들로 읽는다)를 살리면서 행 수를 늘리지 않는 절충.

9. ① **FIX #2 적용 범위**: colgroup 퍼센트를 라벨 글자수가 아니라 실제 렌더 폭에서 패딩을 뺀 값으로 검증하라는 지시였는데, 최초 설계는 Status 열에 테두리 Badge(자체 `px-2 py-0.5` 내부 패딩 포함)를 썼다가 17% 열에서도 공간이 부족함을 직접 계산 중에 발견.
   ② Status 셀을 테두리 pill 없는 아이콘+4자 코드("OK"/"DEG"/"DOWN")로 교체하고, 390px 기준 테이블 실폭(≈356px, 카드 패딩을 상쇄하는 `-mx-4`/`-mx-5` 네거티브 마진 포함)에서 각 열 콘텐츠 폭 = 열%×356−16(균일 `px-2`)을 전부 양수 여유로 재계산(Source/Target 22%, Type 10%, P50 12%, Rpm 17%, Status 17%).
   ③ 패딩을 가진 장식용 Badge 컴포넌트를 좁은 열에 그대로 쓰면 아무리 퍼센트를 늘려도 내부 패딩이 여유를 갉아먹는다는 것을 직전 시도의 실패(라벨만 줄이고 셀 패딩을 반영하지 않아 2px 겹침 발생)에서 얻은 교훈으로 직접 재확인하고, 이번에는 Badge 자체를 쓰지 않는 쪽으로 해결.

10. ① **1920px 울트라와이드 캡의 정확한 수치**는 "자신의 셸 기준으로 직접 계산하라"고만 지시됨.
    ② 사이드바 256px를 제외한 main의 가용폭(1920−256=1664px)과 정확히 같은 1664px를 `max-w`로 설정 — `max-w`가 가용폭보다 작으면 `mx-auto`가 패딩 위에 추가로 센터링 여백을 얹어 40px 기준을 넘긴다는 것을 직접 계산 중에 발견하고 피함.
    ③ 1600 같은 보기 좋은 반올림 수치 대신, 이 셸의 실제 사이드바 폭에서 역산한 고유값을 그대로 사용 — 여백이 `lg:px-8`(32px) 하나로만 구성되게 하기 위함.

11. ① **⌘K 검색에서 노드를 선택했을 때 무엇이 일어나야 하는지**는 브리프가 "검색 기능"만 요구하고 구체 동작은 위임.
    ② 선택한 노드의 `data-view-for` 속성을 가진 테이블의 "View" 버튼을 `document.querySelector`로 찾아 그 지점으로 스크롤하고, 그래프 클릭과 동일한 `openInspector` 경로를 그 버튼을 트리거로 호출.
    ③ 팔레트가 그래프 노드로 직접 점프하는 대신 테이블 버튼으로 점프하게 한 것은, 키보드로 접근 가능한 "진짜" 트리거가 테이블에만 있다는 이 설계의 원칙을 검색 결과 선택 경로에서도 깨지 않기 위함.

12. ① **탑바의 "주요 액션" 버튼이 무엇을 해야 하는지**는 앱 셸 요구사항에 버튼이 있어야 한다고만 명시.
    ② 아무 동작도 없는 장식용 "Export" 버튼 대신, 클릭 시 실제로 인접 리스트 테이블 제목으로 스무스 스크롤하는 `<a href="#adjacency-table-heading">` 링크("Jump to adjacency table")로 구현.
    ③ 클릭해도 아무 일도 일어나지 않는 "죽은 컨트롤"을 두지 않기 위한 선택 — 이전 라운드 심사에서 죽은 컨트롤 여부가 실제로 점검된 바 있음.

13. ① **아바타 처리 방식**은 "사진 대신 이니셜/아이콘"이라는 제약만 있고 접근성 이름 구성은 위임.
    ② 이니셜 배지는 `aria-hidden`, 이름은 `sm:` 이상에서만 보이고, `sr-only sm:hidden` 텍스트가 모바일에서만 전체 접근성 이름을 제공 — 버튼 자체에 별도 `aria-label`을 전혀 달지 않아 "보이는 텍스트와 라벨 불일치" 위험을 원천적으로 제거.
    ③ 라벨을 따로 달면 그 문자열이 보이는 텍스트를 포함해야 한다는 제약을 매번 지켜야 하므로, 애초에 라벨을 안 달고 콘텐츠만으로 접근성 이름을 구성하는 쪽이 더 단순하고 안전하다고 판단.
