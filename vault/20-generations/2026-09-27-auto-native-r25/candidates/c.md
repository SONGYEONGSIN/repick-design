# auto-native-r25 · candidate c — Saved Search Manager

**Concept (one line):** A list of the buyer's standing saved searches (each showing new-match count since last checked), managed with a selection-driven bottom dock whose available bulk actions — Pause/Resume, Merge, Delete — are computed from the *composition* of the current selection (per-item paused state, category compatibility), not just its size.

Files: `native/src/evolve/r25/c/SavedSearchManagerScreen.tsx` (named export `SavedSearchManagerScreen`, also default export) + `native/src/evolve/r25/c/data.ts`. Check string / representative heading: **"Saved Searches"**.

## 브리프에 없던 것 (decisions the brief didn't make for me)

1. **Which two domain-specific derived behaviors to build.** The brief offered "Merge" and "per-item paused mutual exclusivity" as *seed ideas*, not requirements, and said "pick your own." I built both rather than inventing a third, because together they exercise two different kinds of derived state (a pairwise compatibility predicate for Merge vs. a set-wide predicate over per-item state for Pause/Resume) and the brief's own phrasing treats them as the strongest available examples.

2. **Merge's conflict-resolution rules.** Nothing specified what a "merged" search should look like when the two inputs disagree. I chose: price ceiling → `max()` of the two (a merge should never lose coverage either search already had), condition → the shared value or `"Any condition"` if they differ, new-matches → the sum. This is arbitrary but internally consistent (union semantics), and it's a real computation in `buildMergedSearch` (`data.ts`), not a placeholder.

3. **What "paused" means for match-counting.** I decided a paused search's `newMatchesCount` is frozen/ignored for display (the row shows a "Paused" pill instead of a numeric badge, and the header's "new matches" total only sums active searches). Nothing in the brief specified this; it's the obvious reading of "paused" for a standing search but had to be picked.

4. **Delete confirmation mechanism.** The brief's domain description doesn't mention deletion mechanics beyond "bulk-delete"; the *shape* of the confirmation (dock converts to a Cancel/Confirm two-button row inside the live-region container, never a native `Alert`) comes from the harness's mandatory accessibility rules (§5) and `GENERATION.md`'s "파괴적 확인의 밴드→행 일반화" note, not from the domain brief itself.

5. **Post-delete recovery row.** Not required by the brief. I added a minimal `RecoveryRow` ("N saved searches deleted · Undo · Dismiss") for richness, kept strictly mutually exclusive with the dock via an if/else-if render chain (same macro shape `r23/c` used for its Undo strip). I intentionally renamed every style key and component (`RecoveryRow`/`recoveryRow`/`recoveryBtn`… vs. `UndoStrip`/`undoStrip`/`undoButton`… in `r23/c`) so the code surface doesn't literally match, per `GENERATION.md`'s "형태를 맞게 골라도 코드 표면까지 닮으면 진다" rule.

6. **₩ glyph handling.** Of the three options offered (space before digits / write `KRW` / never pair with `tabular-nums`), I chose "space + no `tabular-nums` on that text node" (`formatPriceCeiling` in `data.ts`: `` `under ₩ ${digits}` `` as a single Text node with no `fontVariant`) so the screen keeps the local-currency glyph rather than switching to `KRW`, since price ceilings are a secondary metadata line here, not a hero price.

7. **Row interaction model — no secondary per-row control.** I deliberately gave each row exactly one interactive element (the whole row is the checkbox; `accessibilityRole="checkbox"`) and put every mutation (pause, resume, merge, delete) behind the multi-select dock only. The brief doesn't say whether a row should also have its own inline action (e.g., a per-row pause icon, as `following-feed`'s per-row Follow button does). I avoided that specifically because a row that is both an outer selection-toggle and a container for its own nested interactive control is exactly the `accessible={true}`-collapses-the-subtree trap called out in the mandatory rules — simplest safe choice was to not create the nested-Pressable situation at all rather than add it and manage it carefully.

8. **No fixed chrome at `selectedCount === 0`.** The screen has zero persistent bottom band when nothing is selected (list just scrolls). This isn't a blocked-workflow screen (no state-machine band applies) and it isn't a read-only completed-record screen either (no persistent action bar applies) — per `GENERATION.md` §3's carve-out, the valid choice when neither of those forms fits is to have no band at all outside the selection-driven one.

9. **Category set and the specific 7 dummy searches.** Picked five plausible resale categories (phones, cameras, furniture, sneakers, bags) and built the 7 rows so the interaction surface would demonstrably hit all three derived-logic branches: `ss-1`+`ss-2` (phones, both active) → Merge enabled + Pause enabled; `ss-5`+`ss-6` (sneakers, one active one paused) → Merge enabled but Pause/Resume disabled with an explanatory note; any cross-category pair (e.g. `ss-1`+`ss-3`) → Merge disabled with its own explanatory note. This is arbitrary test-data construction, not specified by the brief, but chosen so a reviewer can reach every branch without hunting.
