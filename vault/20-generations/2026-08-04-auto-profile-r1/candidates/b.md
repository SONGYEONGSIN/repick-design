# auto-profile-r1 / b — "Sable Voss on Loopwire"

**Product/brand/trigger**: Loopwire (the workflow-automation marketplace already established at `ct1` in `works.ts`/`/catalog`) — this is the public developer profile for **Sable Voss**, a Verified Maintainer who has published 9 integrations to the marketplace across support, CRM, payments, e-commerce, analytics, and DevOps categories. No single "trigger" moment (this isn't a paywall/login); the page's job is credibility: a visitor lands here from a marketplace card's "by Sable Voss" byline and needs to judge, at a glance, whether this maintainer is active and trustworthy before installing their apps.

**Macro structure**: deliberately GitHub-profile-shaped rather than dashboard- or landing-shaped, per the brief's steer toward something structurally distinct. `profile-client.tsx` renders a slim brand header (Loopwire wordmark + a real `next/link` to `/catalog`) over a two-column body: a **sticky left sidebar** (`sidebar.tsx`, `lg:sticky lg:top-8`) carrying identity — avatar, `h1` name, verified-maintainer badge, follow button + live follower count, a 2×2 stat `dl` (installs/integrations/avg rating/member-since), an About card with a second flat `dl` (location/joined/website), and a Specialties card of clickable category tags — against a **right content column** that stacks two always-visible proof sections: `activity-heatmap.tsx` (a full 52-week SVG-cell contribution grid, never hidden behind a tab) and `integrations-panel.tsx` (the sortable/filterable published-apps grid). Sidebar tag clicks and the main grid's filters share state lifted to `profile-client.tsx`, so clicking "Payments" in the sidebar visibly narrows the integrations list on the right — the two columns read as one connected view, not two disconnected panels. Mobile stacks sidebar-then-heatmap-then-grid in source order (no reflow trick), sidebar loses its stickiness below `lg`.

**Interactions implemented** (6, all information-bearing):
1. **Follow toggle** (sidebar) — flips "Follow" → "Following" (icon + text + fill change, not color alone) and increments the live follower count (4,821 → 4,822), `aria-pressed`.
2. **Activity time-range toggle** (30d / 90d / 1y) — recomputes the "contributions · active days" stat line live and dims (not hides) out-of-window heatmap cells via opacity, so the full year stays visible at rest while the emphasis shifts.
3. **Heatmap cell tooltip**, keyboard- and mouse-reachable — hovering or focusing any of the 364 real cells (roving `tabIndex`, arrow-key grid navigation, default focus on the most recent day) shows the exact count and date; a parallel `sr-only` `<table>` with `caption`/`scope` gives screen-reader users the same data without depending on hover.
4. **Specialty-tag filter** (sidebar → main grid) — clicking a category tag (e.g. "Payments") filters the integrations grid to that category and shows a dismissible active-filter chip in the main panel; click again (or the chip's ×) clears it.
5. **Sort control** (native `<select>`, "Most installed" / "Highest rated" / "Recently updated") — reorders the integrations grid live.
6. **Status filter chips** (All / Verified / Beta / Community) — combines (AND) with the category filter and current sort.

All six were exercised end-to-end with Playwright against the running dev server (follow count 4,821→4,822; 1y→30d stat 992→78 contributions; sort "Most installed"→"Recently updated" reordering the first card; category+status filters narrowing 9→2 cards) — zero console/page errors.

**Data determinism**: the 52-week × 7-day activity grid (`heatmap-data.ts`) was generated once by a throwaway node script (seeded `mulberry32(1337)`, ending Aug 4 2026) and pasted in as literal `[count, label, isFuture]` tuples — no `Math.random`/`Date.now`/`new Date()` ships in route code. Integration `updatedDaysAgo` values were hand-computed against the same fixed date for sort correctness, `updatedLabel` strings are literals.

**No raster images**: both the avatar (`avatar-mark.tsx`) and the per-integration category tiles (`integration-mark.tsx`) are hash-derived inline SVG gradients with initials/lucide glyphs, not `next/image` photos. This follows the same reasoning the catalog route's own `brand-tile.tsx` documents for its integration cards — a stock photo (even from an allow-listed host like `picsum.photos`) reads as a placeholder nobody replaced and is a network dependency on first paint; skipping raster images entirely keeps the route at zero image-load risk and sidesteps that exact, already-documented mismatch. (No `<img>`/`next/image` anywhere in the route — verified there's nothing for `no-raw-img`/`no-next-image-unopt` to catch, by construction.)

**Palette (dark, amber accent — assigned axis, correcting a 3-round light-theme rut)**: `zinc-950` page / `zinc-900` panel surfaces, no `dark:` variant prefixes anywhere (the whole route commits to one dark scheme rather than adapting to `prefers-color-scheme`, so `no-dark-dim-text`'s `dark:text-*-500/600` regex has nothing to match — the underlying contrast floor is still respected in absolute terms). Contrast measured (WCAG relative-luminance, sRGB):
- `amber-400` on `zinc-900`: **10.61:1**; on `zinc-950`: **11.92:1**; on `zinc-800`: **8.92:1** — used for the accent text roles (stat highlights, active-tab/tag foreground, follow-button-fill outline).
- `amber-500` fill with `zinc-950` text (segmented-control active state, Follow-button filled state): **9.26:1**.
- `zinc-400` secondary text on `zinc-900`: **6.91:1**; on `zinc-800`: **5.81:1** — floor respected everywhere; `zinc-500`/`600` never used for text on any dark surface in this route.
All well clear of AA 4.5:1 with margin even on the lightest surface used (`zinc-800`).

**Font**: `--font-sans` for all body copy; `--font-display-mono` (`JetBrains Mono Display`, allow-listed) applied only to the "Loopwire" wordmark, the `h1` name, and the emphasized stat numbers (sidebar 2×2 stats, activity contributions/active-days figures) — headlines/stats only, per the assigned axis, nothing else. Exactly 3 weight classes route-wide, verified: `grep -roE "font-(thin|extralight|light|normal|medium|semibold|bold|extrabold|black)\b" *.tsx` → `font-normal` (33), `font-medium` (17), `font-semibold` (12), no others.

**Files**: `app/src/app/profile-evolve/r1/b/page.tsx`, `profile-client.tsx`, `sidebar.tsx`, `activity-heatmap.tsx`, `integrations-panel.tsx`, `avatar-mark.tsx`, `integration-mark.tsx`, `data.ts`, `heatmap-data.ts`.

**Confirmed**: `node scripts/dash-static-check.mjs app/src/app/profile-evolve/r1/b/*.tsx` → `[]` (zero violations). `npx tsc --noEmit -p .` clean. `cd app && npx next build` succeeds, route prerendered as static (`○ /profile-evolve/r1/b`). Ran the actual `node scripts/gate.mjs --target web --routes /profile-evolve/r1/b` (with `PW_CHROMIUM_PATH`/`PW_NO_SANDBOX` set for this sandbox's browser) — **all gates pass**: static 0 violations, weights 3, sweep 0 overflow across the full 1264–1920 desktop set + 390 mobile, and a real (non-`unavailable`) Lighthouse run scored **a11y 100 / perf 40** (perf is record-only per the gate; the dev-server + blocked font CDN in this sandbox depresses it, not representative). One real bug the gate caught and I fixed in this pass: the heatmap's per-cell tooltips were originally `opacity-0` (still laid out, contributing to `scrollWidth` even off-screen) — with ~360 cells near the grid's right edge, that pushed the `overflow-x-auto` wrapper's scrollWidth past its clientWidth at every desktop width the sweep tests, a real `table-overflow` hit (the sweep's selector matches any `[class*="overflow-x"]` element, not literal `<table>`s). Fixed by switching tooltips to `hidden`/`group-hover:block`/`group-focus-within:block` (removed from layout entirely when not shown) and shrinking the grid's cell/gap sizing (11px/3px → 10px/2px) to fit the measured ~734px available width at the narrowest tested desktop breakpoint with margin. Single `h1` (the name, in the sidebar) confirmed, heading order `h1 → h2 (About) → h2 (Specialties) → h2 (Activity) → h2 (Integrations) → h3×9 (integration names)`, no skips. Both `<dl>` uses (sidebar stats, About meta rows) follow the flat `dl > div > (dt, dd)` pattern with icons living inside `dt` only — the documented nesting trap doesn't apply here since integration cards use `<ul>/<li>`, not `<dl>`, for their icon+term+description-shaped rows. Focus-visible amber rings on every interactive element. Color is never the sole signal: status badges pair icon + text (ShieldCheck "Verified" / Sparkles "Beta" / Users "Community"), the follow button changes its label text, active toggles/tags/tabs carry both fill and border changes plus `aria-pressed`.
