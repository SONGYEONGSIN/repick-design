# Candidate B — Driftline

Driftline is a dark, teal-accented inventory-shrinkage console for multi-location retail loss-prevention teams: a three-pane layout (a fixed location rail, a per-location shrinkage-bridge waterfall with always-visible deltas and running totals, and a narrow cause-spotlight panel) backed by a full, sortable incident ledger whose per-category rows always reconcile exactly with the chart they explain.

## 인터랙션 (구현한 4개 이상)

1. **크로스헤어 호버 툴팁** — 워터폴 각 막대에 마우스 호버 또는 키보드 포커스(Tab) 시 점선 크로스헤어 + 델타/누적합 툴팁이 뜬다. 막대 자체는 키보드로 완전히 접근 가능(`button`, `aria-label`에 전체 수치 포함).
2. **실제 정렬/필터가 있는 테이블** — Incident ledger는 7개 컬럼 중 4개(ID/Category/Impact/Logged)가 `aria-sort`를 갖는 실제 정렬이고, 검색어·카테고리 드롭다운·상태(All/Open only) 세그먼트 컨트롤이 서로 조합되어 실제로 행을 필터링한다.
3. **위치 선택 = 뷰 토글** — 좌측 Locations 레일(데스크톱) / 모바일 `<select>`에서 지점을 바꾸면 KPI, 워터폴, 스포트라이트, 테이블이 전부 그 지점의 데이터로 다시 계산된다.
4. **선택 팬아웃(티어 2, 브리프 필수 요구사항)** — 워터폴 막대 클릭 = 영속 핀(한 번에 하나) → 우측 Cause spotlight 카드 **하나만** 좁게 갱신(페이지 전체나 테이블은 건드리지 않음). 막대 호버/포커스 = 순수 로컬 state(워터폴 컴포넌트 밖으로 절대 올리지 않음)인 에페메럴 프리뷰이며, `hoveredId !== pinnedId`일 때만 렌더되어 이미 핀된 막대를 다시 호버해도 중복 툴팁이 뜨지 않는다. 핀이 없을 때 Spotlight는 빈 "막대를 선택하세요" 상태가 아니라 해당 지점의 최대 손실 카테고리(`getDefaultCategory`)를 기본으로 보여준다.
5. **⌘K 커맨드 팔레트(보너스)** — 섹션 이동, 지점 전환, 카테고리 핀, 핀 해제, CSV 내보내기를 전부 커맨드로 노출.

부가: KPI 4번째 카드의 3mo/12mo 세그먼트 컨트롤(회사 전체 shrink rate 트렌드 슬라이스)도 실제 상태를 바꾸는 period/view 토글이다. Export 버튼은 선택된 지점의 인시던트를 실제 CSV Blob으로 다운로드하는 동작 핸들러를 갖는다(장식용 버튼 없음).

## 폰트/타이포그래피 확인

- 본문/모든 라틴 UI 텍스트: `--font-sans`(Pretendard) 고정. 한글 텍스트는 사용하지 않음(브리프의 "English only" 규칙 준수).
- 디스플레이 폰트: `--font-display-mono` **하나만** 사용 — 사이드바 워드마크("Driftline")와 KPI 카드의 큰 숫자(오프닝 인벤토리, 넷 쉬링크, shrink rate, 트렌드 %)에만, 전부 라틴 대형 텍스트. `--font-display-grotesk`/`--font-display-wide`는 전혀 사용하지 않음.
- 렌더링되는 폰트 굵기는 정확히 3종: 기본(400, 클래스 없음) / `font-medium`(500) / `font-semibold`(600). `font-bold` 등 다른 굵기는 어디에도 쓰지 않음.
- 모든 숫자(통화, %, 날짜, 인시던트 ID)는 `tabular-nums` + 우측 정렬. 인시던트 ID만 코드성 데이터로 보고 `font-mono`(시스템 모노스페이스, `--font-mono`) 적용 — 추가 `next/font` 임포트 없음. `$` 통화 기호만 사용하므로(₩ 없음) 모노 폰트 글리프 문제는 해당 없음.
- 캡션/라벨은 `text-[11px] uppercase tracking-wide`로 통일.
- 다크 표면의 모든 텍스트는 `text-zinc-400` 이상만 사용(`zinc-500/600` 전면 배제, 아이콘 색상 포함).

## 브리프에 없던 것

1. ① **제품/업종/브랜드**: 브리프는 "SaaS 제품을 자유롭게 발명하라"고만 했고, 3-pane 아키타입의 구체적 도메인(옵션: 예산/옵엑스, 헤드카운트, 이탈매출, 재고 shrinkage 중 택1)도 지정하지 않음.
   ② "Driftline"이라는 이름과 멀티로케이션 리테일의 재고 shrinkage(도난·파손·행정오류·벤더 부족분) 인텔리전스 콘솔이라는 서사를 선택.
   ③ 최근 라운드들이 쓰지 않은 도메인(매출/헤드카운트 브리지 계열이 아님)이면서 브리프가 예시로 명시한 선택지 중 하나를 그대로 따른 것 — 임의 선택.

2. ① **워터폴의 정확한 카테고리 구성과 막대 수(4~12개 범위 내 몇 개, 어떤 이름)**는 브리프가 범위만 주고 정하지 않음.
   ② Opening/Recovered/External theft/Internal theft/Damage/Admin error/Vendor shortage/Closing = 8개 막대로 구성.
   ③ 실제 리테일 loss-prevention 보고서가 흔히 쓰는 6대 손실 카테고리 분류를 그대로 본뜬 임의 설계 — 숫자 자체는 실측치가 아니라 직접 산정.

3. ① **5개 지점의 정확한 달러 금액과 shrink rate 분포(헬시/워치/크리티컬이 각각 몇 개씩 나오게 할지)**는 브리프가 요구하지 않음.
   ② 오프닝 인벤토리 $2.0M~$3.1M 사이 5개 지점을 직접 설계해 헬시 2곳·워치 2곳·크리티컬 1곳이 나오도록 델타 값을 역산.
   ③ 상태 뱃지 3종이 전부 최소 한 번씩 보이도록(심사자가 뱃지 톤 3종을 전부 확인 가능하도록) 의도적으로 분포를 맞춘 임의 설계 — `shrinkStatus` 임계값(1.2%/2.0%)도 직접 정함.

4. ① **인시던트 원장의 정확한 행 구성(지점당 카테고리당 몇 건, 금액을 어떻게 나눌지)**은 브리프가 "현실적이고 결정론적인 더미 데이터"만 요구.
   ② 지점×카테고리마다 정확히 2건으로 고정하고, 두 금액의 합이 그 카테고리의 브리지 델타와 정확히 일치하도록 역산(총 60행).
   ③ 행 수를 고정 비율로 둔 것은 손으로 직접 합을 검증 가능하게 하기 위한 임의 선택 — 워터폴·스포트라이트·테이블 세 군데 숫자가 절대 틀어지지 않게 하는 안전장치.

5. ① **선택 팬아웃에서 "핀이 없을 때 기본값"을 무엇으로 할지**는 브리프가 "최대/최신 델타로 기본값을 두라"는 방향만 제시.
   ② 지점별 감소 카테고리 중 절댓값이 가장 큰 카테고리(모든 지점에서 공통적으로 External theft)를 `getDefaultCategory` 함수로 계산해 기본 표시.
   ③ 하드코딩하지 않고 매 지점 데이터에서 직접 계산하게 한 것은, 데이터가 바뀌어도 "최대 손실 원인"이라는 주장이 거짓이 되지 않도록 하기 위함 — 임의 설계라기보다 브리프의 명시적 요구를 코드로 옮긴 것.

6. ① **울트라와이드(1920px) 캡**은 "자신의 셸 기준으로 직접 계산하라"고만 지시됨.
   ② 캡을 전혀 두지 않고(max-w 없이) 좌측 앱 사이드바(256px)+로케이션 레일(256px)+우측 스포트라이트(12-col 중 4/12, flex-1 기반)가 전부 유동적으로 뷰포트를 채우도록 설계.
   ③ 브리프가 "캡은 선택 사항이고, fluid content가 선호된다"고 명시한 조건을 그대로 따른 임의 선택 — 2개 레일의 폭을 직접 계산해 1920px에서 우측 여백이 페이지 패딩(24px)뿐임을 확인.

7. ① **모바일(390px)에서 "3-pane"을 어떻게 접을지**는 브리프가 구체적으로 정하지 않음(아키타입 설명도 데스크톱 기준).
   ② 로케이션 레일을 모바일에서는 세로 리스트가 아니라 네이티브 `<select>` 하나로 바꾸고, 우측 스포트라이트는 워터폴 아래로 쌓음.
   ③ 이미 테이블이 자체 `overflow-x-auto`를 쓰므로, 레일까지 가로 스크롤 띠로 만들면 "한 페이지에 두 개의 가로 스크롤 컨테이너"가 되어 브리프가 명시적으로 금지한 패턴이 됨 — 그걸 피하려 `<select>`를 선택.

8. ① **아바타 표현 방식**은 "사진 대신 lucide 아이콘/이니셜을 쓰라"는 제약만 있고 구체적 처리는 지정되지 않음.
   ② 조사관 이름의 이니셜 2글자를 단색 원형 배지로 표시(`Avatar` 컴포넌트), `next/image`나 외부 이미지 호스트는 전혀 사용하지 않음.
   ③ 외부 이미지 호스트 의존성과 그에 따른 리스크를 원천적으로 없애는 가장 단순한 선택 — 기존 패턴(이니셜 배지)을 그대로 재사용.

9. ① **Progress 바가 정확히 무엇을 "목표"로 삼을지(임의의 눈금인지, 실제 임계값인지)**는 브리프가 지정하지 않음.
   ② `SHRINK_CRITICAL_PCT`(2.0%, `shrinkStatus`가 critical로 넘어가는 바로 그 임계값)를 progress bar의 `max`로 그대로 재사용.
   ③ 별도의 "표시용 눈금"을 임의로 두면 뱃지(Healthy/Watch/Critical)와 progress bar가 서로 다른 숫자를 말하는 모순이 생기므로, 하나의 상수를 두 곳에서 공유하도록 리팩터링 — 내부 일관성을 위한 선택.

10. ① **세그먼트 컨트롤의 크기 변형(좁은 KPI 카드에 들어가야 할 때)**은 브리프가 다루지 않음.
    ② `SegmentedControl`에 `size="sm"`(h-7, 24px 타겟사이즈 하한 유지) 옵션을 추가해 4번째 KPI 카드(Company trend)에서만 사용, 다른 곳(Incident ledger 필터)은 기본 크기(h-9) 유지.
    ③ xl 4열 그리드에서 KPI 카드 하나의 실제 콘텐츠 폭이 매우 좁아지는 것을 직접 계산해보고, 가로 스크롤이나 줄바꿈 대신 컴포넌트 자체에 안전한 축소 변형을 추가하는 쪽을 선택.
