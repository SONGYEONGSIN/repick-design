# Candidate C — Undertone · Feedback Intelligence Console

**Product/brand**: Undertone — a customer-feedback intelligence platform for B2B retail/e-commerce teams (theme mining across support tickets, reviews, and chat, with sentiment scoring). Route: `app/src/app/dash-evolve/r43/c/page.tsx`.

**One-line concept**: A feed-centric support console where the central, sortable "Feedback feed" ticket stream sits below a theme-intelligence panel — a hand-placed, deterministic phyllotaxis word cloud paired, as a first-class equal citizen (not an afterthought), with a fully ranked frequency + sentiment table — and the cloud/list's term selection and the feed's ticket pin drive two completely separate detail cards that never reset each other.

## Interactions implemented (4 required + 1 extra)
1. **Selection fan-out, two independently-scoped states (assigned tier 1)** — (a) pinning a ticket in `feedback-feed.tsx` only ever updates `pinned-ticket.tsx`'s rollup card; (b) clicking/focusing a theme in `word-cloud.tsx` or `theme-rank-list.tsx` only ever updates `term-detail.tsx`'s trend/mention panel. Neither selection reads or resets the other's state (`pinnedId` and `selectedTermId` are two separate `useState` calls in `page.tsx`, passed to disjoint consumer props). Both default to real, non-empty values (`DEFAULT_PINNED_ID` = the newest escalated ticket, `DEFAULT_TERM_ID` = the top theme) so neither card ever shows an empty "select something" placeholder on first paint. The feed *is* allowed to read `selectedTermId` to render a neutral "Matches theme" chip — that's the brief's own suggested example of what selection (b) should drive, not a violation of independence, since it never writes back to either state.
2. **Real sort + filter on the feed** — `feedback-feed.tsx`: status tabs (All/Open/Escalated/Resolved, counts always computed live from the data, never hand-typed) plus two sortable columns (`aria-sort`, Sentiment score and Reported time) via a shared `SortHeader`.
3. **Period/view toggle** — a 7d/30d/90d segmented control in the page header re-scopes the KPI row, the "Overall sentiment trend" sparkline, *and* the selected theme's own trend sparkline in `term-detail.tsx` simultaneously, from one `period` state.
4. **Hover/focus tooltip on the dominant chart, keyboard-accessible** — each word-cloud term is a real `<button>` (not SVG text, to dodge any SVG-specific `:focus-visible` risk) wrapped in a `group`; a CSS-only tooltip (`group-hover`/`group-focus-within`, `motion-reduce:transition-none`) reveals the exact count, share, and sentiment on hover *or* keyboard focus — but that same information is already permanently visible in the ranked list beside it, so the tooltip only adds a shortcut, never gates the only view of the number.
5. *(extra)* **⌘K command palette** — search filters themes and tickets live; picking a theme sets `selectedTermId`, picking a ticket sets `pinnedId`.

The header's primary action ("Log ticket") has a real `onClick` that opens a functioning right-side drawer (subject/customer/theme/notes fields, Escape and backdrop both close it) — not a dead button.

## Font/typography confirmation
- Body/UI text: `--font-sans` (Pretendard) throughout; **no display face** — the assigned "none" option. Hierarchy reads through size/weight/color alone (page `<h1>` at `text-2xl font-semibold`, card titles `text-sm font-semibold`, data at `text-2xl`/`text-sm` with `tabular-nums`).
- Exactly 3 rendered weights, grep-audited: `font-normal` (400, incl. the implicit Tailwind-preflight default on untouched text), `font-medium` (500), `font-semibold` (600). No `font-bold`/`font-light`/`b`/`strong` anywhere.
- All numeric displays use `tabular-nums` and are right-aligned in table cells; `Intl.NumberFormat` is used for counts and percentages, deliberately **without** `notation: "compact"` to dodge the Node-SSR-vs-browser ICU hydration mismatch the brief warns about — abbreviation is never needed since the dummy counts stay under 1,000.
- `TOTAL_MENTIONS` and every tab count in the feed are derived with `.reduce()`/`.filter()` from the single `TERMS`/`FEED_ITEMS` arrays, never hand-typed, so the ranked-list percentages and the feed's tab counts can never drift out of reconciliation with the underlying data.

## Completeness vs. the SaaS reference bar
- Full mandatory app shell: sidebar (brand lockup, workspace switcher cycling 3 workspaces, 5-item nav with active pill, bottom user/sign-out), top bar (⌘K search trigger, working primary CTA, notifications popover, avatar menu popover), mobile drawer — every header control individually `h-11`/`w-11` (44px), not just the bar container.
- Light theme, white-based: `bg-zinc-50` canvas, `bg-white` sidebar/topbar/cards, `border-zinc-200` hairlines, `shadow-sm`. Single accent **rose**, split by contrast need: `rose-700` (≈6.3:1 on white — AA-safe at body-text size, unlike `rose-600`'s ≈4.3:1) carries all accent *text*/solid buttons/focus rings; `rose-50` tints are always paired with `rose-700` text, never used for body text alone. Rose intentionally doubles as the "negative/alert" semantic color (escalated status, negative sentiment) rather than introducing a second red, keeping the palette to rose + emerald (positive) + zinc (neutral/structure) — still a single *decorative* accent.
- Component system in separate files: `Card`, `StatusBadge`, `SentimentBadge`, `PriorityTag`, `DeltaIndicator`, `SegmentedControl`, `Tabs`, `Avatar`, `Sparkline` (`ui.tsx`); sortable table (`feedback-feed.tsx`, `aria-sort`, hover rows, avatar cells); the required always-visible ranked list (`theme-rank-list.tsx`).
- One shared `DeltaIndicator`: its arrow direction always reflects the literal numeric sign of the delta, while color is computed separately from a per-metric `goodDirection` ("open tickets: down is good", "net sentiment: up is good", etc.) — so the same up/down icon can never be flipped relative to its claimed meaning at any of its four call sites (KPI row ×4, theme-detail trend).
- Explicit 12-col grid (`grid-cols-12`, 7/5 and 12/12 splits), every grid item `min-w-0`, 4-col KPI row only from `xl:` (`sm:col-span-6 xl:col-span-3`), no max-w cap on the content column — fully viewport-filling, so the ultra-wide gap at 1920px is just the page's own `lg:p-8` padding.
- `table-fixed` + `<colgroup>` percentages on both tables, `min-w`/overflow never used on individual cells; desktop has **zero** `overflow-x-auto` containers anywhere on the page (narrow columns are hidden responsively via `sm:`/`md:table-cell` instead of scrolled), so the "never two wide scroll containers" rule is satisfied trivially.
- Focus visibility uses the one verified-safe pattern (`focus-visible:outline-2 outline-offset-2 outline-rose-700`, never preceded by `outline-none`) on every interactive element, including the word-cloud term buttons, the command palette, and the new-ticket drawer's form fields (an early draft had `outline-none` alongside this recipe on the drawer's inputs — removed once traced through, since it permanently zeroes `outline-style` and silently kills the focus ring regardless of the `outline-2` width/color).
- `<dl>` usage (pinned-ticket card) keeps the icon inside `<dt>`, never wrapping both `dt`/`dd`.

## 브리프에 없던 것

1. **Which semantic color "negative sentiment" should use, given a single rose accent**
   ① The brief fixes rose as *the* one accent but says nothing about color for a three-way sentiment axis (positive/neutral/negative) that also needs to read as distinct from the brand accent itself.
   ② Let rose do double duty as both the brand accent *and* the negative/alert sentiment color (paired with `TrendingDown`), used emerald for positive, zinc for neutral — never a second, separate red.
   ③ Arbitrary but principled: it's the same pattern this catalog already uses for single-accent dark themes (e.g. a lime accent reused as the "positive" semantic color elsewhere in the catalog) — here it reads as "the one color that means both 'us' and 'something needs attention,'" a common real-world SaaS convention (e.g. error/alert states sharing a brand's red accent) rather than inventing a second near-identical hue.

2. **How to lay out a generative word cloud without SVG text, given the SVG-focus-risk warning**
   ① The brief asks for a "generative SVG/CSS" word cloud with a deterministic spiral and warns that SVG `<text>` elements can have real focus/pseudo-class issues, but doesn't say which markup to actually use for the terms themselves.
   ② Built the spiral purely in CSS: trig-computed `left%`/`top%` positions (golden-angle phyllotaxis, radius `∝ √i`, rounded to 2 decimals) applied to absolutely-positioned plain `<button>` elements, not an `<svg>` at all.
   ③ A native HTML `<button>` gets real, unambiguous `:focus-visible` behavior and a real accessible name "for free," sidestepping the exact SVG-text caution in the brief rather than trying to patch around it.

3. **How many word-cloud terms to show and how to keep small ones tappable**
   ① The brief requires a 24×24px minimum touch target for every term, including low-frequency ones, but not how many terms total or how small the smallest visual size should go.
   ② Used all 15 themes in the dummy dataset, with a font-size scale clamped to 13–34px purely for *visual* size, while every term button independently carries `min-h-6 min-w-6` (24px) regardless of its scaled font size, so the hit target never shrinks with the text.
   ③ 15 was simply "enough terms to make a cloud read as a cloud rather than a short list" while staying inside what a frequency table of the same size can still show one-screen, always-visible, in the paired ranked list — the two widths were kept in lockstep deliberately, not derived from any rule.

4. **Whether a KPI's "improved" direction should ever change the arrow's orientation**
   ① The brief's directional-icon check asks that an icon's orientation match its *claimed meaning* everywhere it's reused, but doesn't say whether "claimed meaning" should be the metric's literal direction or its good/bad verdict — these conflict for a KPI like "open tickets," where going down is good.
   ② Fixed the icon's rotation to the literal numeric sign only (`delta > 0` is always `TrendingUp`, regardless of metric) and moved all of the good/bad verdict into color via a separate `goodDirection` lookup per KPI.
   ③ This is the stricter, unambiguous reading of the brief's own check — an icon that flips orientation based on a secondary "is this good" judgment is the exact kind of silent mismatch the check is trying to catch, so direction was kept 1:1 with the number and verdict was pushed entirely onto color (never color alone, always paired with the same icon + a signed number).

5. **Whether the always-visible ranked list needs its own period toggle, separate from the trend charts**
   ① The brief requires the frequency-ranked list to be a first-class, always-visible fallback, but doesn't say whether its counts should themselves be period-scoped like the KPI row and the trend charts are.
   ② Kept `TERMS`' counts/percentages as a single all-time snapshot (not period-scoped), while the *trend* sparklines (`OVERALL_TREND`, `getTermTrend`) do respond to the period toggle.
   ③ Arbitrary simplification to avoid fabricating 3× as many mention-count datasets (one per period) that would need to individually reconcile against 3 separate period-scoped totals — the ranked list answers "what are the big themes, ever," the trend chart answers "how is sentiment moving lately," and conflating the two risked exactly the kind of sums-don't-reconcile bug the brief singles out.
