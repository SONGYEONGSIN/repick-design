# auto-native-r61 / candidate C — Dispute Resolution Outcome

**One-line concept**: A closed-case record screen (item, amount, dates, decision rationale, 4-step timeline) with a single persistent action bar — "Download Decision PDF" — that actually flips to a confirmed "Downloaded" state when pressed, never a state-machine band.

## Files
- `native/src/evolve/r61/c/DisputeResolutionOutcomeScreen.tsx` — screen component (named export `DisputeResolutionOutcomeScreen`, also default export).
- `native/src/evolve/r61/c/data.ts` — deterministic dummy data (`disputeOutcome` record: case facts, rationale, 4-step `timeline`).

**For the orchestrator**: import `{ DisputeResolutionOutcomeScreen }` (or default) from `native/src/evolve/r61/c/DisputeResolutionOutcomeScreen`. Suggested gate check-string: `"Dispute Resolution Outcome"` (the screen's `accessibilityRole="header"` title, always rendered, never conditional).

## Why this form (band = persistent single-action bar, not a state machine)
The dispute is already decided — refund issued, case closed on Nov 2, 2026. There is no blocked step and no "why can't I proceed yet" sentence to say, so per GENERATION.md §3's read-only-record carve-out, the bottom band is **not** a blocked/ready/done skeleton. It's a persistent action bar with exactly one always-available, real action. Everything above the bar (case summary, fact card, rationale, timeline) is strictly non-interactive — no tabs, no row taps, no expand/collapse — so the download button stays the only control on the screen, keeping the read-only/single-action distinction clean rather than blurring it with some other interactive mechanism elsewhere.

**Action chosen**: "Download Decision PDF." I rejected "Request Payout" because in my scenario the refund is already issued (not pending — there's nothing to request), and "Contact Support About This Case" felt like it would just open an unimplemented sub-flow (risking the `accessibilityHint` no-op trap from GENERATION.md §4). A decision PDF is realistically always available for a closed case and lets the press do something fully self-contained and observable within this screen's own state.

**Press behavior**: `handleDownloadPress` sets `receiptState` from `"available"` to `"retrieved"`. This swaps the `Pressable` out entirely for a plain confirmation `View` (`accessibilityRole="text"`, label "Decision PDF downloaded") — not a disabled-but-still-a-Pressable husk — so a second tap has no element left to no-op on. The bar's sentence text changes from "A PDF copy of this decision is available any time." to "Decision PDF saved to this device." Verified the `onPress` prop is actually wired (this round's open-delta: a declared state with full styles is not evidence it's reachable) — `handleDownloadPress` is passed directly to `onPress` and is the only place `setReceiptState` is called.

## Accessibility
- Live region pairing on the state transition (GENERATION.md §4, applies beyond bands to any "what can I do next" change): the action bar `View` carries `accessibilityLiveRegion="polite"`; only the one sentence `Text` inside it carries `accessibilityRole="alert"`. Nothing else in the bar or screen carries `alert`, so exactly one live region is active at a time (open-delta #2).
- No `accessible={true}` anywhere, and specifically never on a wrapper containing the `Pressable` (open-delta #3) — the action bar `View` only sets `accessibilityLiveRegion`, not `accessible`.
- `accessibilityHint="Saves a PDF copy of this case decision to your device."` is only attached to the idle-state `Pressable`, and the handler it sits on actually performs that transition (open-delta #4) — once the state flips, the hinted `Pressable` is gone (replaced by a label-only `View`), so there's never a hint attached to a button that can't act on it.
- Section headings (`Dispute Resolution Outcome`, `Decision Rationale`, `Case Timeline`) use `accessibilityRole="header"`.

## Determinism
All dates (`Oct 14, 2026` filed → `Nov 2, 2026` resolved, plus the 4 intermediate timeline dates) and amounts (`$420.00` disputed, `$180.00` refunded) are fixed strings in `data.ts`. No `Math.random`, `Date.now`, or bare `new Date()`.

## RN idiom / tokens
Plain `react-native` core only (`View`/`Text`/`Pressable`/`FlatList`/`SafeAreaView`/`StyleSheet`) — no Expo-specific or navigation APIs, since this screen renders standalone outside a navigator. The 4-step timeline uses `FlatList` with `data`/`renderItem` (not `.map()`) per the RN-idiom rule, even though the list is short, with the case summary as `ListHeaderComponent`. All colors/spacing/radius come from `tokens.ts` (`tokens.color.success`/`successBg`/`successBorder` for the "Resolved" status chip and refund-amount emphasis; `tokens.color.accent` only for the timeline dots and the primary download button — single accent, no hardcoded hex anywhere).

## Duplication check against r56–r60
- Nearest precedent is `r56/c` (read-only tier status + one-shot persistent share action bar) — same sanctioned band *form*, different domain, and I did not reuse its style-key names, copy, or control-flow shape (my states are `"available"`/`"retrieved"` driving a Pressable-vs-View swap, not a boolean flag toggling a single element's style).
- Distinguished from `r60/c` (Dispute Evidence Checklist, same broad "dispute" domain) by focus: r60/c is about *assembling* evidence for an *open* dispute (selection-count-derived band, submit threshold); mine is the *already-decided outcome* of one (no selection state, no threshold, nothing left to assemble — pure record + one download action). Copy is written to keep this distinction legible: "already closed," "resolution issued," "case timeline" vs. r60/c's "attach," "submit," "required."
- Distinguished from `r59/c` (2-tab compare, chooser band locks to permanent status after press) by having **no tab-switching or content-swap mechanism anywhere else on the screen** — the only interactive element on the whole page is the single action-bar button; everything above it is inert record content.

## 브리프에 없던 것
1. **① Exact dispute scenario / domain details.** ② A Leica M6 camera body dispute: buyer claims condition didn't match listing, seller offered store credit, support issued a partial refund ($180 of $420 disputed) in the buyer's favor. ③ The brief only specified the screen *form* (read-only record + action bar) and an example outcome sentence; I needed a concrete, plausible item/amount/reasoning to make the fact card and rationale paragraph non-generic, and picked "partial refund" specifically because it's richer than a clean full-refund/no-refund binary — it gives the rationale paragraph something real to explain.
2. **② Which single action to make real.** Chose **"Download Decision PDF"** over "Request Payout" or "Contact Support." ③ Payout doesn't fit because my scenario's refund is already issued, not pending; Contact Support risked becoming an unimplemented-navigation stub (hint no-op trap). A downloadable decision record is realistically always available for *any* closed dispute regardless of refund status, so it generalizes better as "the one always-available action" the brief asks for.
3. **② Confirmed-state design: swap the `Pressable` for a plain `View` on success, rather than keep a `Pressable` and disable it.** ③ This was the cleanest way to guarantee the `accessibilityHint` no-op trap is structurally impossible after the first press — there's no interactive element left for a hint to misrepresent.
4. **② The 4 timeline steps and their labels** ("Dispute Filed" → "Evidence Reviewed" → "Seller Response Received" → "Resolution Issued") and their dates spanning Oct 14 → Nov 2, 2026. ③ The brief asked for "3-4 steps" generically; I picked 4 to show a believable review cadence (roughly 5 days apart) ending exactly on the stated resolved date.
5. **② Status chip color: `tokens.color.success` (not `warning` or `accent`).** ③ The case is closed and resolved — not pending, not neutral — so the positive/settled semantic (success) fit better than warning (which the tokens reserve for "expiring/at-risk" states) or accent (reserved for the single primary-action color, which would blur the chip with the download button).
6. **② Style key naming scheme** (`actionBar`, `actionBarSentence`, `actionButton`, `actionButtonDone`, `factCard`, `factRow`, `timelineDot`, etc.) chosen to not share any key name with the `band*`/`statusFor`/`jumpTo` vocabulary GENERATION.md flags from prior rounds, and not copied from `r56/c`'s or `r60/c`'s key names. ③ GENERATION.md §3's L2 rule: form reuse is sanctioned, literal code-surface reuse (style keys, copy, control flow) is what judges actually catch.
7. **② Used `FlatList` for a 4-item timeline rather than a plain mapped `View` list.** ③ GENERATION.md §1 states the RN idiom is `FlatList` with `data`/`renderItem` instead of `.map()` for lists generally, with no "unless short" carve-out, so I followed it even at this small scale to stay inside the stated idiom.
