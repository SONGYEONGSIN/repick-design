# auto-native-r62 / candidate C — Seller Monthly Performance Digest

**One-line concept**: A closed, finalized monthly seller summary — sales total, a view-count trend, a rating trend, and a 3-item ranked list of that month's top-performing listings (each tap-expandable for a short detail note) — with a single persistent bottom action bar, "Export PDF Report," that flips to a genuinely confirmed "Exported" state on press rather than resetting itself.

## Files
- `native/src/evolve/r62/c/SellerMonthlyPerformanceDigestScreen.tsx` — screen component (named export `SellerMonthlyPerformanceDigestScreen`, also default export).
- `native/src/evolve/r62/c/data.ts` — deterministic dummy data (`monthlyDigest` record: period, totals, trends, `topListings` array of 3).

**For the orchestrator**: import `{ SellerMonthlyPerformanceDigestScreen }` (or default) from `native/src/evolve/r62/c/SellerMonthlyPerformanceDigestScreen`. Exact visible heading text for the automated check string: **"Seller Monthly Performance Digest"** — this is the screen's `accessibilityRole="header"` title, rendered unconditionally on first render, never behind any state branch.

## Why this form (persistent read-only action bar, not a state machine)
October's book is closed — the digest is explicitly labeled "Finalized Nov 1, 2026 — figures below will not change." There's no pending step and no "why can't I proceed" sentence to justify a blocked/ready/done skeleton band, so per GENERATION.md §3 this gets form (b): one always-visible bottom bar offering exactly one real, honest action — exporting a PDF copy of the digest. Everything above the bar is read-only record content; the only other interaction on the screen is the optional per-row disclosure on the top-listings list, which is local, non-destructive, and carries no live region of its own.

**Press behavior**: `runExport` moves `reportStatus` from `"unexported"` to `"exported"`, one-way and guarded against re-firing. Unlike swapping the control out for an inert `View`, I kept the *same* `Pressable` mounted and simply `disabled` it afterward (`accessibilityState={{ disabled: isExported }}`), relabeling it "Exported," because that still makes the terminal state reachable only through a real tap while keeping the control surface itself stable — a deliberately different confirmed-state strategy from r61/c's Pressable→View swap, not a structural copy of it.

## Accessibility
- The live-region wrapper `statusAnnouncer` is unconditionally mounted from first render (its text is `"This digest is closed for October — export a PDF copy any time."` before any export, and switches after); only the inner `Text`'s content changes, with `accessibilityRole="alert"` on that `Text` and `accessibilityLiveRegion="polite"` on its containing `View`. It is the only live region on the screen.
- The top-listing rows pair `accessibilityState={{ expanded }}` on each row's `Pressable` with `accessibilityElementsHidden` + `importantForAccessibility="no-hide-descendants"` on the decorative `+`/`–` glyph, so the glyph is never announced as a second signal of the same expand/collapse state.
- No wrapper `View`/`Pressable` uses `accessible={true}`; labels sit on the leaf `Pressable`s (export button, each listing row) instead.
- `accessibilityHint`s describe exactly what the matching `onPress` does and nothing more: the export hint only appears pre-export and is removed once exported (no hint survives onto a disabled control it no longer describes); the per-row hint says "Expands"/"Collapses" and the `onPress` is a pure open/close toggle, nothing else.
- Touch targets are computed, not eyeballed (see the two math comments in the stylesheet): the export control's `paddingVertical` (16×2=32) plus its label's `lineHeight` (20) totals 52pt, and the listing-card header's `paddingVertical` (12×2=24) plus its shortest possible one-line title+meta stack (18+16=34) totals 58pt — both independently clear 44pt, with an explicit `minHeight: 44` as a second guarantee on each.

## Determinism
All figures in `data.ts` are fixed literals: `$8,240.50` sales total, `47` orders, `14,320` views (`+12% vs September`), `4.86` average rating over `156` ratings (`+0.04 vs September`), and three named listings with fixed unit counts and revenue figures. No `Math.random`, `Date.now`, or bare `new Date()` anywhere.

## RN idiom / tokens
Core `react-native` only (`View`/`Text`/`Pressable`/`FlatList`/`SafeAreaView`/`StyleSheet`), no Expo-specific or navigation APIs. The ranked top-listings section is the screen's one `FlatList` (`data`/`renderItem`, not `.map()`); it sits as its own `flex: 1` sibling between a plain, non-scrolling header `View` and the fixed footer `View` — deliberately NOT a root-level `FlatList` with everything else stuffed into `ListHeaderComponent` (see "Duplication check" below), and deliberately not a `FlatList` nested inside a `ScrollView` either, since nesting a scrollable `VirtualizedList` inside a `ScrollView` of the same orientation is an RN anti-pattern this layout avoids by only ever having the one scrollable region. All colors/spacing/radius come from `tokens.ts` — `tokens.color.accent`/`accentBg` for the one primary action, the finalized-pill chip, and the rank badges; `tokens.color.success`/`danger` only for the small up/down trend footnotes (matching this repo's existing semantic-color convention, not a new hardcoded hue).

## Duplication check against r61/c and recent rounds
- **r61/c (Dispute Resolution Outcome)** is the closest analog (same form-(b) mechanism, also a PDF-style export-and-confirm action) and the one GENERATION.md explicitly flags. Differentiated on: (1) layout — r61/c is a root-level `FlatList` with a `ListHeaderComponent` holding the case summary; this screen puts the header+stats in a plain `View` *above* a smaller, purpose-built `FlatList`, with the footer below both as a true sibling, not the next item after a header component; (2) confirmed-state mechanics — r61/c swaps its `Pressable` for an inert `View` on success, this screen keeps the same `Pressable` and disables it; (3) style-key vocabulary — no shared names (`recordFooter`/`exportControl`/`exportControlDone`/`statusAnnouncer`/`runExport` here vs. `actionBar`/`actionButton`/`actionButtonDone`/`handleDownloadPress` there); (4) copy voice — "This digest is closed for October," "Exported," "Finalized Nov 1, 2026" vs. "available any time" / "Downloaded" / "Resolved — Buyer"; (5) this screen adds a second, independent interactive mechanism (per-row disclosure on ranked listings) that r61/c deliberately has none of.
- **r54/c (Seller Performance Score Breakdown)** is the nearest "seller + metrics" neighbor but has no band at all (in-flow conditional action at the end of a `ScrollView`, gated on data health) and uses a `Set<string>` for multi-row expansion. This screen has a persistent bottom band whose action is unconditionally available (nothing to gate — the digest is simply done), and uses a single nullable `openListingId` (only one row open at a time), not a `Set`.
- Not reusing any domain from the excluded list (local meetup scheduling, price-drop alerts, seller tier milestones, search presets, mis-description queue, locker selection, bulk discounts, warehouse intake, plan comparison, customs declaration, age/ID verification, dispute evidence checklist, seller identity re-verification, saved payment methods, dispute outcome) or any production screen folder (account, auction, authentication, certificate, charts, chat, condition, detail, disputes, handoff, listing, meetup-time, membership, notifications, offer-thread, order-status, payout, pickup, relist, review, sessions, storefront, verification, wallet, watchlist, MatchList).

## Brief gaps
1. **① Exact sales/view/rating figures and the reporting month.** ② Sales total `$8,240.50` over `47` orders; `14,320` views (`+12% vs September`); `4.86` average rating over `156` ratings (`+0.04 vs September`); the closed month is **October 2026**, finalized `Nov 1, 2026`. ③ The brief named the metric *categories* (sales total, view trend, rating trend) but not concrete values. Today's in-world date is Nov 23, 2026, so October is the most recently closed calendar month — a natural, defensible choice for "a closed, already-finalized monthly summary." I picked numbers that are internally consistent (a plausible average order size, a plausible view-to-order ratio) rather than round, obviously-fake figures.
2. **② Number of top-performing listings shown.** ② Three. ③ The brief said "a short ranked list" without a count. Three is short enough to read at a glance without scrolling, still gives the rank concept (1st/2nd/3rd) real meaning, and matches this repo's convention for "short" lists in nearby candidates (e.g. r61/c's 4-step timeline, which called itself a comparably-sized record list).
3. **② What the exported PDF conceptually contains.** ② A one-page export mirroring exactly what's on screen: the period, the three headline figures with their trend deltas, and the ranked top-listings table with unit/revenue figures. ③ The brief said "exporting/downloading a PDF report of the digest" without specifying scope; since this is a *digest* screen and the whole point is that it's a finished, legible summary, the PDF's natural scope is "this screen, as a document" rather than a deeper drill-down the UI doesn't otherwise expose.
4. **② Whether the top-listing rows should be expandable at all, versus a flat non-interactive list.** ② Made each row tap-expandable for one short `detailNote` sentence, using the accordion pattern GENERATION.md §4 explicitly anticipates ("If you use any accordion/expand-collapse row..."). ③ A flat list would have been simpler, but the brief's accessibility section specifically pre-supplies the accordion a11y pairing rule, which read as an invitation to use one somewhere reasonable; a ranked listing row is a natural fit since "why is this one #1" is a real question a seller would want answered without leaving the screen.
5. **② Confirmed-export mechanic: keep the same `Pressable` and disable it, vs. swapping it for a separate `View` (the r61/c pattern).** ③ Chosen specifically to produce a code-surface and interaction-model difference from the closest analog while still satisfying every stated requirement (real one-way state flip, reachable only via `onPress`, `accessibilityState` reflecting disabled-ness, no stale hint left behind).
6. **② Style-key and function naming scheme** (`recordFooter`, `exportControl`/`exportControlDone`, `statusAnnouncer`, `runExport`, `toggleListing`, `rankBadge`, `disclosureGlyph`, etc.). ③ Chosen to share no key or function name with r61/c's (`actionBar`, `actionButton`, `actionButtonDone`, `handleDownloadPress`, `receiptState`) or with r54/c's (`actionSection`, `confirmationCard`, `handleRequestReview`), per the explicit architecture-cloning risk flag for this round.
