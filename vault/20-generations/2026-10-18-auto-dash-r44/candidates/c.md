# Candidate C — Quorum

**One-line concept**: Quorum is a reliability console for a platform-engineering team — a live incident feed as the page's main event, with a six-service response-time box-plot bench sitting above it and feeding a single pinned Service Detail card (tier-2 selection split).

- Archetype: feed-centric shell (central incident/alert stream) + box-plot bench as the dominant visualization (response-time distributions, six services).
- Theme: light (white canvas, white cards, `border-zinc-200`) · accent: **violet-600** (`#7c3aed`) · display face: `--font-display-mono` (JetBrains Mono Display).
- Structure, top to bottom: KPI strip (4 cards) → Latency distribution bench (full width) → Incident feed (8 cols) + Service detail (4 cols) → Monitors table (full width, sortable).

## Interactions (4+ implemented)

1. **Crosshair hover/focus on the box-plot bench** (`box-plot-bench.tsx`) — six real `<button>` overlays (one per service column) sit over a hand-built SVG box-plot. Hover *or* keyboard focus (`onMouseEnter`/`onFocus` paired, `onMouseLeave`/`onBlur` paired) sets `hoveredServiceId`, which (a) draws a dashed vertical crosshair line **inside the SVG's own viewBox** (never absolutely positioned over the chart, so it can never push the page wider at any viewport) and (b) swaps a one-line readout paragraph directly above the chart from its default instructional text to the exact hovered group's median/Q1/Q3/range. Each overlay button's sole content is an `sr-only` span carrying the full five-number summary, so screen-reader users get the same information on focus with no separate announcement path needed.
2. **Real sort/filter on the incident feed** (`incident-feed.tsx`) — status tabs (All/Open/Investigating/Resolved) + a severity filter popover (checkable Critical/Warning/Info) + a text search, all composing together, plus two `aria-sort` sortable columns (Severity, Age) with ascending/descending toggle.
3. **Period/view segmented control** (1h / 24h / 7d, in the page header) — recomputes two KPIs (Fleet P95 latency, Latency spread/IQR), the entire box-plot bench's five-number summaries, the incident feed's time window, and the Service Detail card's P95/summary/open-count. The Monitors table is deliberately **not** wired to it (see brief gaps below).
4. **Selection → multi-widget sync, tier 2** — (a) a **persistent pin**: clicking a box-plot group *or* clicking a feed row's pin button sets `pinnedServiceId`, which feeds exactly **one** narrow consumer, the Service Detail card (the pinned box's own border/fill highlight and the pinned feed row's own background tint are self-identity markers on the source widgets, not a second consumer). (b) an **ephemeral hover/focus preview** touching no persistent state: hovering/focusing a box-plot group also drives a one-line "Comparing: …" note inside the Service Detail card, explicitly guarded by `hoveredServiceId !== pinnedServiceId` so it never fires when the hovered group is already the pinned one. The Service Detail card never renders an empty "select something" placeholder — its default pin (`checkout-api`) is computed at module load from whichever service has the most open incidents in the default 24h window.

Also present: a sortable **Monitors** table (`monitors-table.tsx`, 4 `aria-sort` columns: Service/Status/Uptime/P95, plus avatar and sparkline cells), a working ⌘K command palette, a functional "New monitor" drawer, and a notifications popover — none of these are decorative; every header button has a real `onClick`.

## Font/typography confirmation

- Body, every label, every table cell, every badge: `--font-sans` (Pretendard), no exceptions, no extra `next/font` import anywhere.
- Display face: exactly **one**, `--font-display-mono`, applied via inline `style={{ fontFamily: "var(--font-display-mono)" }}` (never a bare `font-family` string) to three places only, all Latin/numeral large text: the sidebar wordmark "Quorum", the four KPI-strip numbers, and the Service Detail card's big P95 figure.
- Rendered font weights, route-wide: exactly 3 — `font-normal` (400), `font-medium` (500), `font-semibold` (600). Every heading explicitly carries one of these (no default-bold `<h1>`/`<h2>`).
- All numeric values are `tabular-nums` and right-aligned where tabular (table cells); every label is `text-[11px] uppercase tracking-wide`/`tracking-[0.06em]`.
- Accent contrast: `violet-600` (#7c3aed) on white ≈ **5.70:1** by WCAG relative-luminance math (self-computed: L(white)=1.0, L(#7c3aed)≈0.1343, contrast=(1.05)/(0.1343+0.05)=5.70) — clears AA body text (≥4.5:1) with margin, so it is used directly for links/icons/active states, not just large UI. `zinc-500` on white ≈ 4.83:1 (AA floor, used for the lightest permitted text); `zinc-400` is never used for text anywhere (confirmed by search).

## 브리프에 없던 것

1. ① The concrete SaaS product/domain the box-plot bench and feed should be about — the brief only said "box-plot bench… test-duration, latency, deal-size… your choice" and "incident/alert feed" as one feed-centric option.
   ② Invented **Quorum**, an internal reliability console for a platform-engineering team: a response-time box-plot bench across six services (`checkout-api`, `payments-api`, `search-api`, `auth-api`, `notifications-svc`, `media-cdn`) paired with a live incident/alert feed for those same six services.
   ③ Chose this specific pairing (not test-duration/deal-size) because it lets one shared vocabulary ("service") drive every widget on the page — the bench, the feed, the Monitors table and the pin consumer all key off the same six `serviceId`s — which is what makes the tier-2 pin wiring ("click a feed item *or* a box-plot group") read as one coherent product instead of two bolted-together demos.

2. ① The exact incident dataset (how many incidents, what ages, what severities/statuses) and the exact latency-generation formula — the brief only requires "deterministic… realistic" dummy data and bans `Math.random`/`Date.now`/`new Date()`.
   ② Wrote 14 literal incidents with fixed `ageMinutes` offsets (6 to 7800) chosen so the 1h/24h/7d period windows each surface a different, non-degenerate slice (4 / 10 / 14 incidents respectively), and a latency generator (`generateLatencySeries`) built from three stacked `Math.sin`/`Math.cos` waves keyed only by `(serviceIndex, periodIndex, sampleIndex)` — same inputs always give the same output.
   ③ Arbitrary but deliberately checked by hand against the three tested periods so none of them would show an empty or identical-to-another-period incident list, which would have made the period toggle feel inert.

3. ① How to guarantee min ≤ Q1 ≤ median ≤ Q3 ≤ max "computed from one function, never hand-typed per group" in a way that survives the period toggle too.
   ② Wrote a single `percentile(values, p)` (sort + linear interpolation) and a single `fiveNumberSummary(values)` built only from repeated calls to it; every service/period combination, the fleet-wide KPI figures, and the P95 column all call these same two functions on different input arrays — never a hand-typed number anywhere in the five-number chain.
   ③ Not optional — this was the brief's explicit structural requirement, but *how* to implement it (percentile method, where to centralize it) was left open, so I centralized it at the data-layer level rather than per-component to make the guarantee mechanical rather than reviewable-by-eye.

4. ① Where to put the box-plot's "crosshair hover tooltip" without creating a sweep-gate overflow risk — the brief requires it but doesn't say how to position it.
   ② First built a classic absolutely-positioned floating tooltip anchored to the hovered column's x%, then rejected it once I traced the math: at the leftmost/rightmost of six columns on a narrow viewport, a `whitespace-nowrap`, `-translate-x-1/2` tooltip can extend past the container's left/right edge with nothing clipping it, which is exactly the kind of absolutely-positioned overflow the sweep gate's `scrollWidth > clientWidth` check is built to catch. Replaced it with (a) a dashed crosshair line drawn *inside* the SVG's own `viewBox` (bounded by construction, can never overflow) and (b) a readout paragraph in normal document flow above the chart that swaps its text on hover/focus (no absolute positioning, no overflow surface at all).
   ③ Not in the brief, but directly motivated by this exact brief passage: "A desktop horizontal-scroll strip… is caught by the sweep gate… verify your real rendered widths" — I generalized that caution from scrolling strips to absolutely-positioned tooltips, since the failure mode (something escaping its container's bounds) is the same.

5. ① The exact algorithm for the Service Detail card's default (first-paint) pin, and for the KPI deltas' comparison baseline — the brief only says "give it sensible default content" and "verify... internally consistent," not the formula.
   ② Default pin = whichever service has the most non-resolved incidents inside the default 24h window, tie-broken by worst P95 (`getDefaultPinnedServiceId`, computed once at module load, currently resolves to `checkout-api`). KPI deltas for Fleet P95 and Latency-spread (IQR) always compare the selected period against the 7-day figure ("vs 7-day baseline"); when the 7-day period itself is selected, the card shows the words "7-day baseline" instead of a self-comparison delta of 0, so no KPI ever claims a meaningless trend.
   ③ Arbitrary but chosen so the comparison is always well-defined (the 7d dataset is the superset of every other period, so "vs 7-day" never has a missing counterpart) and so the pin is reproducible from the data rather than a hardcoded id that could silently go stale.

6. ① Whether the Monitors table should also respond to the page-level period toggle, and whether avatars need `next/image`.
   ② Kept Monitors deliberately independent of the period toggle — its Status and "P95" columns are fixed to a live/trailing-24h view (labelled as such in the section's subtitle), the same way a real fleet-health roster usually shows "current state" rather than retargeting to whatever window an analyst happens to be looking at elsewhere on the page. For on-call avatars, used plain initials-in-a-colored-circle (`Avatar` component, decorative `aria-hidden`, real name given as adjacent visible text) instead of photographic avatars, since the brief's `next/image` rule only engages "for any avatars" that are actual images — no `<img>`/`<Image>` appears anywhere on the page.
   ③ Both are arbitrary but defensible product decisions: the first avoids a roster table that silently reshuffles every time someone is just comparing latency windows elsewhere; the second sidesteps the entire fixed-URL/remote-host/`unoptimized` constraint surface for a cast of three fictional on-call engineers where a photo would add risk with no real benefit.

7. ① The exact ultra-wide (1920px) right-edge gap, and whether a `max-w` cap is needed at all.
   ② No `max-w` cap anywhere — the shell's own geometry already satisfies the ≤40px rule. At 1920px: sidebar `w-64` = 256px fixed, main content padding `lg:p-8` = 32px each side → available grid width = 1920 − 256 − 64 = 1600px, flush to the content edge, leaving exactly the 32px padding as the right-edge gap (≤40px).
   ③ Verified by the same arithmetic this round's own prior candidate used for its grotesk-font shell with a cap; here the fixed sidebar + fixed padding alone already clears the bar without a cap, so adding one would only have been extra, unnecessary surface area to get wrong.

8. ① Whether the two "value went up/down" icon families (KPI deltas vs. table sort order) could safely share the same ArrowUp/ArrowDown icons the brief's own "directional icon check" warns about.
   ② Switched the KPI `DeltaIndicator` to `TrendingUp`/`TrendingDown` (kept `ArrowUp`/`ArrowDown`/`ArrowUpDown` exclusively for the two tables' sort headers), so the two unrelated meanings — "this value moved" vs. "this column is currently sorted this direction" — are never rendered with the same glyph anywhere on the page.
   ③ Arbitrary — nothing in the brief forbids reusing one arrow family for two honestly-consistent meanings in separate components — but the brief flags this exact trap explicitly enough that paying the one-icon-swap cost to remove the ambiguity entirely seemed cheaper than relying on "it's fine, they're in different components" holding up under review.
