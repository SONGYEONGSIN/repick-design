# r18 · b — Tenure 갱신 데스크

**한 줄 컨셉** — B2B 구독 갱신 데스크 **Tenure**(다크·rose 단색 액센트, Pretendard 단일 활자)를 **마스터-디테일 골격**(셸 사이드바 + 비율 기반 갱신 목록 레일 + `flex-1 min-w-0` 상세 페인)으로 짜고, 상세 안에 **시점 스크러버**(T-12 → 갱신)를 주 컨트롤로 두어 레일을 건드리지 않고 상세만 시간축으로 움직이게 했다. 적용 인터랙션: ① 좌석 소진 차트 크로스헤어 툴팁(포인터 + 화살표 키) ② 지원 티켓 테이블 실제 정렬(`aria-sort` · 컨테이너 쿼리로 모바일 카드 교체) ③ 레일 리스크 등급 필터 + 정렬 드롭다운 ④ 시점 스크러버(range + 이전/다음/갱신 시점 복귀 — 사용량 커서·시점 리스크 배지·4개 카운터·이벤트 윈도·티켓 원장을 동시 재계산) ⑤ ⌘K 커맨드 팔레트.

## 브리프에 없던 것

### 1. 리스크 등급을 몇 가지 색으로 나눌 것인가
- **무엇을 정해야 했나** — 브리프는 "액센트: rose 계열 1색"과 "색만으로 의미 전달 금지"를 동시에 요구한다. 리스크 3단계(위험/주의/안정)를 rose 하나의 명도 차이로만 낼지, 상태색을 따로 둘지.
- **무엇으로 정했나** — 브랜드 액센트는 rose 단색으로 고정(활성 nav pill, 기본 버튼, 차트 주 계열, 스크러버, 선택 행)하고, 리스크 등급에만 위험 = rose-400 / 주의 = amber-200 / 안정 = zinc-300 을 쓰되 **세 등급 모두 lucide 아이콘 + 한글 라벨 + 점수 숫자를 항상 병기**했다. 추가 색상은 amber 하나뿐이다.
- **왜 그렇게 정했나** — rose 명도만으로 3단계를 나누면 "색만으로 의미 전달 금지" 조항을 지켜도 실사용에서 등급이 구분되지 않는다. 아이콘·텍스트·숫자를 항상 붙이면 색은 보조 채널이 되므로, 액센트 1색 원칙의 취지(브랜드 톤의 단일성)는 유지하면서 상태 구분은 의미로 전달된다.

### 2. 시점을 옮겼을 때 이벤트·티켓을 어느 폭으로 보여줄 것인가
- **무엇을 정해야 했나** — "그때 무슨 일이 있었나"가 정확히 그 달만인지, 앞뒤를 포함하는 구간인지.
- **무엇으로 정했나** — 이벤트는 **시점 ±2개월**, 지원 티켓은 **시점 포함 직전 3개월**. 계약당 사건은 다섯 개를 인덱스 {0,3,5,8,11}·{1,4,6,9,12}·{2,4,7,9,12} 류로 흩어 배치해 13개 시점 어디에 서도 창이 비지 않게 했다.
- **왜 그렇게 정했나** — 갱신 판단은 "그 달의 스냅숏"이 아니라 "그 무렵의 정황"을 읽는 일이라 단월 필터는 정보가 아니라 빈칸을 만든다. 반대로 창을 넓히면 스크러버를 움직여도 내용이 거의 안 바뀌어 컨트롤이 무의미해진다. ±2 / 직전 3개월이 "움직이면 확실히 바뀌되 비지는 않는" 폭이었다. 빈 상태 문구도 zinc-300/zinc-400 으로 별도 작성해 대비 하한을 지켰다.

### 3. 상세 페인의 내부 브레이크포인트를 무엇으로 잴 것인가
- **무엇을 정해야 했나** — 상세 페인의 폭은 뷰포트가 아니라 레일 비율에 종속된다(1280 에서 589px, 1920 에서 1115px). 뷰포트 브레이크포인트로 내부 그리드를 나누면 실제 폭과 어긋난다.
- **무엇으로 정했나** — 상세 페인 루트에 `@container` 를 걸고 내부는 전부 컨테이너 쿼리(`@md`/`@xl`/`@2xl`)로 나눴다. 티켓 표는 `@xl`(576px) 이상에서만 진짜 `<table>` 이고 그 아래는 스택 카드로 **교체**한다.
- **왜 그렇게 정했나** — delta 1 이 지적한 실패(퍼센트 열이 nowrap 헤더의 고유 최소폭 아래로 눌려 옆 열로 번지지만 `scrollWidth` 는 멀쩡한 상태)는 컨테이너가 실제로 좁을 때 발생하는데, 그 "실제로 좁다"를 뷰포트로는 잴 수 없다. 겸해서 열 헤더는 2글자("접수·등급·상태")로 줄여 11px uppercase + 정렬 화살표의 고유폭이 최소 열폭(17%)에 들어가도록 실측 배분했고, 긴 표현("접수일·심각도")은 폭 여유가 있는 모바일 정렬 칩 쪽에 남겼다.

### 4. 오늘 날짜와 갱신일을 어떻게 고정할 것인가
- **무엇을 정해야 했나** — D-일수와 13개월 라벨을 만들려면 기준 시각이 필요한데, 인자 없는 Date 생성자는 하드페일이다.
- **무엇으로 정했나** — Date 자체를 아예 쓰지 않았다. 계약마다 `renewYear/renewMonth/renewDay/daysOut` 을 직접 적고, 13개월 라벨은 `renewYear * 12 + (renewMonth - 1) - (12 - i)` 정수 산술로 만든다.
- **왜 그렇게 정했나** — ISO 문자열을 인자로 넘기면 규칙은 통과하지만 서버/클라이언트 타임존 차이로 하루가 밀려 하이드레이션이 깨질 여지가 남는다. 날짜 연산을 정수 산술로 내리면 그 여지가 0이 된다.

### 5. 스크러버와 차트가 같은 상태를 만질 때 어느 쪽이 소유자인가
- **무엇을 정해야 했나** — 차트에도 키보드 크로스헤어를 요구받았는데, 차트가 자체 커서 상태를 가지면 스크러버와 두 개의 진실이 생긴다.
- **무엇으로 정했나** — `vantage` 는 상세 페인이 소유하고, 차트는 `vantage`/`onVantage` 만 받는다. 차트의 자체 상태는 포인터 hover 인덱스 하나뿐이며 이건 툴팁만 바꾸고 페이지의 다른 부분은 건드리지 않는다. 차트 플롯은 `tabIndex=0` 로 화살표·Home·End 를 받아 스크러버와 **같은** 값을 움직인다.
- **왜 그렇게 정했나** — hover 가 이벤트 목록과 카운터까지 바꾸면 마우스를 스치기만 해도 페이지가 요동친다. "잠깐 미리보기(hover)"와 "이 시점에 선다(vantage)"를 분리하되 키보드 경로는 vantage 로 통일해야, 화살표 키만으로도 마우스 사용자와 동일한 정보에 도달한다.

### 6. 셸 사이드바와 마스터 레일을 어떻게 구별할 것인가
- **무엇을 정해야 했나** — 브리프가 명시적으로 경고한 지점. 왼쪽에 세로 목록이 두 개 서면 위계가 뭉갠다.
- **무엇으로 정했나** — 셸 사이드바는 `bg-zinc-950` 위에 테두리 없는 아이콘 nav(높이 36px 행, 섹션 라벨 11px uppercase)로, 마스터 레일은 `border-white/10 + bg-zinc-900/40` 의 **둥근 표면**으로 카드 안에 담고 자체 필터 바·스크롤 영역·합계 푸터를 붙였다.
- **왜 그렇게 정했나** — 하나는 "앱의 장소", 하나는 "데이터의 목록"이다. 표면(카드 vs 배경)과 밀도(아이콘 행 vs 4줄 데이터 행)를 다르게 하면 폭이 비슷해도 두 목록이 같은 종류로 읽히지 않는다. 레일 폭도 고정 px 이 아니라 `lg:basis-[38%] / xl:34% / 2xl:30%` 비율로 두어, 폭이 넓어질수록 상세가 더 벌어진다.

### 7. 초광폭에서 캡을 둘 것인가
- **무엇을 정해야 했나** — 1920px 에서 콘텐츠 우단과 뷰포트 사이가 페이지 패딩뿐이어야 한다는 결과 기준.
- **무엇으로 정했나** — `max-w` 를 아예 두지 않고 페이지 좌우 패딩을 `lg:px-6`(24px)으로 고정했다. 1920 기준 사이드바 256 + 패딩 48 → 가용 1616 을 레일 485 / 갭 16 / 상세 1115 로 나눈다.
- **왜 그렇게 정했나** — 캡을 두면 "가용폭보다 큰 값"을 셸 폭이 바뀔 때마다 다시 계산해야 하고 틀리면 그대로 감점이다. 캡이 없으면 우단 여백은 정의상 항상 24px 이고, 비율 배분이 상세를 계속 넓히므로 초광폭에서 레일만 늘어나는 붕괴도 생기지 않는다.

### 8. 리스크 점수를 하드코딩할 것인가 파생시킬 것인가
- **무엇을 정해야 했나** — 시점마다 리스크 배지가 바뀌어야 하는데, 8개 계약 × 13개월 = 104개 점수를 손으로 적을지.
- **무엇으로 정했나** — `50 − 활용률·40 − 3개월추세·68 − 6개월추세·30 + 당월티켓·3.4 + 전월티켓·1.7 + baseRisk` 를 6..96 으로 clamp 한 순수 함수로 파생시키고, 정성 신호(스폰서 이탈·구매팀 태도)만 계약별 `baseRisk` 상수로 손으로 넣었다.
- **왜 그렇게 정했나** — 하드코딩하면 좌석·티켓 시리즈를 손보는 순간 점수와 그래프가 어긋나 "숫자가 서로 안 맞는 더미"가 된다. 파생시키면 부분합=총합 정합이 구조적으로 보장되고(월별 티켓 수도 생성된 티켓 로그에서 세고, 레일 합계 ARR 도 표시 중인 배열을 `reduce` 한다), 시점을 옮겼을 때 배지가 움직이는 이유가 화면 안의 다른 요소로 설명된다.
